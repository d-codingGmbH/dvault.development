## Developer Rework Note

This rework keeps the existing CI workflow contract and fixes the local formatting-gate failure mode seen during tester verification.

Repository changes:
- `tools/check-format.sh` still attempts solution-based `dotnet format whitespace DVault.slnx --verify-no-changes --no-restore` first. If the MSBuild workspace loader cannot run in a constrained local environment, it retries non-mutating folder-based whitespace verification and still fails on files that would be rewritten.
- `docs/formatting.md` now documents the solution-first check and constrained-environment fallback.

Tester path clarification:
- `bash tools/check-format.sh` and `bash tools/verify-packages.sh` are command invocations, not repository file paths. Validate them through `.github/workflows/ci.yml` step names and `run:` lines plus the real scripts `tools/check-format.sh` and `tools/verify-packages.sh`.
- `dotnet build DVault.slnx` and `dotnet test DVault.slnx` are also command invocations. Validate them through `.github/workflows/ci.yml` and the root `DVault.slnx` file.
- `bin/packages/` is generated by `dotnet pack DVault.slnx --configuration Release --nologo`. It is intentionally untracked because `.gitignore` excludes `bin/`, and tracking a placeholder there would conflict with `tools/DCoding.Data.DVault.PackageVerification/PackageVerifier.cs`, which reports non-`.nupkg` and non-`.snupkg` files as unexpected package artifacts.

Local verification performed in this sandbox:
- `bash -n tools/check-format.sh tools/verify-packages.sh` passed.
- `bash tools/check-format.sh` passed after the new fallback: one-member-per-file passed for 31 packable source files, folder whitespace verification passed, and the command exited 0.
- `dotnet build DVault.slnx --nologo` and `dotnet test DVault.slnx --nologo --filter "Category!=ProviderIntegration.ExternalOptIn"` were attempted but could not complete because this sandbox denies network access to `https://api.nuget.org/v3/index.json`.
- `bash tools/verify-packages.sh` was exercised without a fresh successful pack and correctly failed on incomplete/stale `bin/packages` contents, demonstrating the package verifier remains a blocking gate after `dotnet pack`.
