# Provider Optimization Gap Matrix

Status: v1 planning matrix
Ticket: 06FBSC4HSXFJ5FM6GWECH2CTGG

## Purpose

This document turns the current provider optimization evidence into a prioritized backlog matrix for later save and read strategy work. It uses [Provider Optimization Evidence Matrix](provider-optimization-evidence-matrix.md) as the canonical row lookup surface and cites the checked-in benchmark and architecture documents instead of restating raw benchmark output.

The matrix separates capability gaps from evidence gaps:

- PostgreSQL `latest-satellite-read` rows are capability gaps because the checked-in guidance rows record `providerSpecificReadStrategy=not registered for latest satellite reads`.
- SQL Server, MySQL, Oracle, and DB2 `latest-satellite-read` rows plus PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `provider-native-bulk-ingestion` rows are evidence gaps because provider strategy posture is already visible, but the root benchmark triplet keeps those optional-provider rows as skipped placeholders when connection strings are unset.
- PostgreSQL, SQL Server, and MySQL `pit-as-of-read` and `bridge-traversal-read` are closed evidence rows for this matrix when cited through the checked-in provider-configured v0.32.0 smoke-read bundle. The root quick triplet still preserves skipped PostgreSQL, SQL Server, and MySQL placeholders for unconfigured local runs and is not the completed timing source.
- Oracle and DB2 `pit-as-of-read` and `bridge-traversal-read` rows remain evidence gaps because their current repository-backed guidance is still a skipped placeholder or diagnostics/smoke posture until a provider-configured benchmark lane is checked in and promoted by its own ticket.
- DB2 rows keep the narrower v0.34.0 boundary: clean-context save and latest-satellite/PIT/bridge candidate behavior may be cited from diagnostics and smoke evidence, but no completed DB2 timing, staged DB2 bulk, or provider-native chunk execution is claimed.

## Ordering Rules

Priorities are deterministic and repository-backed:

1. `P0` rows are latest-satellite follow-ups: PostgreSQL remains a capability gap, while SQL Server, MySQL, Oracle, and DB2 are retained as evidence-gap rows until configured timing exists.
2. `P1` rows are external-provider save timing-evidence gaps, using the same provider order.
3. `P2` rows are remaining external-provider PIT as-of timing-evidence gaps after the closed PostgreSQL P2.01, SQL Server P2.02, and MySQL P2.03 rows, using the same provider order.
4. `P3` rows are remaining external-provider bridge traversal timing-evidence gaps after the closed PostgreSQL P3.01, SQL Server P3.02, and MySQL P3.03 rows, using the same provider order.

SQLite completed timing rows are reference baselines, not backlog gaps.
