# Provider Optimization Gap Matrix

Status: v1 planning matrix
Ticket: 06FBSC4HSXFJ5FM6GWECH2CTGG

## Purpose

This document turns the current provider optimization evidence into a prioritized backlog matrix for later save and read strategy work. It uses [Provider Optimization Evidence Matrix](provider-optimization-evidence-matrix.md) as the canonical row lookup surface and cites the checked-in benchmark and architecture documents instead of restating raw benchmark output.

The matrix separates capability gaps from evidence gaps:

- PostgreSQL `latest-satellite-read` is a closed capability gap because the checked-in guidance row now records `PostgresDataVaultReadStrategy` for supported hub-parent, non-multi-active latest-satellite requests; the row remains a skipped placeholder until a provider-configured timing lane runs.
- SQL Server and Oracle `latest-satellite-read` rows plus PostgreSQL, MySQL, and Oracle `provider-native-bulk-ingestion` rows remain evidence gaps because provider strategy posture is already visible, but the root benchmark triplet keeps those optional-provider rows as skipped placeholders when connection strings are unset.
- MySQL `latest-satellite-read` is closed as a scoped completed-timing baseline by the checked-in ticket `06FE4QQ9VF7B74E60CXEHSS5XW` provider-configured benchmark triplet. That closure keeps the current window-function path and proves `MySqlDataVaultReadStrategy` selection; it does not claim a provider-neutral fallback improvement comparator by itself.
- SQL Server `provider-native-bulk-ingestion` is closed for this matrix only when cited through the ticket-specific configured SQL Server bulk-threshold bundle.
- PostgreSQL, SQL Server, MySQL, and Oracle `pit-as-of-read` and `bridge-traversal-read` are closed evidence rows for this matrix when cited through the checked-in provider-configured v0.32.0 smoke-read bundle. The root quick triplet still preserves skipped PostgreSQL, SQL Server, MySQL, and Oracle placeholders for unconfigured local runs and is not the completed timing source.
- DB2 `provider-native-bulk-ingestion`, `latest-satellite-read`, `pit-as-of-read`, and `bridge-traversal-read` rows are closed evidence rows for this matrix when cited through the checked-in provider-configured DB2 hotspot bundle for ticket `06FE4QR3DD7EFZ4F35SBTFGWSR`.
- DB2 rows keep the narrower provider boundary: completed timing is limited to clean-context optimized save plus supported latest-satellite/PIT/bridge reads, while staged DB2 bulk, provider-native chunk execution, DB2 live-schema timing evidence, dirty-context saves, unsupported latest-satellite shapes, stale PIT/bridge maintenance, and incomplete read-shape evidence remain outside the claim.

## Ordering Rules

Priorities are deterministic and repository-backed:

1. `P0` rows are latest-satellite follow-ups: PostgreSQL P0.01 is closed as a capability gap by strategy registration, MySQL P0.03 is closed as a scoped completed-timing baseline by the ticket `06FE4QQ9VF7B74E60CXEHSS5XW` bundle, SQL Server P0.02 and Oracle P0.04 remain evidence-gap rows, and DB2 P0.05 is closed by the provider-configured DB2 hotspot bundle.
2. `P1` rows are external-provider save timing-evidence rows: PostgreSQL P1.01, MySQL P1.03, and Oracle P1.04 remain evidence gaps, while SQL Server P1.02 is closed by the configured 2026-06-20 bulk-threshold bundle and DB2 P1.05 is closed by the provider-configured DB2 hotspot bundle.
3. `P2` rows are external-provider PIT as-of timing-evidence rows: PostgreSQL P2.01, SQL Server P2.02, MySQL P2.03, and Oracle P2.04 are closed by the v0.32.0 smoke-read bundle, and DB2 P2.05 is closed by the provider-configured DB2 hotspot bundle.
4. `P3` rows are external-provider bridge traversal timing-evidence rows: PostgreSQL P3.01, SQL Server P3.02, MySQL P3.03, and Oracle P3.04 are closed by the v0.32.0 smoke-read bundle, and DB2 P3.05 is closed by the provider-configured DB2 hotspot bundle.

SQLite completed timing rows are reference baselines, not backlog gaps. Oracle and DB2 PIT and bridge rows are closed external-provider timing rows, not backlog gaps.

## v0.42 Gap Gate Interpretation

The v0.42 release gate uses this matrix as the deferred-work and stop-condition surface, not as a timing evidence source. A gap row may justify follow-up work only inside the provider and shape shown in the row. It does not promote skipped placeholders, diagnostics-only posture, smoke-only posture, or storage-footprint evidence into measured provider timing.

Apply these tuning boundaries when deciding whether a gap can close:

- PostgreSQL save work keeps the direct or UNNEST path below 60 operations and staged COPY at 60-plus operations.
- SQL Server save work keeps native bulk at 50-plus total operations and no more than 500 satellite operations.
- MySQL save work keeps retained multi-row behavior for smaller eligible batches and staged bulk for larger eligible batches, while tiny satellite-history fallback remains provider-neutral.
- Oracle save work keeps direct optimized batching at 50-plus total operations and no more than 10000 satellite operations; staged Oracle bulk remains unclaimed without new completed evidence.
- DB2 work stays limited to the checked-in completed clean-context save plus diagnostics-gated latest-satellite/PIT/bridge rows from the DB2 hotspot bundle; staged DB2 bulk, provider-native chunk execution, dirty-context save support, unsupported latest-satellite shapes, stale PIT/bridge maintenance, incomplete read-shape evidence, and DB2 live-schema timing evidence remain outside this matrix.

Provider-neutral fallback remains the public behavior whenever a required `DVAULT_TEST_*` connection string is unset, provider diagnostics do not select the expected strategy, the provider mismatches, the context is dirty for provider save work, a latest-satellite request is outside the supported hub-parent non-multi-active shape, read-shape evidence is incomplete, or PIT/bridge maintenance is stale.

## Follow-Up Split Guidance

Future tickets should split by gap family:

- Strategy-expansion work: PostgreSQL latest-satellite strategy registration is closed in `P0.01`; reopen only if the supported shape boundary changes.
- Latest-satellite evidence collection: `P0.02` and `P0.04` when configured benchmark lanes are available; PostgreSQL latest-satellite timing also requires an opt-in provider-configured run before any measured timing claim. Reopen MySQL `P0.03` only for a provider-neutral comparator, steadier multi-iteration evidence, or a changed supported read boundary, and reopen DB2 `P0.05` only if the benchmark lane, accepted artifact, or supported shape boundary changes.
- Save evidence work: PostgreSQL `P1.01`, MySQL `P1.03`, and Oracle `P1.04` provider-native bulk ingestion timing gaps remain. SQL Server `P1.02` is closed by the configured 2026-06-20 bulk-threshold bundle and DB2 `P1.05` is closed for the clean-context set-based save boundary only; do not split them again unless a future ticket changes the benchmark lane, rejects the artifact, or changes the supported save boundary.
- Read evidence work: PostgreSQL `P2.01`/`P3.01`, SQL Server `P2.02`/`P3.02`, MySQL `P2.03`/`P3.03`, and Oracle `P2.04`/`P3.04` are closed by the provider-configured v0.32.0 smoke-read bundle; DB2 `P2.05`/`P3.05` are closed by the provider-configured DB2 hotspot bundle. Split new read work only if a future ticket changes the benchmark lane, rejects the artifact, or changes the supported read boundary.

Do not combine capability design with external-provider timing collection unless the ticket also provisions the exact provider, connection-string gate, benchmark artifact triplet, diagnostics evidence, and finite fallback behavior needed for that provider and scenario.
