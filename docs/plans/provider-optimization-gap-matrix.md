## Purpose

This document turns the current provider optimization evidence into a prioritized backlog matrix for later save and read strategy work. It uses [Provider Optimization Evidence Matrix](provider-optimization-evidence-matrix.md) as the canonical row lookup surface and cites the checked-in benchmark and architecture documents instead of restating raw benchmark output.

The matrix now separates closed provider optimization gaps from ongoing runtime boundaries:

- PostgreSQL `latest-satellite-read` moved from capability-only closure to completed timing evidence in the 2026-06-23 provider optimization closure bundle. The completed row selected `PostgresDataVaultReadStrategy` and averaged `15.068` ms.
- SQL Server and Oracle `latest-satellite-read` rows are closed by the same closure bundle. SQL Server completed with `SqlServerDataVaultReadStrategy` at `20.337` ms, and Oracle completed with `OracleDataVaultReadStrategy` at `18.783` ms after the ODP.NET LOB-prefetch read tuning.
- PostgreSQL, MySQL, Oracle, SQL Server, and DB2 `provider-native-bulk-ingestion` rows are closed by provider-configured timing rows in the closure bundle. MySQL keeps the split retained multi-row, bounded staged, and deliberate large mixed provider-neutral fallback rows; DB2 keeps its clean-context set-based path and measured 1000-row command cap.
- PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `pit-as-of-read` and `bridge-traversal-read` rows are closed by the closure bundle. Earlier v0.32.0 and DB2 hotspot bundles remain historical evidence, but the current completed timing source is the 2026-06-23 closure bundle.
- Remaining boundaries are runtime fallback boundaries, not open optimization gaps: provider mismatch, dirty contexts for save work, unsupported latest-satellite shapes, stale or incomplete PIT/bridge read-model evidence, unsupported bridge maintenance push-down, evaluated but unimplemented MySQL PIT full-rebuild maintenance push-down, DB2 staged bulk, and provider-native chunk execution still fall back or remain unclaimed.

Priorities are deterministic and repository-backed:

1. `P0` rows are latest-satellite rows. PostgreSQL P0.01, SQL Server P0.02, MySQL P0.03, Oracle P0.04, and DB2 P0.05 are closed by completed provider-configured timing rows.
2. `P1` rows are external-provider save timing rows. PostgreSQL P1.01, SQL Server P1.02, MySQL P1.03, Oracle P1.04, and DB2 P1.05 are closed by completed provider-configured timing rows.
3. `P2` rows are external-provider PIT as-of timing rows. PostgreSQL P2.01, SQL Server P2.02, MySQL P2.03, Oracle P2.04, and DB2 P2.05 are closed by completed provider-configured timing rows.
4. `P3` rows are external-provider bridge traversal timing rows. PostgreSQL P3.01, SQL Server P3.02, MySQL P3.03, Oracle P3.04, and DB2 P3.05 are closed by completed provider-configured timing rows.

SQLite completed timing rows are reference baselines, not backlog gaps. Oracle and DB2 PIT and bridge rows are closed external-provider timing rows, not backlog gaps.

## v0.42 Gap Gate Interpretation

The v0.42 release gate uses this matrix as the deferred-work and stop-condition surface, not as a timing evidence source. A gap row may justify follow-up work only inside the provider and shape shown in the row. It does not promote skipped placeholders, diagnostics-only posture, smoke-only posture, or storage-footprint evidence into measured provider timing.

Apply these tuning boundaries when deciding whether a future change still fits the closed evidence:

- PostgreSQL save work keeps the direct or UNNEST path below 60 operations and staged COPY at 60-plus operations.
- SQL Server save work keeps native bulk at 100-plus total operations, mixed hub/link batches at 900-plus total operations, and no more than 500 satellite operations.
- MySQL save work keeps retained multi-row behavior for smaller eligible batches, staged bulk for the bounded measured window, and provider-neutral fallback for large mixed hub/link batches, while tiny satellite-history fallback remains provider-neutral.
- Oracle save work keeps direct optimized batching at 50-plus total operations and no more than 10000 satellite operations; staged Oracle bulk remains unclaimed without new completed evidence.
- DB2 work stays limited to clean-context set-based save with the measured 1000-row command cap plus diagnostics-gated latest-satellite/PIT/bridge rows; staged DB2 bulk, provider-native chunk execution, dirty-context save support, unsupported latest-satellite shapes, stale PIT/bridge maintenance, and incomplete read-shape evidence remain outside this matrix.

Provider-neutral fallback remains the public behavior whenever a required `DVAULT_TEST_*` connection string is unset, provider diagnostics do not select the expected strategy, the provider mismatches, the context is dirty for provider save work, a latest-satellite request is outside the supported hub-parent non-multi-active shape, read-shape evidence is incomplete, or PIT/bridge maintenance is stale.
