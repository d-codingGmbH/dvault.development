## Stable Hash Algorithm Guidance

`AddDVault()` keeps `sha256-v1` as the default stable hash service registration. The default compatibility contract is SHA-256 over UTF-8 normalized input bytes without a byte order mark, serialized as 32 digest bytes and 64 lowercase hexadecimal characters. This remains the safe baseline for persisted hub keys, link keys, hash diffs, and related stable hashes because it preserves the repository-published vectors and the existing provider-neutral hash contract.

The built-in stable hash ids are:

| AlgorithmId | Registration posture | Digest bytes | Hex characters | Guidance |
| --- | --- | ---: | ---: | --- |
| `sha256-v1` | Default registered by `AddDVault()` | 32 | 64 | Safe persisted-compatibility baseline |
| `sha1-v1` | Explicit opt-in only | 20 | 40 | Non-adversarial identity tradeoff only |
| `sha256-128-v1` | Explicit opt-in only | 16 | 32 | Non-adversarial shorter SHA-256-derived identity tradeoff |
| `sha256-160-v1` | Explicit opt-in only | 20 | 40 | Non-adversarial shorter SHA-256-derived identity tradeoff |

`AddDVault()` does not automatically register or enable `sha1-v1`, `sha256-128-v1`, or `sha256-160-v1`. A caller must deliberately select a non-default built-in id through stable-hash options or provide a replacement `IStableHashService`. Provider packages may optimize transport, staging, existence checks, and insert shapes, but they must not silently replace the registered stable hash normalizer or service with provider SQL hashing.

Shorter digest ids may be reasonable only when the caller has a non-adversarial Data Vault identity-hashing use case and accepts the collision-risk and compatibility tradeoff for its key volume, retention period, reload strategy, and downstream comparisons. `sha256-128-v1` and `sha256-160-v1` use the leading bytes of the `sha256-v1` digest for the same normalized input, then serialize those bytes as lowercase hexadecimal text under their own algorithm ids.

`sha1-v1` is not a security or compliance control. It must not be cited as a password-hashing policy, message authentication code, digital signature, encryption scheme, regulatory control, or adversarial collision-defense policy. Callers with cryptographic, regulatory, or adversarial-collision requirements must use a separate security-specific component.

## Compatibility And Migration Posture

Algorithm ids are part of persisted stable-hash semantics. Changing the algorithm id, digest length, truncation policy, scalar normalization, field ordering, or culture formatting after hub keys, link keys, hash diffs, or other stable-hash values have been persisted is caller-owned compatibility work.

DVault does not automatically rehash, backfill, migrate, repair, reconcile, or dual-write existing stored values when callers replace the stable hash service or select a different built-in id. Consumers that intentionally change algorithms should model that as an application migration with reviewed compatibility rules, not as an implicit DVault runtime feature.

Stable model and key hashing remain separate from the persistence content hash tuple contract. `DataVaultConventions.PersistenceContentHashAlgorithm` continues to describe the storage-integrity policy value `sha-256`, and persistence `content_hash` values keep their storage-policy shape. Selecting a non-default stable-hash id does not weaken, replace, or broaden persistence content-hash semantics.

## Validation Evidence

The repository validation command baseline remains:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/verify-packages.sh
bash tools/check-format.sh
```

Package-tested evidence is the release pack script plus package verification lane. `bash tools/pack-release-packages.sh` creates eight `8.35.0` `.nupkg` files for `net8.0` / EF Core 8 and eight `10.35.0` `.nupkg` files for `net10.0` / EF Core 10, plus matching runtime/provider symbol packages. `bash tools/verify-packages.sh` checks the sixteen `.nupkg` files, the fourteen expected symbol packages, package metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, DB2 `IBM.EntityFrameworkCore` dependency alignment, and the line-specific `net8.0` or `net10.0` dependency group for each package version.

Stable hash evidence is anchored by:

- [Stable Hashing Contract](../plans/stable-hashing-contract.md) for the default `sha256-v1` contract, non-default candidate set, caveats, normalization rules, vectors, and no-automatic-migration posture.

## Limitations And Non-Goals

v0.35.0 does not change the runtime default stable hash algorithm, canonical normalizer, built-in algorithm set, `StableHashDigest` validation rules, provider-side hashing behavior, or persistence content-hash semantics.

v0.35.0 does not add automatic rehashing, backfilling, dual-writing, persisted-key repair, migration tooling, collision simulation, quantitative sizing tables, benchmark rows, or provider-specific diagnostics for algorithm selection.

v0.35.0 does not make `sha1-v1` or truncated SHA-256 ids security features, compliance controls, password-hashing policies, message authentication codes, digital signatures, encryption schemes, or adversarial collision-defense policies.

v0.35.0 does not record package publication. Package publication, final approval, package hashes, published package links, signing evidence, and stop-condition resolution remain separate release-operation records governed by the manual publication checklist.
