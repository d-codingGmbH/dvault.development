# DVault v0.7.0 Release Notes

Release: `v0.7.0 - Model-First Governance and Read Flows`
Intended release date: 2026-05-12

## Package Scope

This is a coordinated release for the six-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.7.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Added model-first governance documentation for reviewed `dvault.model.v1` JSON artifacts alongside the existing Code-First and metadata-first declaration paths.
- Documented public model-first import, EF projection, canonical export, and drift comparison surfaces: `DataVaultModelArtifactImporter.ImportJson`, `UseDataVaultMetadata(DataVaultModelImportResult)`, `DataVaultModelArtifactExporter.ExportJson`, and `DataVaultModelDriftReporter.Compare`.
- Defined the v0.7.0 artifact baseline as JSON-first and exact-versioned with the top-level `schemaVersion` value `dvault.model.v1`.
- Preserved canonical declaration order for the stable JSON categories `hubs`, `links`, `satellites`, `pits`, and `bridges`, including strict unknown-field rejection at every object level.
- Documented the YAML boundary: teams may convert YAML before DVault sees the model, but first-party ingestion accepts JSON and does not define YAML parser semantics.
- Updated README guidance so Code-First, metadata-first, and model-first are distinct supported declaration paths rather than replacements for one another.
- Documented implemented latest/as-of satellite reads, provider-neutral PIT-backed as-of reads, and provider-neutral bridge reads without claiming PIT refresh, PIT row maintenance, bridge row maintenance, full graph traversal, or provider-specific PIT/bridge optimization.
- Documented bridge read usage around endpoint hash-key filtering, many-to-many `From`/`To` endpoints, hierarchy `Ancestor`/`Descendant` endpoints, bounded hierarchy `maximumDepth`, `TraversalDepth`, and typed projection delegates that read exact generated column names.
- Kept benchmark summary language tied to repository evidence: latest satellite, PIT as-of, and bridge read rows are available through the benchmark harness, while provider-specific read optimization evidence is currently limited to the latest-satellite read surface documented by the benchmark README.

## Declaration Path Guidance

Code-First declarations remain the app-local EF model path for the implemented fluent hub, hub-parent satellite, multi-active driving-key, and ordered hub-link surface through `ApplyDataVaultMetadata(vault => ...)`.

Metadata-first declarations remain the shared registry-backed path when a `DataVaultMetadataModel` or `DataVaultMetadataRegistry` should drive schema projection, explicit saves, typed latest/as-of reads, diagnostics, examples, or provider setup through `AddDVault(...)` and `UseDataVaultMetadata()`.

Model-first governance is the v0.7.0 path when the source-controlled model authority should be a reviewed `dvault.model.v1` JSON artifact. Import diagnostics, EF projection, canonical export, and drift reports become review evidence for that artifact. The detailed workflow is documented in `docs/model-first-governance.md`.

## Model-First Governance Notes

`dvault.model.v1` artifacts must use the exact `schemaVersion` string `dvault.model.v1`. v1 consumers reject missing values, non-string values, `dvault.model`, `dvault.model.v1.0`, `dvault.model.v2`, vendor-prefixed dialects, and future schema versions until a separate future contract supports them.

Canonical JSON uses the stable top-level declaration categories `hubs`, `links`, `satellites`, `pits`, and `bridges`. `naming.policy` defaults to `default`; `loadTimestampStorage` defaults to `provider-default`; supported timestamp storage tokens are `provider-default`, `iso-8601-utc-text`, and `utc-ticks`.

Unknown fields are errors at every object level, including nested `naming`, parent reference, participant, and bridge endpoint objects. Import, export, EF projection, and drift evidence preserve declaration array order, so reviewers should treat ordering as part of the governed model.

Canonical export is available from fluent Code-First declaration callbacks and already materialized metadata through `DataVaultModelArtifactExporter.ExportJson`. It accepts a Code-First declaration callback, `DataVaultMetadataModel`, and `DataVaultMetadataRegistry`. It does not extract artifacts from arbitrary EF `ModelBuilder` state, runtime save/read state, or legacy `PointInTimeTables` metadata.

Drift comparison through `DataVaultModelDriftReporter.Compare` is design-time EF metadata comparison. It does not inspect a live database.

## Advanced Read Flow Notes

Latest and as-of satellite reads continue through `IDataVaultReadService` and `DataVaultLatestSatelliteReadRequest`. `ReadLatestSatelliteAsync(...)` maps selected rows through caller-owned projection delegates, and `ReadLatestSatelliteRowsAsync(...)` remains the raw row-level escape hatch for `DataVaultSatelliteReadRecord` values.

PIT-backed as-of reads use `DataVaultPitAsOfReadRequest` and `IDataVaultReadService.ReadPitRowsAsync(...)` for raw `DataVaultPitReadRecord` rows. `DataVaultReadServicePitExtensions.ReadPitAsync(...)` maps selected rows through caller-owned delegates with exact-name access to `ParentHashKey`, `LoadTimestamp`, and declared satellite segments. The current PIT read surface expects already materialized PIT rows and does not maintain or refresh them.

Bridge reads use `DataVaultBridgeReadRequest` with endpoint hash-key filtering. Many-to-many bridge reads use `DataVaultBridgeTraversalEndpoint.From` or `DataVaultBridgeTraversalEndpoint.To`. Hierarchy bridge reads use `DataVaultBridgeTraversalEndpoint.Ancestor` or `DataVaultBridgeTraversalEndpoint.Descendant` and require a bounded `maximumDepth`. `ReadBridgeRowsAsync(...)` returns `DataVaultBridgeReadRecord` rows with endpoint values in generated column order, while `ReadBridgeAsync(...)` maps `DataVaultBridgeProjectionRow` values through caller-owned typed projection delegates.

Bridge projection delegates read exact generated column names. Current examples use names such as `OrderHashKey`, `AncestorSalesRegionHashKey`, `DescendantSalesRegionHashKey`, and `TraversalDepth`. The bridge read surface does not maintain bridge rows, infer graph closure, expose full graph traversal semantics, or provide provider-specific bridge read optimization.

## Benchmark And Package Verification Notes

The benchmark README documents the current evidence boundary for read models. The default benchmark matrix includes latest satellite, PIT as-of, and bridge traversal read scenarios. Fixture creation and seeding run before the timed operation so measured rows focus on `ReadLatestSatelliteRowsAsync(...)`, `ReadPitRowsAsync(...)`, and `ReadBridgeRowsAsync(...)`.

SQLite latest-satellite read rows compare provider-neutral `AddDVault()` fallback with the `AddDVaultSqlite()` optimized provider read strategy. PIT and bridge read rows remain provider-neutral baselines. Do not cite provider-specific PIT or bridge read optimization until repository benchmark artifacts measure such a surface.

Package verification remains governed by `docs/manual-nuget-publication.md`. Before publication, the release operator must run the build, test, pack, package verification, and format gates from the same checkout. `bash tools/verify-packages.sh` validates the six-package family, matching symbols, package README/XML metadata, and provider dependency alignment against the packed `DCoding.Data.DVault` version. These notes do not imply that v0.7.0 packages have already been published.

## Compatibility Notes

- v0.6.0 Code-First declarations remain compatible. Applications can keep declaring supported hubs, hub-parent satellites, multi-active driving keys, and ordered hub links in `OnModelCreating` through `ApplyDataVaultMetadata(vault => ...)`.
- Metadata-first `DataVaultMetadataModel` and `DataVaultMetadataRegistry` usage remains compatible for shared schema, explicit saves, read metadata, diagnostics, examples, and provider setup.
- Model-first governance is additive. It provides a reviewed JSON artifact path and does not remove Code-First or metadata-first usage.
- There is still no extraction from arbitrary EF `ModelBuilder` state into a model artifact. Use Code-First declaration callbacks, metadata-first, or model-first when a reusable public metadata artifact is required.
- YAML is not a first-party ingestion format. Convert YAML outside DVault and review the canonical JSON that DVault imports.
- Current read-service additions are provider-neutral except for the documented SQLite latest-satellite optimized read strategy. Provider-specific save strategies continue to be separate from provider-specific read optimization.

## Known Limitations

- No first-party model-first CLI commands are delivered in v0.7.0.
- No documented CI gate snippets for model-first drift reports are delivered in v0.7.0.
- No direct YAML ingestion or YAML fixture contract is delivered in v0.7.0.
- No live database drift introspection is delivered in v0.7.0.
- No extraction from arbitrary EF `ModelBuilder` state into a model artifact is delivered in v0.7.0.
- PIT refresh, PIT row maintenance, and bridge row maintenance are not delivered in v0.7.0.
- Full graph traversal semantics and complex bridge traversal maintenance are not delivered in v0.7.0.
- Provider-specific PIT or bridge read optimizations are not delivered in v0.7.0.
