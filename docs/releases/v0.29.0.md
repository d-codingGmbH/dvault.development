## Boundary Shift From v0.28.0

v0.28.0 moved the coordinated public baseline forward for provider read optimization guidance. That evidence boundary remains intact and historical.

v0.29.0 moves the public documentation baseline forward for provider identifier and DDL guardrail guidance. It documents the finite supported-provider schema baseline, how provider-neutral logical names relate to provider-safe physical names, which provider caveats matter during generated DDL review, and how adopters should run the existing design-time validation, drift, and migration guardrail lanes before applying schema changes.

This release is documentation-focused. It does not change provider capability profiles, annotations, diagnostics, migration guardrail runtime behavior, generated schema behavior, provider package registrations, benchmark evidence, or package publication state.

## Supported Provider Schema Baseline

The supported-provider baseline for provider-specific schema safety claims is finite:

| Provider | EF provider name evidence | DVault capability profile | Documentation baseline facts |
| --- | --- | --- | --- |
| SQLite | `Microsoft.EntityFrameworkCore.Sqlite` | `sqlite-v1` | No profile identifier cap is currently declared; unsupported included-index columns are appended to the index key when needed. |
| Oracle | `Oracle.EntityFrameworkCore` | `oracle-v1` | No profile identifier cap is currently declared; unsupported included-index columns are appended to the index key when needed; secondary indexes covered by the primary key are not treated as safe. |
| PostgreSQL | `Npgsql.EntityFrameworkCore.PostgreSQL` | `postgres-v1` | No profile identifier cap is currently declared; native included-index columns are preserved. |
| SQL Server | `Microsoft.EntityFrameworkCore.SqlServer` | `sqlserver-v1` | No profile identifier cap is currently declared; native included-index columns are preserved. |
| MySQL | `Pomelo.EntityFrameworkCore.MySql`, `MySql.EntityFrameworkCore` | `mysql-pomelo-v1` | Physical identifiers are capped at 64 characters; unsupported included-index columns are ignored. |

Unrecognized providers do not inherit provider-specific DDL safety guarantees from these profiles. They may still use existing provider-neutral APIs where supported by the current code path, but documentation and adopter records must not claim provider-specific identifier safety, included-index behavior, duplicate-index safety, live-schema behavior, or migration DDL support for an unrecognized provider.

## Logical And Physical Name Guidance

DVault logical names stay provider-neutral. Logical table, column, primary-key, index, PIT, bridge, participant, payload, and technical names come from the default naming policy and metadata declarations. `DataVaultAnnotationNames.ProducedName` remains the traceable DVault-produced logical name for generated EF metadata, and provider-specific projection must not replace that logical annotation.

Provider profiles may derive provider-safe physical names only when a generated logical name is unsafe for a supported provider because of identifier length, reserved-word, escaping, native included-index, duplicate-index, or post-truncation collision rules. When a physical name differs from the logical produced name, adopters should expect traceability through the produced-name annotation, metadata-name annotation, provider-profile annotation, EF relational metadata, live-schema snapshots, migration summaries, and guardrail diagnostics.

Physical projection is scoped to DVault-owned generated metadata. DVault does not rewrite arbitrary consumer-authored migration operations, raw SQL, third-party DDL, or provider objects outside the generated Data Vault model.

## Provider DDL Caveats

Generated indexes, keys, and future generated constraints must be reviewed as provider-specific DDL, not just as provider-neutral logical metadata:

- PostgreSQL and SQL Server may preserve included-index columns through native provider support.
- SQLite and Oracle currently project unsupported included-index columns by appending them to the effective index key.
- MySQL currently ignores unsupported included-index columns.
- Oracle currently treats secondary indexes covered by the primary key as unsafe or redundant and omits them from generated metadata.
- MySQL currently enforces a 64-character identifier cap in its capability profile.

Load timestamp storage is also part of the provider profile. The `dvault.model.v1` tokens remain `provider-default`, `iso-8601-utc-text`, and `utc-ticks`. The selected token changes the provider capability profile's load timestamp and satellite snapshot reference mappings only. A migration that changes the store type or value format away from the selected profile should be reviewed as schema drift unless the metadata contract intentionally changed the token.

## Examples

### MySQL Identifier Length

A model-first artifact may keep a long logical satellite or index name so reviewers can understand the business meaning. When the selected provider profile is `mysql-pomelo-v1`, generated physical identifiers must fit the 64-character MySQL limit. A safe projection can preserve a readable left prefix and append a deterministic hash suffix while keeping `ProducedName` as the original logical name. If no safe physical name can be produced without collision or truncation ambiguity, validation or migration guardrails should fail before unsafe DDL is emitted. The adopter response is to rename the source declaration or role, split the declaration, or choose a supported profile that can represent the shape.

### Oracle Duplicate Index Review

A generated satellite or PIT shape can produce a secondary index whose effective key is covered by a primary key. Under the `oracle-v1` profile, that duplicate index is not a safe generated DDL claim. The reviewed EF model and migration guardrail report should show the Oracle profile and effective index shape instead of pretending that Oracle emitted the provider-neutral index unchanged. The adopter response is to keep the migration aligned with the generated DVault metadata and block incompatible hand-edited operations that reintroduce the unsafe index.

### Unsupported Provider Claim

If a consumer configures a provider name outside SQLite, Oracle, PostgreSQL, SQL Server, and MySQL, the project can still run the provider-neutral validation and drift workflow where the current API supports it. The documentation baseline does not allow the consumer to say that the provider has DVault provider-specific DDL safety. The adopter response is to treat provider-specific migration DDL as unsupported until a future contract adds that provider profile and its identifier, index, load-timestamp, and diagnostics facts.

## Adopter Workflow

Adopters should keep the provider schema guardrail lane inside the consumer-owned design-time workflow:

1. Import and review any `dvault.model.v1` artifact with `DataVaultModelArtifactImporter.ImportJson(...)`.
2. Build the configured design-time `DbContext` through the consumer-owned factory.
3. Run `dotnet run --project <consumer-project> -- validate` to analyze the configured model and provider explain output.
4. When a reviewed artifact exists, run `dotnet run --project <consumer-project> -- drift --artifact <path>` before accepting schema changes.
5. Scaffold EF migrations normally with `dotnet ef migrations add`.
6. Before `dotnet ef database update` or integration, run `dotnet run --project <consumer-project> -- guardrail --migration <name>`.
7. Review `DataVaultMigrationGuardrailReport.ToDisplayString()` and the per-operation `Safe`, `Risky`, or `Incompatible` outcomes from `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)`.
8. Stop on incompatible output until the generated migration is corrected or the reviewed metadata contract intentionally changes.

`DataVaultPreflight.Run(...)` can aggregate validation, reviewed-artifact drift, explicit snapshot-model drift, idempotency live-schema preflight, migration guardrail, and representative request diagnostics when the consumer supplies those inputs. Omitted lanes are not auto-discovered.

## Limitations And Non-Goals

v0.29.0 does not add provider support beyond SQLite, Oracle, PostgreSQL, SQL Server, and MySQL. It does not give unrecognized providers provider-specific DDL safety guarantees or silently map them to one of the supported profiles.

v0.29.0 does not add automatic migration repair, migration execution, EF command interception, a migration runner, schema synchronization, schema drift repair, physical-design advice, automatic index creation, automatic live-database validation, raw SQL rewriting, arbitrary DDL rewriting, or provider command execution.

v0.29.0 does not add a consumer-visible physical naming override API, broaden `dvault.model.v1` tokens, change default logical naming, rewrite consumer-authored migrations, change provider capability profiles, change `DataVaultMigrationOperationDiagnostics`, change `DataVaultMigrationGuardrailReport`, change Activity tracing behavior, publish packages, publish support bundles, or alter package verification automation.

The guardrail lane is design-time and review-oriented. It evaluates configured model evidence and scaffolded EF migration operations, reports bounded diagnostics, and helps consumers block unsafe provider-specific DDL before apply. It does not apply the migration or repair the migration automatically.
