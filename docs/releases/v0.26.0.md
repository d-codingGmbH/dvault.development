Release: `v0.26.0 - Provider Performance And Schema Guardrails`
Intended release date: 2026-06-02

## Boundary Shift From v0.25.0

v0.25.0 moved the coordinated public baseline forward for request-bound `ReadShape` diagnostics and support-bundle-driven satellite, PIT, and bounded bridge typed read helpers. That boundary remains intact and historical.

v0.26.0 makes the current public documentation baseline coherent around provider-tuning diagnostics, benchmark verifier evidence, migration guardrails, idempotency preflight, and the stored-procedure artifact boundary. It aligns README, performance profiles, the production checklist, architecture guidance, and release notes with the already-landed repository contracts.

This release does not add runtime behavior. It does not add diagnostics fields, verifier rules, benchmark rows, benchmark artifact fields, provider-specific SQL generation, stored-procedure execution, migration automation, schema repair, package publication, or release automation.

## Performance Profile Baseline

The public performance guidance uses four checked-in performance-profile categories:

- `SmallAppLocalVault`
- `MediumChunkedIngestion`
- `StagedProviderIngestion`
- `ReadModelHeavy`

The adopter-facing labels are small app-local vault, medium chunked ingestion, staged provider ingestion, and read-model heavy. These categories are documented in [Performance Profiles](../performance-profiles.md) and are tied to the root benchmark artifact triplet:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

Timing values remain observations from the checked-in run only. Documentation must keep run context attached to timing claims: 3 iterations, 1 warmup iteration, `ProviderDefault` load timestamp storage, provider filter `all`, Debian GNU/Linux 13 x64, .NET 10.0.8, required SQLite local temporary files, and optional PostgreSQL, SQL Server, MySQL, and Oracle rows skipped when their connection-string environment variables are unset.

SQLite remains the only repository-proven optimized latest-satellite, PIT, and bridge read provider path. Non-SQLite optimized read claims require future benchmark evidence and should not be inferred from provider-neutral read support or provider-specific write strategy registrations.

## Provider Eligibility Diagnostics

Provider-specific optimized saves and reads remain diagnostics-gated implementations behind the existing public services. User-facing examples should show bounded strategy facts only:

```text
save strategy: ProviderNeutralFallback
provider: Microsoft.EntityFrameworkCore.SqlServer
selected strategy: <none>
candidate: SqlServerDataVaultSaveStrategy
candidate gate requirements: ProviderNameMismatch, DirtyDbContext
fallback causes: DirtyDbContext
```

Allowed provider diagnostics facts include provider names, provider profile names, strategy status, selected strategy name when present, candidate strategy names, candidate priorities, operation counts, gate requirements, and finite fallback causes.

Examples must not include raw business keys, raw hash-key values, payload values, record sources, load timestamps, SQL text, provider query plans, provider exception text, stack traces, credentials, connection strings, transient stage-row contents, or raw workload values.

The provider write boundary stays:

- PostgreSQL staged COPY starts at the documented 60-plus-operation staged boundary; smaller eligible batches retain the direct or UNNEST path.
- SQL Server native bulk starts at 50-plus total operations and accepts no more than 500 satellite operations.
- MySQL native dispatch starts at 50-plus operations; staged bulk starts at 60-plus operations; the retained multi-row path remains visible below the staged boundary.
- Oracle direct optimized batching starts at 50-plus total operations and accepts no more than 10000 satellite operations; staged Oracle remains not selected until measured evidence proves a win.

## Benchmark Verifier Evidence

The benchmark evidence story is the checked-in artifact triplet plus verifier coverage. Release and adopter docs should point to those files instead of duplicating raw evidence tables.

Bounded verifier summaries may use this shape:

```text
benchmark artifact verifier: passed
artifact triplet: benchmark-summary.md, benchmark-summary.csv, benchmark-summary.json
profile categories: SmallAppLocalVault, MediumChunkedIngestion, StagedProviderIngestion, ReadModelHeavy
required provider: SQLite local temporary files
optional provider rows: preserved as skipped when connection-string environment variables are unset
```

Repository tests verify that markdown, CSV, and JSON rows match, optional-provider context remains visible, provider-guidance rows preserve planned strategy details when skipped, and regression-budget defaults stay documented in the shared [Performance Evidence And Benchmark Artifact Contract](../plans/performance-evidence-benchmark-artifact-contract.md).

## Migration And Idempotency Guardrails

Migration guardrails remain explicit consumer-owned preflight work. Consumers scaffold EF migrations normally, resolve the proposed `MigrationOperation` values in their project, pass those operations to `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)` or `DataVaultPreflight.Run(...)`, review `Safe`, `Risky`, and `Incompatible` outcomes, and decide whether to apply the migration.

Idempotency preflight is also explicit consumer-owned work. Consumers supply a `DataVaultLiveSchemaReadResult` to `DataVaultIdempotencyPreflight.Compare(...)` or `DataVaultPreflightRequest.IdempotencyLiveSchemaReadResult` when they want live-schema evidence for idempotency-critical primary keys and secondary indexes. Missing, unsupported, unavailable, or mismatched structures are bounded report outcomes, not automatic repair instructions.

The current design-time workflow does not ship a standalone DVault CLI, intercept `dotnet ef`, discover migrations or snapshots, open live databases by default, run migrations, synchronize EF migrations, create indexes, repair schema, or perform background self-healing. Startup-project and target-project splits remain outside the v1 design-time workflow.

## Stored-Procedure Artifact Boundary

Stored procedures, generated routines, and provider-specific SQL artifacts are not DVault default runtime behavior. The default public runtime surfaces remain `IDataVaultSaveService`, `IDataVaultReadService`, explicit PIT maintenance, explicit bridge maintenance, diagnostics, support-bundle export, and typed helper generation over the existing read service.

Any stored-procedure or provider-specific SQL artifact lane must be explicit opt-in design-time output for a reviewed consumer project. The consuming application owns deployment, invocation, versioning, rollback, cleanup, credentials, environment selection, transaction behavior, monitoring, and lifecycle management. DVault does not auto-generate routines, auto-deploy artifacts, auto-invoke procedures, register a procedure dispatcher, route ordinary saves or reads through stored procedures by default, or automatically synchronize artifacts with EF migrations, live schema reads, metadata changes, model-first import/export, or support-bundle refreshes.

Future artifact proposals need their own provider evidence, migration-synchronization plan, benchmark artifact set, diagnostics examples, and parity proof with explicit DVault semantics before implementation scope is accepted.

## ReadShape And Typed Helper Baseline

The v0.25.0 read-plan and typed helper baseline carries forward unchanged:

- The read-shape kind vocabulary is closed to `LatestSatellite`, `PitAsOf`, and `Bridge`.
- `IDataVaultReadDiagnosticsService.Analyze(...)` exposes provider strategy facts through `ReadStrategy` and additive translated facts through `ReadShape`.
- Redacted `dvault.support-bundle.v1` JSON can include `readShape` only when application code supplies representative request-bound diagnostics through `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics`.
- Typed read-model generation remains opt-in with `DVaultGenerateTypedReadModels=true` and exactly one authoritative `dvault.support-bundle.v1` additional file.
- Generated helpers remain ergonomic extension methods over `IDataVaultReadService`; they do not add provider-specific SQL, dynamic request compilation, runtime maintenance, automatic support-bundle discovery, or new helper shapes.
