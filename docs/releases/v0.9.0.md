# DVault v0.9.0 Release Notes

Release: `v0.9.0 - Read and Runtime Performance Ergonomics`
Intended release date: 2026-05-15

## Package Scope

This is a coordinated release for the six-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.9.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Added `UseDataVaultSaveChangesMetadataInterceptor(...)` as an explicit opt-in EF Core interceptor for generated DVault rows.
- Kept the default `AddDVault()` persistence boundary unchanged. Applications still write through `IDataVaultSaveService` unless they deliberately use another EF tracking flow.
- Filled missing `LoadTimestamp` and `RecordSource` values on added generated hub, link, and satellite rows when those rows carry DVault metadata annotations.
- Preserved manually supplied load timestamps and record sources so callers can still provide exact batch metadata.
- Proved EF compiled model and compiled query compatibility for the generated shared-type table surface on SQLite.
- Reconfirmed the existing typed read helpers and provider save-strategy SPI as the v1 boundaries for read ergonomics and bulk-save extensibility.

## SaveChanges Metadata Interceptor

The interceptor is metadata-only. It does not create rows, compute hash keys, compute satellite hash diffs, resolve ordering, or replace `IDataVaultSaveService`.

Applications opt in at `DbContextOptionsBuilder` level:

```csharp
options.UseDataVaultSaveChangesMetadataInterceptor(interceptor => interceptor
    .UseLoadTimestamp(() => DateTimeOffset.UtcNow)
    .UseRecordSource("crm-import"));
```

The load-timestamp provider is evaluated once per `SaveChanges` operation that needs a generated timestamp, then normalized to UTC. The record-source provider is evaluated only when at least one generated DVault row needs a record source.

The interceptor targets generated EF rows by DVault entity annotations and technical-column annotations. That keeps ordinary domain entities and non-DVault tables outside the interceptor surface.

## Compiled Model and Query Compatibility

DVault v0.9.0 documents and tests the bounded EF Core compiled-model surface:

- `UseDataVaultMetadata(...)` annotations survive runtime model usage with `UseModel(...)`.
- Generated shared-type DVault tables remain queryable through EF compiled queries.
- The release does not ship a compiled-model generator, design-time compiled-model command wrapper, or provider-specific compiled-query optimizer.

## Read and Bulk Boundaries

No separate v0.9.0 read-helper family or second bulk-insert SPI was added. The release instead ratifies the existing v1 boundaries:

- Typed latest/as-of, PIT-backed, and bridge read helpers remain the public read ergonomics baseline.
- `IDataVaultProviderSaveStrategy`, provider capability profiles, and provider package strategy registration remain the public provider bulk-save extensibility point.
- Provider-specific bulk behavior still falls back to the provider-neutral writer when a strategy declines the current context or request batch.

## Compatibility Notes

- Existing `IDataVaultSaveService` callers are unaffected.
- Existing `AddDVault()` registrations do not acquire a `SaveChanges` interceptor unless the application explicitly calls `UseDataVaultSaveChangesMetadataInterceptor(...)`.
- Generated-row EF tracking flows can opt in incrementally because the interceptor only fills missing technical metadata.
- The interceptor preserves current values and therefore does not override caller-supplied load timestamp or record source values.
- Compiled model compatibility is proven for the generated shared-type table shape used by the current metadata model. Provider-specific compiled-model guarantees remain outside this release.

## Known Limitations

- The interceptor does not compute `HashKey`, parent hash keys, link participant hash keys, PIT keys, bridge keys, or satellite `HashDiff` values.
- The interceptor does not create generated DVault rows from domain entities.
- The interceptor does not replace validation or explicit ordering performed by `IDataVaultSaveService`.
- Typed CLR entities with non-null default values can appear already populated to EF; callers should provide nullable technical metadata properties or explicit values when using the interceptor outside generated shared-type rows.
- Compiled-model support is compatibility evidence, not a code generator or provider-specific compiled-query optimization surface.
- External provider live integration evidence remains opt-in through the documented connection-string environment variables.
