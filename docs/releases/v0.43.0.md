# DVault v0.43.0 Release Notes

Release: `v0.43.0 - Binary Adoption, Analyzer Guidance, and Allocation Evidence`
Release date: 2026-06-21

These notes define the coordinated v0.43.0 documentation, package-line, binary-adoption, analyzer, provider-evidence, and allocation-evidence baseline for DVault. The public release label maps to the consumer package versions `8.43.0` and `10.43.0`. There is no consumer-facing `0.43.0` package version.

This release note does not record a NuGet push, package hashes, package-signing approval, release automation, automatic migration, rehashing, backfill, dual-write, repair, provider provisioning, benchmark reruns beyond the checked-in artifacts, or widened provider capability guarantees.

## Binary-First Adoption Boundary

New projects should opt into the binary-first profile before creating a generated schema:

```csharp
services.AddDVault(options => options.UseBinaryFirstProfile());
modelBuilder.ApplyDataVaultMetadataWithBinaryFirstProfile(vault => {
  // Code-First hub, link, and satellite declarations.
});
```

The binary-first profile changes the recommended physical storage for new generated hash-key columns. It does not change the public DVault hash-key representation: public APIs, save requests, read requests, diagnostics, explain output, and support bundles continue to use canonical lowercase hexadecimal strings.

Existing persisted `HexString` setups remain compatible until the application owner intentionally plans and executes a separate reviewed migration, reset, or data-move change. Use the [Hash-Key Storage Migration Guide](../hash-key-storage-migration.md) and its `dvault.hash-key-storage-migration.v1` dry-run manifest path before changing persisted hash-key storage. Do not combine a stable-hash algorithm, digest-length, truncation, or storage-profile change in one unreviewed compatibility event.

DVault does not automatically migrate, backfill, dual-write, repair, reconcile, or rehash persisted keys.

- [hash-key-footprint.csv](../../artifacts/benchmarks/06FE4R1N2ADN77NDFDP4GR7020-provider-hash-key-matrix-20260621/hash-key-footprint.csv)
- [hash-key-footprint.json](../../artifacts/benchmarks/06FE4R1N2ADN77NDFDP4GR7020-provider-hash-key-matrix-20260621/hash-key-footprint.json)

The bundle ran one iteration and no warmup on Windows/.NET 10.0.9 with provider filter `all` and the variants `sha256-v1-hex`, `sha256-v1-binary`, `sha256-128-v1-hex`, and `sha256-128-v1-binary`. SQLite ran as the required local provider; PostgreSQL, MySQL, Oracle, and DB2 completed provider discovery; SQL Server was skipped because the local TLS/runtime setup could not open the configured connection.

Treat completed rows as measured only with the bundle and run context. Keep like-for-like algorithm comparisons separate from shortened-digest comparisons: `sha256-v1` hex versus `sha256-v1` binary compares storage profile only, while `sha256-v1` versus `sha256-128-v1` also changes digest length and collision tradeoffs. Treat PostgreSQL bytea/text operator failures, MySQL and DB2 truncation failures, Oracle reexecution failures, SQL Server skipped setup, diagnostics-only rows, and storage-footprint rows as caveats or follow-up evidence, not successful provider timing or automatic migration proof.

The footprint sidecar records the physical payload boundary for supported variants: `sha256-v1` `HexString` hash-key payloads at 64 bytes and two-column hash-reference index payloads at 128 bytes versus `Binary` at 32 and 64 bytes; `sha256-128-v1` `HexString` at 32 and 64 bytes versus `Binary` at 16 and 32 bytes. These are storage-footprint facts, not universal timing promises.

The refreshed after report ranks `DefaultDataVaultSaveService.AddSatellitesAsync`, then `FilterSatellitePlansAsync` and `LoadLatestSatelliteHashDiffsAsync`, then `DefaultStableHashNormalizer.NormalizeFields`, then `BuiltInStableHashService.ComputeHash`.

## Analyzer Guidance

The analyzer package remains project-local tooling. Use it only in projects that own DVault Code-First declarations, compile-time generated row mapping declarations, or support-bundle-driven typed satellite, PIT, and bridge read helpers. Keep the package reference local with `PrivateAssets="all"` and use the same selected package line as the runtime and provider packages.

The diagnostics stay bounded to source-visible evidence. `DMV1912` through `DMV1914` do not add runtime guards, provider-specific lifecycle guarantees, cross-assembly inference, or whole-application inference. Typed read-model generator diagnostics remain support-bundle-driven and do not parse raw `dvault.model.v1` additional files directly.

## Limitations And Non-Goals

v0.43.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.43.0 does not define a consumer-facing `0.43.0` package version. Consumers should use the target-specific `8.43.0` or `10.43.0` package line.

v0.43.0 does not change the public save/read API, public hash-key representation, stable hash default, provider dependency matrix, analyzer target-framework boundary, or provider strategy dispatch semantics.

v0.43.0 does not make binary hash-key storage automatic for existing persisted schemas. It does not perform automatic migration, rehashing, truncation, reset, backfill, dual-write, reconciliation, repair, or provider-specific remediation for failed binary rows.

v0.43.0 does not promote skipped, failed, diagnostics-only, smoke-only, or storage-footprint rows into successful provider timing claims. Future provider-specific binary-storage caveats or optimizations need their own diagnostics-selected behavior, migration guidance when applicable, and preserved benchmark evidence before documentation can promote them.
