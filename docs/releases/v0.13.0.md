# DVault v0.13.0 Release Notes

Release: `v0.13.0 - Code-First Parity Expansion`
Intended release date: 2026-05-18

## Package Scope

This is a coordinated release for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.13.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Expanded the fluent Code-First surface to cover repeated same-hub links through `DataVaultCodeFirstLinkBuilder.Participant<TEntity>(string role)`.
- Added Code-First link-parent satellites through `DataVaultCodeFirstLinkBuilder.Satellite<TSatellite>(...)` so link-attached descriptive state can be declared with the same payload and driving-key selector rules as hub-parent satellites.
- Kept repeated same-hub links explicit: callers must use an explicit relationship name and distinct non-blank roles for each repeated participant.
- Documented effectivity as a caller-owned link-parent satellite pattern instead of a separate effectivity-specific builder, entity family, metadata kind, or technical column set.
- Preserved metadata-first and model-first as authoritative alternatives for shared registries, reviewed artifacts, bridge/PIT declarations, custom naming, and ownership needs outside the bounded Code-First API.
- Refreshed README, quickstart, analyzer-package, production-adoption, model-first governance, and Code-First planning guidance for the `0.13.0` public baseline.

## Code-First Link Parity

Code-First links continue to support explicit relationship names and derived relationship names for ordinary non-repeated hub participant sets:

```csharp
modelBuilder.ApplyDataVaultMetadata(vault => {
  vault.Hub<Customer>(hub => hub.BusinessKey(customer => customer.CustomerId));
  vault.Hub<Order>(hub => hub.BusinessKey(order => order.OrderId));

  vault.Link("CustomerOrder", link => {
    link.Participant<Customer>();
    link.Participant<Order>();
  });
});
```

Repeated same-hub links require the explicit relationship-name overload and role-bearing participants. The roles become the produced participant names and generated hash-key column prefixes:

```csharp
modelBuilder.ApplyDataVaultMetadata(vault => {
  vault.Hub<Customer>(hub => hub.BusinessKey(customer => customer.CustomerId));

  vault.Link("CustomerIdentityMatch", link => {
    link.Participant<Customer>("SourceCustomer");
    link.Participant<Customer>("MatchedCustomer");
  });
});
```

The example above projects a `CustomerIdentityMatch` link with `SourceCustomerHashKey` and `MatchedCustomerHashKey` participant columns. Derived link names remain available for non-repeated participants, but a repeated same-hub link without an explicit relationship name is rejected so public names stay deterministic.

## Link-Parent Satellites And Effectivity

Code-First link-parent satellites are declared inside a link callback with `Satellite<TSatellite>(...)`:

```csharp
modelBuilder.ApplyDataVaultMetadata(vault => {
  vault.Hub<Customer>(hub => hub.BusinessKey(customer => customer.CustomerId));
  vault.Hub<Order>(hub => hub.BusinessKey(order => order.OrderId));

  vault.Link("CustomerOrder", link => {
    link.Participant<Customer>();
    link.Participant<Order>();
    link.Satellite<CustomerOrderState>("State", satellite => {
      satellite.DrivingKey(state => state.StateSource);
      satellite.Payload(state => state.StatusCode);
      satellite.Payload(state => state.StateChangedAt);
    });
  });
});
```

The produced satellite parent reference is `Link`/`CustomerOrder`. `Payload(...)` and optional `DrivingKey(...)` keep the existing direct scalar selector contract and preserve canonical declaration order. This is also the documented v0.13 effectivity path: model effectivity as descriptive state attached to the relationship link, then save and read it through the generic explicit metadata, registry, and latest/as-of satellite flows already used for other satellites.

v0.13 does not add an effectivity-specific fluent API, metadata kind, entity family, validation layer, or technical column family. Applications that need stricter effectivity conventions should keep those conventions in application-owned metadata, validation, or follow-on extension work.

## Compatibility Notes

- Existing Code-First, metadata-first, and model-first declaration paths remain additive alternatives for different ownership needs.
- Existing `DataVaultMetadataModel`, `DataVaultMetadataRegistry`, `IDataVaultSaveService`, typed latest/as-of read helpers, provider save strategies, diagnostics, and opt-in metadata interceptor behavior remain compatible.
- Code-First remains app-local EF model declaration. It does not create a public Code-First-to-registry bridge; callers that need one reusable metadata object for schema, save, read, diagnostics, and examples should continue using metadata-first or model-first registration.
- The explicit save boundary remains intact. DVault does not make Data Vault persistence implicit through ordinary EF entity tracking, and generated row creation still belongs to the caller or explicit save service flow.
- The analyzer package remains optional developer tooling and should usually be referenced with `PrivateAssets="all"`.

## Known Limitations

- Dependent child key modeling is deferred and is not part of the v0.13 public claim set.
- Repeated same-hub runtime and metadata support does not imply same-hub typed mapper or source-generator parity. The current typed link-mapper and generated mapper surfaces keep their existing unique-participant mapping boundary.
- Effectivity is documented as generic link-parent satellite usage, not as a first-class effectivity API.
- Runnable Code-First same-as or effectivity examples are not included in this release note; the checked-in quickstarts remain metadata-first.
- Link-parent satellites do not change PIT or bridge maintenance behavior. PIT-backed reads and bridge reads still operate over already materialized tables and do not maintain those tables.
- Startup-project and target-project splits for design-time discovery remain outside the documented v1 workflow.
- DVault does not provide a first-party `dotnet ef` command shim, EF CLI interception, automatic migration execution, or automatic schema repair.
