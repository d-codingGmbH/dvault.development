# DVault v0.51.0 Release Notes

Release: `v0.51.0 - Analyzer Host, Provider Parity, and Native Crypto Capabilities`
Release date: 2026-07-01

These notes record the coordinated v0.51.0 analyzer host support, provider optimization parity closure, provider-native crypto capability diagnostics, documentation, validation, package-verifier, and package-line baseline for DVault. The public release label maps to the consumer package versions `8.51.0` and `10.51.0`. There is no consumer-facing `0.51.0` package version.

## Package Lines

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.51.0` | `net8.0` | EF Core 8 |
| `10.51.0` | `net10.0` | EF Core 10 |

Use exactly one line in a consumer project. Do not mix `8.51.0` and `10.51.0` packages in one project, install example, restored target, or publish approval.

## Analyzer Compatibility Baseline

`DCoding.Data.DVault.Analyzers` remains a local build-time package reference with `PrivateAssets="all"`. The analyzer package now ships one `netstandard2.0` analyzer asset under `analyzers/dotnet/cs/` for both visible package lines, and supported analyzer consumption uses either a `.NET 8 SDK` or `.NET 10 SDK` build host.

v0.51.0 preserves one analyzer package id and one reviewed asset path while replacing the previous net10-only host boundary. Consumers can target `net8.0` with the `8.51.0` line and run the analyzer package on a `.NET 8 SDK` host, while the corresponding `.NET 10 SDK` host proof remains covered for the `10.51.0` line. Package verification and the dedicated analyzer package smoke lanes guard the packaged asset shape and both SDK-host paths.

## Provider Optimization Parity Closure

v0.51.0 closes the current provider optimization parity pass by aligning the source, tests, performance guidance, and evidence matrix around the completed provider-native save, latest-satellite read, PIT read, and bridge read rows for PostgreSQL, SQL Server, MySQL, Oracle, and DB2. The current performance reference remains the checked-in 2026-06-23 provider optimization closure bundle, plus the source and test-backed provider maintenance boundaries documented for later maintenance work.

The closure is intentionally bounded. It does not create absolute provider service-level objectives, automatic routing guarantees, provider-specific bridge maintenance, new automatic PIT maintenance lanes, database provisioning, deployable provider-specific SQL payload generation, or runtime artifact dispatch. Explicit fallback boundaries and unsupported shapes remain documented in [Performance Profiles](../performance-profiles.md) and the provider optimization evidence matrix.

## Provider-Native Crypto Capability Diagnostics

v0.51.0 extends the redaction-safe diagnostics surface with a finite reviewed provider-native crypto capability matrix and one provider-owned native selection path:

- `ProviderCryptoCapabilities` exposes guidance facts for SQLite encrypted-file builds, PostgreSQL deployment encryption and `pgcrypto`, SQL Server TDE and Always Encrypted, MySQL SQL crypto functions and file or tablespace encryption, Oracle TDE and `DBMS_CRYPTO`, and DB2 native database encryption.
- SQL Server `AddDVaultSqlServerAlwaysEncryptedSelection(...)` records an alias-driven Always Encrypted selection in `ProviderNativeCryptoSelections` when the caller supplies redaction-safe prerequisite proof names and the active SQL Server capability profile matches the reviewed conditional capability.
- The selection fails closed when prerequisite proof names are missing, reviewed capability facts are unavailable or unsupported, or the active capability profile is incompatible.

These facts are model and configuration evidence only. They do not replace caller-owned alias registration, `DataVaultEncryptedPayloadValueConverter`, custom conversion, or key-provider wiring. They do not emit provider-native encrypted DDL, call provider SQL crypto functions, probe database encryption capabilities, provision providers or key stores, migrate providers, re-encrypt values, backfill values, dual-write payloads, manage keys, shred data, delete rows, purge backups, rewrite historical satellite values, or provide a GDPR/DSGVO compliance attestation.

## Package Verification

`bash tools/pack-release-packages.sh` creates the coordinated package artifacts under `artifacts/packages/` for both visible package lines. `bash tools/verify-packages.sh` validates the expected package counts, package ids, versions, filenames, metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, DB2 dependency alignment, EF Core dependency lines, symbol packages, and stale package artifacts.

Package verification preserves stale-version guardrails for current-package guidance. Packaged README install guidance must not publish `0.51.0` from the release label, must not use stale `8.50.0` or `10.50.0` package lines, must not mix the `8.51.0` and `10.51.0` lines, and must retain the dual `.NET 8 SDK` / `.NET 10 SDK` analyzer build-host guidance plus the one `netstandard2.0` analyzer asset contract.

Package creation and verification do not imply signed NuGet publication or final publish approval.

## Validation

The release validation lane is:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/run-analyzer-package-smoke.sh 8
bash tools/run-analyzer-package-smoke.sh 10
bash tools/verify-packages.sh
bash tools/check-format.sh
```

The local validation baseline requires both .NET 8 and .NET 10 SDKs. Helper projects may stay on `net10.0`; the packaging lane proves the consumer `net8.0` and `net10.0` package outputs, and the analyzer smoke lanes prove packed analyzer consumption on both SDK hosts.

## Non-Goals

v0.51.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.51.0 does not define a consumer-facing `0.51.0` package version. Consumers should use the target-specific `8.51.0` or `10.51.0` package line.

v0.51.0 does not change package ids, dependency-major baselines, provider scope, manual-publication workflow, provider provisioning, analyzer compatibility beyond the `.NET 8 SDK` and `.NET 10 SDK` build-host boundary, automatic privacy execution, runtime provider-native encryption behavior, provider-native encrypted DDL, SQL crypto execution, key-store setup, automatic re-encryption, backfill, dual-write, provider migration, deletion, backup purge, crypto-shredding, automatic hash-key migration execution, dependent child key modeling, model-first same-hub typed mapper generation, effectivity-specific fluent APIs, implicit persistence, absolute provider performance guarantees, provider-specific bridge maintenance, or automatic PIT or bridge maintenance.
