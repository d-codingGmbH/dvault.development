# DVault v0.38.0 Release Notes

Release: `v0.38.0 - Binary-First New Project Profile`
Release date: 2026-06-15

These notes define the v0.38.0 coordinated package, documentation, and new-project hash-key storage baseline for the DVault package compatibility lines visible in the repository. They record the eight-package family, the supported consumer package-version lines, the accepted target-specific dependency matrix, the binary-first profile contract, diagnostics visibility, carried-forward validation evidence, and explicit non-goals. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Binary-First Profile

v0.38.0 adds an explicit named profile for new projects that should use binary physical hash-key storage from the start:

```csharp
services.AddDVault(options => options.UseBinaryFirstProfile());
```

For direct Code-First model projection, the matching model-builder API records the same named conventions profile before metadata is applied:

```csharp
modelBuilder.UseDataVaultBinaryFirstProfile();
```

The binary-first profile selects `DataVaultHashKeyStorageProfile.Binary` for generated hash-key columns and records the profile name `binary-first`. It preserves the active stable hash algorithm selection, including explicit calls such as `UseStableHashAlgorithm("sha1-v1")`, and keeps the public DVault hash-key value boundary as lowercase hexadecimal strings. It is not a public `byte[]` key model.

The compatible existing-project path remains unchanged:

- `AddDVault()` keeps `sha256-v1` and `HexString` unless the caller opts into another supported choice.
- `UseDataVault()` keeps the default compatible model conventions unless the caller opts into a profile or provider capability shape.
- Existing `HexString`-compatible databases and configurations remain valid until an application owner intentionally plans and executes a separate reviewed migration, reset, or data-move change.

## Diagnostics And Evidence

Diagnostics and support-bundle output report hash-key storage facts needed for support and drift review without exposing raw hash-key values, raw business keys, payload values, connection strings, provider SQL text, provider messages, or support-bundle payload text. The visible facts include:

- stable hash algorithm id
- digest byte length
- digest encoding
- hash-key storage profile
- provider store type
- provider value format
- conversion behavior

The model-cache key includes the selected stable hash algorithm id, digest byte length, hash-key storage profile, and conventions profile name so app-level default convention changes do not reuse an incompatible EF model.

The SQLite quickstart and PostgreSQL quickstart now demonstrate the binary-first new-project setup path. The benchmark evidence for the binary-first profile is recorded through the checked-in hash-key storage benchmark surfaces and carried forward from the v0.36.0 hash-key footprint baseline.

## Analyzer Compatibility

`DCoding.Data.DVault.Analyzers` remains one `net10.0` analyzer package asset for both coordinated consumer package lines. Analyzer references must stay local to the declaration-owning project with `PrivateAssets="all"`.

Supported analyzer consumption for both `8.38.0` and `10.38.0` uses a `.NET 10 SDK` build host. This includes `net8.0` consumer projects on the `8.38.0` package line. ## Carried-Forward Baselines

v0.38.0 moves the current documentation baseline forward for binary-first new-project setup while carrying forward the v0.37.0 dependency-line and analyzer compatibility baseline, the v0.36.0 binary hash-key storage adoption guidance, the v0.35.0 stable hash algorithm-selection baseline, the v0.34.0 DB2 provider package baseline, the v0.33.0 dual `net8.0` / `net10.0` compatibility contract, the v0.32.0 benchmark-driven provider threshold evidence and review-only SQL artifact manifest lane, the v0.31.0 performance decision-tree and observability baseline, the v0.30.0 typed helper support-bundle freshness baseline, the v0.29.0 provider schema guardrail baseline, the v0.28.0 provider read optimization evidence boundary, the v0.27.0 EF lifecycle analyzer guardrails, the v0.26.0 provider-tuning diagnostics and benchmark verifier evidence, the v0.25.0 ReadShape and typed helper boundary, the v0.24.0 async streaming and EF safety boundary, and the v0.21.0 PIT/bridge maintenance boundary.

The carried-forward hash-key storage baseline still keeps logical hash-key values as lowercase hexadecimal strings at public request, save, read, diagnostics, and support-bundle boundaries. `HexString` remains the default compatible physical storage profile, and `Binary` is the recommended explicit physical storage profile for new projects that can start with generated binary hash-key columns. Existing `HexString`-compatible databases and configurations remain valid until the application owner intentionally plans and executes a separate reviewed migration, reset, or data-move change. DVault does not automatically rehash, backfill, dual-write, repair, or migrate persisted hash-key storage when the storage profile or stable hash algorithm changes.

## Limitations And Non-Goals

v0.38.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, add release automation, or change the manual publication stop conditions.

v0.38.0 does not claim a consumer-facing `0.38.0` package version. It documents the repository-visible `8.38.0` and `10.38.0` consumer package lines.

v0.38.0 does not validate pure `.NET 8 SDK` analyzer consumption. If that becomes a product requirement, the analyzer asset target and verification lane must change explicitly.

v0.38.0 does not automatically convert existing `HexString` databases to binary storage, rehash persisted keys, backfill stored values, dual-write key storage, repair persisted-key drift, or provide migration tooling for profile changes.

v0.38.0 does not change the default stable hash algorithm, provider-side hashing behavior, DB2 live-schema support, provider provisioning, or external database test requirements.
