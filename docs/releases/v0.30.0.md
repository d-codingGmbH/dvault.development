# DVault v0.30.0 Release Notes

Release: `v0.30.0 - Typed Helper Freshness And Recovery`
Intended release date: 2026-06-05

These notes define the v0.30.0 coordinated documentation baseline for support-bundle freshness, stale typed read-model generator inputs, and request-bound `ReadShape` troubleshooting. They record the repository documentation boundary for refreshing authoritative `dvault.support-bundle.v1` inputs after metadata changes, updating or removing stale `DVaultTypedReadModelMetadataSourceFingerprint` values, and re-supplying representative PIT or bridge read diagnostics when helper generation lacks request-bound evidence. They do not record a NuGet push, package hashes, final publication links, release approval, benchmark reruns, support-bundle publication, runtime behavior changes, source-generator redesign, or package-publication automation by themselves. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Boundary Shift From v0.29.0

v0.29.0 moved the coordinated public baseline forward for provider identifier and DDL guardrails. That provider schema evidence boundary remains intact and historical.

v0.30.0 moves the current documentation baseline forward for typed helper support-bundle freshness and stale-input recovery. The typed read-model generator remains support-bundle-driven and opt-in through `DVaultGenerateTypedReadModels=true`. It still consumes exactly one authoritative `dvault.support-bundle.v1` additional file and still relies on request-bound `diagnostics.readShape.pit` or `diagnostics.readShape.bridge` facts for PIT and bridge helpers.

This release documents how adopters should refresh that input after Code-First metadata, metadata registry, reviewed `dvault.model.v1` artifact, provider profile, load-timestamp storage, or representative read request changes. It also documents how to interpret `DMV1960` and `DMV1961` as stale support-bundle or fingerprint recovery signals. It does not add raw model-file generator parsing, source-visible metadata inference, runtime reflection, dynamic query expansion, support-bundle routing, automatic request generation, or new generator diagnostics.

## Authoritative Support-Bundle Refresh

Typed helper generation starts from the same consumer-owned design-time workflow as validation and support-bundle export:

```sh
dotnet run --project <consumer-project> -- validate
dotnet run --project <consumer-project> -- support-bundle --output <path-to-reviewed-support-bundle.json>
```

After any metadata or request-shape change, adopters should treat the prior support bundle as stale until it has been regenerated from the configured design-time `DbContext` and reviewed. The refreshed project should expose exactly one reviewed `dvault.support-bundle.v1` file to the analyzer through `AdditionalFiles`. If the project pins `DVaultTypedReadModelMetadataSourceFingerprint`, the pin must be updated to the refreshed support bundle's `metadataSourceFingerprint` value or removed while the new bundle is under review.

`DMV1960` is the recovery signal for a support-bundle source boundary failure. It covers missing, invalid, incompatible-version, non-authoritative, or ambiguous support-bundle input, and raw or residual `dvault.model.v1` additional files that were not imported, projected, and re-exported as the authoritative support bundle.

`DMV1961` is the recovery signal for a stale fingerprint pin. It means the generator resolved a support bundle, but its metadata-source fingerprint does not match `DVaultTypedReadModelMetadataSourceFingerprint`.

## Request-Bound ReadShape Recovery

PIT and bridge helpers require request-bound support-bundle evidence because the generated helper must know the selected table identity, parent or endpoint vocabulary, projected columns, deterministic ordering, traversal-depth boundary, and snapshot-reference or endpoint column groups. The generic support-bundle command runner does not invent representative PIT or bridge requests.

When PIT or bridge helper generation reports stale or missing shape evidence, adopters should re-run the support-bundle export with application-supplied representative read diagnostics through `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics`:

```csharp
var readDiagnostics = services.GetRequiredService<IDataVaultReadDiagnosticsService>();

var host = new DataVaultDesignTimeCommandHost(
    diagnostics,
    () => new SalesVaultDesignTimeFactory().CreateDbContext(args),
    DataVaultDesignTimeExportSource.FromMetadataModel(SalesVaultMetadata.CreateModel()),
    ResolveMigrationOperations) {
  CreateSupportBundleDiagnostics = context => readDiagnostics.Analyze(
      context,
      SalesVaultRepresentativeRequests.CreateCustomerBridgeRead()),
};
```

Use a representative `DataVaultPitAsOfReadRequest` when validating a PIT helper and a representative `DataVaultBridgeReadRequest` when validating a bridge helper. Re-export the support bundle after changing the representative request factory, then rebuild the consuming project with the refreshed bundle. If the generator still reports `DMV1963`, `DMV1964`, `DMV1967`, or `DMV1969`, the selected PIT or bridge shape remains outside the bounded helper contract; unrelated supported helpers in the same valid support bundle can still generate.

## Adopter Recovery Checklist

1. Confirm the configured design-time model is the intended source by running `validate`.
2. Recreate any reviewed `dvault.model.v1` import or metadata registry projection before exporting the support bundle.
3. Supply representative PIT or bridge read diagnostics through `CreateSupportBundleDiagnostics` when helper generation needs `ReadShape` facts.
4. Re-export the support bundle from the consumer-owned project and review the refreshed `metadataSourceKind`, `metadataSourceFingerprint`, and `diagnostics.readShape` section.
5. Replace the analyzer `AdditionalFiles` input so exactly one reviewed support bundle is visible.
6. Update or remove `DVaultTypedReadModelMetadataSourceFingerprint`.
7. Rebuild and treat remaining `DMV1960` or `DMV1961` diagnostics as unresolved stale-input recovery work.

## Limitations And Non-Goals

v0.30.0 does not add provider support beyond SQLite, Oracle, PostgreSQL, SQL Server, and MySQL. It carries forward the provider schema guardrail baseline from v0.29.0 without changing provider package registrations or provider-specific safety claims.

v0.30.0 does not add a source-generator ability to parse raw `dvault.model.v1` files, inspect source-visible Code-First callbacks, infer helpers from literal metadata declarations, discover support bundles automatically, compile dynamic read requests, generate provider-specific SQL, emit unbounded hierarchy traversal helpers, maintain PIT or bridge rows, or schedule read-model refresh.

v0.30.0 does not publish, upload, attach, retain, route, or approve support-bundle JSON. Consumers remain responsible for artifact storage, review, transport, fingerprint pinning, and deciding which representative request-bound diagnostics belong in the authoritative support bundle.

Closure-stage relation housekeeping for any ticket that tracked this documentation work remains outside this repository release note. The repository baseline only records the documentation evidence.
