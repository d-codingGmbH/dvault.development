## Boundary Shift From v0.19.0

v0.19.0 introduced and documented the provider-neutral chunked explicit-save boundary. It deliberately kept provider-native chunk execution and staged provider bulk ingestion outside that release's public claim set.

v0.20.0 does not change the public write entry point. It documents the provider-specific optimized write-path boundary that repository evidence already exposes for materialized ordered saves. This is a forward-looking release boundary, not a retroactive rewrite of the v0.19.0 baseline.

## Write Path Hierarchy

`IDataVaultSaveService` remains the public write boundary. Single-request saves, ordered bulk saves, and bounded chunked saves continue to use explicit caller-supplied load timestamps, record sources, metadata resolution, hash-key and hash-diff behavior, caller-owned `DbContext` lifetime, caller-owned transaction behavior, and explicit cancellation flow.

Use this hierarchy in adopter guidance:

- `DataVaultSaveRequest` remains the focused single-save request.
- `DataVaultBulkSaveRequest` remains the compatibility baseline when the loader already has a complete ordered request set materialized.
- `DataVaultChunkedSaveRequest` remains the provider-neutral bounded streaming path for loaders that should not materialize the complete ordered set before saving.
- Provider-specific optimized strategies are diagnostics-gated implementations behind the same service contract. They are not a separate public persistence API.

`DataVaultChunkedSaveRequest` should not be presented as a blanket provider-optimized default. It is provider-neutral bounded chunking guidance. Provider-native chunk execution remains outside the v0.20.0 claim set unless a future release adds explicit provider evidence and behavior contracts.

## Provider-Specific Optimized Paths

PostgreSQL staged COPY is the preferred optimized path only for larger eligible PostgreSQL ordered batches where the repository exposes the staged boundary. Benchmark-facing documentation must preserve the retained direct or UNNEST path below the 60-operation staged threshold.

MySQL staged bulk is the preferred optimized path only for larger eligible MySQL ordered batches where the repository exposes the staged boundary. Benchmark-facing documentation must preserve the retained multi-row path above the 50-operation native gate and below the 60-operation staged threshold.

SQL Server remains documented as the current native-bulk optimized boundary. Do not invent a direct-versus-staged SQL Server split unless repository evidence later exposes and measures one.

Oracle remains documented as the retained direct optimized batching path. The current benchmark-facing boundary is `stagedOracleBulk=not-selected-no-measured-win`; do not describe staged Oracle bulk as selected until an artifact set proves a measured staged Oracle win over direct Oracle batching with deterministic cleanup under the caller-owned transaction boundary.

Unsupported shapes, dirty tracked contexts, provider-name mismatches, and batches outside provider gates can still decline to a smaller provider-native path or the provider-neutral writer. That fallback behavior is part of the compatibility story, not a failed public contract.

## Stored Procedure Boundary

Stored procedures are not the default DVault write recommendation and are not an automatically generated or automatically managed runtime path.

Treat stored procedures only as an explicit design-time or provider-specific escape hatch after the adopting application has documented:

- confirmed provider evidence for the specific procedure shape
- migration synchronization rules for creating, replacing, versioning, and dropping procedures
- deployment and rollback ownership
- transaction and cleanup behavior
- parity with explicit save ordering, hash-key, hash-diff, load timestamp, record source, and satellite latest-state semantics
- validation evidence that shows the procedure path is safer or faster for that provider and workload

The standard DVault guidance remains service-based explicit save through `IDataVaultSaveService`. A stored-procedure escape hatch must not be described as DVault auto-generating stored procedures, auto-managing database routines, or selecting procedures as a standard provider runtime path.

## Benchmark Evidence

Benchmark-facing v0.20.0 documentation reuses the existing root artifact triplet:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

The shared evidence contract remains [Performance Evidence And Benchmark Artifact Contract](../plans/performance-evidence-benchmark-artifact-contract.md). Do not introduce new artifact schemas or staged-bulk-specific filenames for this release boundary.

Provider-specific claims must keep provider, baseline, strategy family, execution status, skip reason, timing, allocation, execution detail, persisted outcome, and run context together. Skipped optional-provider rows remain meaningful evidence because they preserve the planned provider boundary and normalized skip reason instead of silently omitting unavailable external providers.

The provider-native bulk-ingestion matrix is the benchmark-facing source for staged, direct, and native-bulk wording:

- PostgreSQL evidence must preserve both the staged COPY row at the 60-operation threshold and the retained direct or UNNEST row below that threshold.
- MySQL evidence must preserve both the staged bulk row at the 60-operation threshold and the retained multi-row row above the 50-operation native gate and below the staged threshold.
- SQL Server evidence remains the current native-bulk row for its provider boundary.
- Oracle evidence remains the direct optimized row with `stagedOracleBulk=not-selected-no-measured-win` until a measured staged Oracle path is selected.

Stored procedures are outside the default benchmark matrix. If an application or future release wants stored-procedure guidance, that work needs its own provider evidence and migration-synchronization record before it can be treated as more than an escape hatch.

## Compatibility Notes

Existing callers of `IDataVaultSaveService.SaveAsync(DbContext, DataVaultSaveRequest, ...)`, `SaveAsync(DbContext, DataVaultBulkSaveRequest, ...)`, and `SaveAsync(DbContext, DataVaultChunkedSaveRequest, ...)` remain on the same public service boundary described by v0.19.0. v0.20.0 documentation does not require callers to change method calls or request types to receive provider-specific strategy dispatch where the provider package and diagnostics gates already support it.

Applications that already use `DataVaultBulkSaveRequest` for materialized ordered saves can keep that path. Applications that use `DataVaultChunkedSaveRequest` for bounded streaming should keep treating it as provider-neutral chunking unless a later release explicitly documents provider-native chunk execution.

## Validation Evidence

Repository validation should continue to use the standard local command baseline from the README:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/check-format.sh
```

External PostgreSQL, SQL Server, MySQL, and Oracle benchmark or integration evidence remains opt-in behind the documented connection-string environment variables. Release notes and copied benchmark tables must keep skipped optional-provider rows visible when those providers are not configured.

## Limitations

v0.20.0 documentation does not implement a new public save API, provider-native chunk execution, release automation, automatic stored-procedure generation, generic stored-procedure scaffolding, or migration helpers for database routines.

The staged-provider guidance is not universal. It applies only where repository evidence already exposes the provider-specific staged lane. SQL Server and Oracle should not inherit staged-bulk wording by analogy.

The benchmark artifact contract remains unchanged. Future work that changes artifact shape, adds stored-procedure evidence, or selects staged Oracle bulk should land under a separate contract update or provider-specific follow-up rather than widening this release note beyond its documented evidence boundary.
