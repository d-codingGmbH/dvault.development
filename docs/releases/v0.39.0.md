# DVault v0.39.0 Release Notes

Release: `v0.39.0 - Provider Evidence Matrix Documentation Baseline`
Release date: 2026-06-16

These notes define a docs-only v0.39.0 provider-evidence baseline for the DVault performance guidance visible in the repository. They record the provider optimization evidence matrix, the provider optimization gap matrix, the current benchmark caveats, and the follow-up posture for provider save and read work. They do not record a NuGet push, package hashes, final publication links, release approval, release automation, package-version movement, new benchmark execution, provider implementation work, diagnostics behavior changes, or expanded provider capability claims.

This release record covers documentation alignment only:

- [Performance Profiles](../performance-profiles.md)

The existing package compatibility, publication checklist, README installation guidance, pack script, and package verification surfaces remain on the repository-visible package baseline that predates this docs-only note. This release note is not evidence of a new consumer package-version line.

## Provider Evidence Baseline

[Provider Optimization Evidence Matrix](../plans/provider-optimization-evidence-matrix.md) is the canonical row lookup surface for provider evidence. Documentation and follow-up tickets should cite matrix rows by:

- `scenario`
- `provider`
- `baseline`
- `posture`

The supported evidence postures remain:

| Posture | Release-note meaning |
| --- | --- |
| `completed-timing` | A checked-in benchmark row completed and may support a timing claim only with its artifact triplet and run context. |
| `skipped-placeholder` | A checked-in optional-provider row preserves row identity, planned strategy facts, skip reason, and `persistedOutcome=not executed`; it is not timing evidence. |
| `diagnostics-only` | Diagnostics, provider registrations, capability profiles, or fallback vocabularies prove a bounded strategy candidate or fallback condition without benchmark timing. |
| `smoke-only` | Opt-in live or smoke coverage proves representative execution behavior when configured without becoming a measured benchmark lane. |
| `storage-footprint` | SQLite-local hash-key storage sidecars record physical storage facts and scoped benchmark rows for hash-key variants; they are not cross-provider timing claims. |

## Checked-In Benchmark Caveats

The root benchmark artifact triplet remains the quick local SQLite and skipped-provider baseline:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

That checked-in run recorded completed SQLite local temporary-file timing rows and kept PostgreSQL, SQL Server, MySQL, Oracle, and DB2 optional-provider rows visible as skipped placeholders because the corresponding connection-string environment variables were unset. Those skipped rows preserve row identity, planned execution details, skip reasons, and fallback posture; they do not prove completed timing for those external providers.

Completed external-provider timing claims must cite the provider-threshold bundles linked from [Performance Profiles](../performance-profiles.md), including the preserved run context, provider configuration, iteration count, warmup count, dataset shape, and skipped or failed rows where applicable.

## Follow-Up Recommendation Posture

[Provider Optimization Gap Matrix](../plans/provider-optimization-gap-matrix.md) is the canonical follow-up recommendation surface. Its backlog rows are planning recommendations, not measured evidence:

- P0 rows are non-SQLite `latest-satellite-read` capability gaps. SQLite remains the only repository-proven optimized latest-satellite provider path in the current baseline.
- P1 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `provider-native-bulk-ingestion` evidence gaps until provider-configured benchmark triplets complete.
- P2 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `pit-as-of-read` evidence gaps until provider-configured benchmark triplets complete.
- P3 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `bridge-traversal-read` evidence gaps until provider-configured benchmark triplets complete.

The gap matrix may be used to prioritize future capability or evidence work, but it does not promote skipped placeholders, diagnostics-only rows, smoke-only rows, or storage-footprint rows into completed provider timing evidence.

## Provider Boundaries

Provider save claims stay bounded by request-bound diagnostics, provider registration, provider gates, and preserved benchmark artifacts. PostgreSQL staged COPY, SQL Server native bulk, MySQL retained or staged bulk, and Oracle direct optimized batching should be cited only with the evidence bundle that proves the claimed row and run context. The root quick baseline alone is not completed timing evidence for those external-provider rows when the row is skipped.

Provider read claims stay bounded by `IDataVaultReadService`, request-bound read-shape diagnostics, explicit PIT or bridge maintenance, and provider diagnostics. Non-SQLite latest-satellite reads remain provider-neutral fallback unless a later ticket adds diagnostics-selected strategy evidence and benchmark-backed timing. PostgreSQL, SQL Server, MySQL, Oracle, and DB2 PIT/bridge paths remain diagnostics-gated candidates when their rows are skipped in the root triplet.

DB2 keeps the narrower current posture: clean-context save and PIT/bridge candidate behavior may be cited from diagnostics and opt-in smoke evidence where applicable. Completed DB2 timing, DB2 latest-satellite optimization, staged DB2 bulk, provider-native chunk execution, and DB2 live-schema reading are not part of this release baseline.

## Limitations And Non-Goals

v0.39.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, add release automation, change package compatibility surfaces, or define a new consumer package-version line.

v0.39.0 does not rerun benchmarks, generate new benchmark artifact triplets, change benchmark schemas, add provider implementations, add provider-specific latest-satellite strategies, or widen provider timing claims beyond checked-in completed evidence.

v0.39.0 does not expand DB2 beyond the current diagnostics and smoke posture. It does not claim completed DB2 timing, DB2 latest-satellite optimization, staged DB2 bulk, provider-native chunk execution, or DB2 live-schema reading.

v0.39.0 does not turn gap-matrix recommendations into release promises. Future provider work must add its own diagnostics-selected behavior and preserved benchmark evidence before documentation can promote a row from follow-up recommendation to completed timing claim.
