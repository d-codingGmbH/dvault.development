# DVault v0.39.0 Release Notes

Release: `v0.39.0 - Provider Evidence Matrix Documentation Baseline`
Release date: 2026-06-16

These notes define the coordinated v0.39.0 package and documentation baseline for DVault. The public release label maps to the consumer package versions `8.39.0` and `10.39.0`, while the provider evidence documentation records the current matrix baseline, benchmark caveats, and follow-up posture for provider save and read work.

This release note does not record a NuGet push, package hashes, final publication links, release approval, release automation, new benchmark execution, provider implementation work, diagnostics behavior changes, or expanded provider capability claims.

## Checked-In Benchmark Caveats

The root benchmark artifact triplet remains the quick local SQLite and skipped-provider baseline:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

That checked-in run recorded completed SQLite local temporary-file timing rows and kept PostgreSQL, SQL Server, MySQL, Oracle, and DB2 optional-provider rows visible as skipped placeholders because the corresponding connection-string environment variables were unset. Those skipped rows preserve row identity, planned execution details, skip reasons, and fallback posture; they do not prove completed timing for those external providers.

Completed external-provider timing claims must cite the provider-threshold bundles linked from [Performance Profiles](../performance-profiles.md), including the preserved run context, provider configuration, iteration count, warmup count, dataset shape, and skipped or failed rows where applicable.

## Follow-Up Recommendation Posture

[Provider Optimization Gap Matrix](../plans/provider-optimization-gap-matrix.md) is the canonical follow-up recommendation surface. Its backlog rows are planning recommendations, not measured evidence:

- P0 rows are latest-satellite follow-ups. PostgreSQL, MySQL, and DB2 remain capability gaps, while SQL Server and Oracle are skipped-placeholder evidence gaps until configured benchmark triplets exist. SQLite remains the only completed optimized latest-satellite timing row in the current baseline.
- P1 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `provider-native-bulk-ingestion` evidence gaps until provider-configured benchmark triplets complete.
- P2 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `pit-as-of-read` evidence gaps until provider-configured benchmark triplets complete.
- P3 rows are PostgreSQL, SQL Server, MySQL, Oracle, and DB2 `bridge-traversal-read` evidence gaps until provider-configured benchmark triplets complete.

The gap matrix may be used to prioritize future capability or evidence work, but it does not promote skipped placeholders, diagnostics-only rows, smoke-only rows, or storage-footprint rows into completed provider timing evidence.

## Provider Boundaries

Provider save claims stay bounded by request-bound diagnostics, provider registration, provider gates, and preserved benchmark artifacts. PostgreSQL staged COPY, SQL Server native bulk, MySQL retained or staged bulk, and Oracle direct optimized batching should be cited only with the evidence bundle that proves the claimed row and run context. The root quick baseline alone is not completed timing evidence for those external-provider rows when the row is skipped.

Provider read claims stay bounded by `IDataVaultReadService`, request-bound read-shape diagnostics, explicit PIT or bridge maintenance, and provider diagnostics. PostgreSQL, MySQL, and DB2 latest-satellite reads remain provider-neutral fallback unless a later ticket adds diagnostics-selected strategy evidence and benchmark-backed timing. SQL Server and Oracle latest-satellite rows plus PostgreSQL, SQL Server, MySQL, Oracle, and DB2 PIT/bridge paths remain diagnostics-gated candidates when their rows are skipped in the root triplet.

At the v0.39.0 baseline, DB2 kept the narrower posture: clean-context save and PIT/bridge candidate behavior could be cited from diagnostics and opt-in smoke evidence where applicable. Completed DB2 timing, DB2 latest-satellite optimization, staged DB2 bulk, provider-native chunk execution, and DB2 live-schema reading were not part of that release baseline.

## Validation Evidence

Repository release validation should include:

- `dotnet build DVault.slnx --nologo`
- `dotnet test DVault.slnx --nologo`
- `bash tools/pack-release-packages.sh`
- `bash tools/verify-packages.sh`
- `bash tools/check-format.sh`

The package validation checks the expected `8.39.0` and `10.39.0` artifact set, package metadata, dependency groups, analyzer asset placement, XML documentation, symbols packages, README installation guidance, and stale-version guardrails. Package creation and verification do not imply signed NuGet publication.

No provider benchmarks were rerun for this release note, and no benchmark schemas were changed. The checked-in benchmark and provider-threshold artifact bundles remain the evidence boundary for any timing claim.

## Limitations And Non-Goals

v0.39.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.39.0 does not define a consumer-facing `0.39.0` package version. Consumers should use the target-specific `8.39.0` or `10.39.0` package line.

v0.39.0 does not rerun benchmarks, generate new benchmark artifact triplets, change benchmark schemas, add provider implementations, add provider-specific latest-satellite strategies, or widen provider timing claims beyond checked-in completed evidence.

v0.39.0 did not expand DB2 beyond the diagnostics and smoke posture available at that release. It did not claim completed DB2 timing, DB2 latest-satellite optimization, staged DB2 bulk, provider-native chunk execution, or DB2 live-schema reading.

v0.39.0 does not turn gap-matrix recommendations into release promises. Future provider work must add its own diagnostics-selected behavior and preserved benchmark evidence before documentation can promote a row from follow-up recommendation to completed timing claim.
