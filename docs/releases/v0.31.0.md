# DVault v0.31.0 Release Notes

Release: `v0.31.0 - Performance Guidance, Observability Examples, And Quickstart Evidence`
Intended release date: 2026-06-06

These notes define the v0.31.0 coordinated release baseline for the performance decision-tree guidance, application-owned observability posture, and realistic customer-profile quickstart evidence already landed in the repository. They record documentation and example evidence for choosing DVault save/read paths, preserving benchmark context, using bounded diagnostics, and keeping telemetry and tracing opt-in. They do not record a NuGet push, package hashes, final publication links, release approval, benchmark reruns, runtime behavior changes, dashboards, exporters, collectors, hosting, ingestion orchestration, automatic PIT or bridge maintenance, provider-specific SQL artifact generation, or package-publication automation by themselves. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Boundary Shift From v0.30.0

v0.30.0 moved the coordinated public baseline forward for support-bundle freshness, stale typed read-model generator inputs, and request-bound `ReadShape` troubleshooting. That support-bundle and generator-input recovery boundary remains intact and historical.

v0.31.0 moves the current documentation baseline forward for adopter performance decisions and example evidence. The detailed decision tree now starts from explicit DVault service boundaries, checked-in benchmark evidence, request-bound diagnostics, opt-in telemetry, listener-driven tracing, and caller-owned PIT or bridge maintenance. The baseline also records a compact customer-profile quickstart scenario that exercises explicit saves, typed latest/as-of reads, and bounded diagnostics without exposing raw values.

This release does not add automatic runtime routing, raw SQL inspection, provider physical-plan promises, provider service-level objectives, background ingestion, scheduler templates, dashboard or exporter setup, database provisioning, automatic PIT or bridge refresh, source-generator expansion, or provider-specific SQL artifact workflow.

## Performance Guidance Baseline

[Performance Profiles](../performance-profiles.md) is the authoritative v0.31.0 performance decision-tree contract. It keeps the four existing profile families visible while making the choice order explicit:

- small app-local vault work starts with `AddDVault()` and request-bound save/read diagnostics;
- medium chunked ingestion uses bounded `DataVaultChunkedSaveRequest` or async chunk-source inputs only when the caller already owns ordered chunks;
- staged provider ingestion remains diagnostics-gated behind `IDataVaultSaveService` and the matching provider extension; and
- read-model-heavy workloads keep PIT and bridge rows as caller-maintained read models consumed by `IDataVaultReadService`.

The evidence baseline remains the root benchmark artifact triplet:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

The current checked-in run preserves 3 iterations, 1 warmup iteration, `ProviderDefault` load timestamp storage, provider filter `all`, Debian GNU/Linux 13 x64, .NET 10.0.8, required SQLite local temporary files, and skipped optional PostgreSQL, SQL Server, MySQL, and Oracle rows when their connection-string environment variables are unset. Timing values stay observations from that run only, and adopters should rerun the benchmark triplet whenever provider, hardware, runtime, load-timestamp storage, iteration count, warmup count, dataset size, request shape, or provider configuration changes.

## Observability Baseline

The v0.31.0 observability posture is application-owned. `AddDVault()` remains telemetry-free by default. Built-in save/read metrics require explicit `AddDVaultTelemetry()` registration, custom `IDataVaultTelemetryObserver` implementations remain optional sibling surfaces, and Activity tracing is listener-driven through the `DCoding.Data.DVault` ActivitySource.

Authoritative observability and diagnostics boundaries are:

- [README observability guidance](../../README.md#observe-explicit-save-and-read-attempts)
- [DVault V1 Activity Tracing Contract](../architecture/dvault-v1-activity-tracing-contract.md)
- [DVault V2 Redacted Read-Plan Explain Contract](../architecture/dvault-v2-redacted-read-plan-explain-contract.md)
- [DVault Quickstart Examples](../../examples/README.md#observability-examples)

Those surfaces keep exporters, collectors, dashboards, alerting, hosting, sampling policy, telemetry backends, and deployment instructions application-owned. They also keep diagnostics and tracing redacted: no raw business keys, hash keys, payload values, record sources, SQL text, query plans, connection strings, credentials, provider messages, exception text, stack traces, support-bundle content, exporter endpoints, or deployment-specific diagnostics are emitted as release-note evidence.

## Quickstart Evidence

[DVault Quickstart Examples](../../examples/README.md) and [QuickstartHistoryFlow.cs](../../examples/DCoding.Data.DVault.Quickstarts.Shared/QuickstartHistoryFlow.cs) now provide the release-level example evidence for the realistic customer-profile flow:

- one `Customer` hub identified by a synthetic customer business key;
- one `CustomerProfile` satellite with `Profile Name` and `Customer Status` payload fields;
- an initial CRM import at `2026-04-29T10:15:00Z` with record source `crm-import`;
- a later CRM change at `2026-04-29T11:30:00Z` with record source `crm-change`;
- explicit hub and satellite writes through `IDataVaultSaveService`;
- typed latest and as-of reads through `IDataVaultReadService`; and
- bounded save/read diagnostics reporting strategy status, selected strategy presence, fallback presence, and latest/as-of read-shape category.

The quickstarts intentionally keep output sanitized. They summarize projected payload-field presence, load timestamps, row counts, strategy status, selected strategy name when available, fallback presence, and read-shape category. They do not copy raw console values into this release note and do not print raw SQL, connection strings, business keys, hash keys, payload values, provider message text, exception text, support-bundle content, exporter endpoints, or deployment instructions.

## Limitations And Non-Goals

v0.31.0 does not add provider support beyond SQLite, Oracle, PostgreSQL, SQL Server, and MySQL. It carries forward the provider schema guardrail baseline from v0.29.0, the provider read optimization evidence boundary from v0.28.0, the EF lifecycle analyzer guardrails from v0.27.0, and the support-bundle generator-input recovery boundary from v0.30.0 without changing provider package registrations or provider-specific safety claims.

v0.31.0 does not add dashboards, exporters, collectors, hosting, OpenTelemetry package requirements, alert rules, backend-specific observability pipelines, custom trace identifiers, custom baggage, raw diagnostics transport, support-bundle publication, package publication, or release automation.

v0.31.0 does not add automatic PIT or bridge maintenance, automatic read-model refresh, ingestion orchestration, background workers, CDC ingestion, scheduler behavior, EF `SaveChanges` interception as the default persistence path, provider-specific physical tuning, provider physical-plan promises, raw SQL visibility, provider-specific SQL artifact generation, stored-procedure invocation, or runtime artifact dispatch.

The provider-specific SQL artifact lane remains future v0.32 scope only. This release keeps it as a forward non-goal boundary and does not specify, implement, publish, deploy, invoke, synchronize, or validate that workflow.
