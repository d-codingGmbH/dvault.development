## Boundary Shift From v0.24.0

v0.24.0 moved the public documentation baseline forward for async chunk-source saves and EF safety guidance. That boundary remains intact and historical.

v0.25.0 moved the coordinated public baseline forward for request-bound read-plan diagnostics and support-bundle-driven typed read helpers. For this release, read plan means `IDataVaultReadDiagnosticsService.Analyze(...)` output on `DataVaultDiagnosticsResult`: the provider strategy facts in `ReadStrategy` plus additive translated read facts in `ReadShape`. The same redacted `ReadShape` data appears as camelCase `readShape` JSON in `dvault.support-bundle.v1` when the consumer application supplies representative request-bound diagnostics through `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics`.

The typed read-model generator remains opt-in with `DVaultGenerateTypedReadModels=true` and exactly one authoritative `dvault.support-bundle.v1` additional file. It now documents the implemented helper baseline for satellite latest/current/as-of helpers, PIT `Read...AsOfAsync` helpers, many-to-many bridge `Read...FromAsync` and `Read...ToAsync` helpers, and hierarchy bridge `Read...AncestorAsync` and `Read...DescendantAsync` helpers with required `maximumDepth`.

This release note does not record package publication claims, release automation, benchmark reruns, provider-specific SQL, raw query-plan capture, automatic index advice, automatic PIT or bridge maintenance, support-bundle transport automation, or consumer sample-app expansion.

## Read-Plan And ReadShape Diagnostics

`IDataVaultReadDiagnosticsService.Analyze(...)` is the bounded read-plan explain surface. Request-bound diagnostics expose:

- `DataVaultDiagnosticsResult.ReadStrategy` for provider strategy status, selected strategy name when one is selected, provider names, finite fallback causes, and candidate facts.
- `DataVaultDiagnosticsResult.ReadShape` for translated read-shape identity, provider caveats, table and column facts, deterministic selection and ordering rules, projected column groups, expected key/index baselines, and fallback caveats.

The read-shape kind vocabulary is closed to `LatestSatellite`, `PitAsOf`, and `Bridge`. Read-strategy statuses are `NotEvaluated`, `ProviderStrategySelected`, and `ProviderNeutralFallback`. Fallback causes remain finite `DataVaultReadStrategyFallbackCauseKind` enum values.

ReadShape output is value-free diagnostics. It may include metadata names, generated table names, generated column names, enum values, provider names, provider profile names, selected strategy names, status values, and finite fallback causes. It must not include raw request keys, raw business keys, raw hash-key values, raw as-of or load-timestamp request values, payload values, record-source values, SQL text, provider query plans, credentials, connection strings, provider error text, exception text, stack traces, or secret-bearing dumps.

Support-bundle export serializes the same bounded data under `diagnostics.readShape` when application code supplies representative request-bound diagnostics. The generic design-time command runner does not invent read requests; applications that need helper-generation evidence or troubleshooting examples must provide representative diagnostics through `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics`.

## Typed Read Helper Baseline

Generated helpers are compile-time ergonomics over `IDataVaultReadService`. They construct stable metadata/read request values from reviewed support-bundle evidence and project rows returned by the existing runtime read boundary. They are not a new query API and do not widen runtime read semantics.

Supported satellite helpers cover:

- hub-parent satellites.
- link-parent satellites.
- deterministic multi-active satellites whose driving keys and payload values are strings after projection.
- `Read...CurrentAsync`, `Read...LatestAsync`, and `Read...AsOfAsync` methods.

Supported PIT helpers cover:

- hub-parent ordinary PITs.
- hub-parent multi-active PITs when every referenced multi-active satellite shares one canonical driving-key name/order family.
- bounded link-parent PITs when every referenced satellite is unique, non-multi-active, and attached to the same declared link parent.
- one `Read...AsOfAsync` method that delegates through `ReadPitRowsAsync`.

Generated PIT read models project maintained PIT-table columns only: `ParentHashKey`, `LoadTimestamp`, canonical PIT driving keys when the read shape proves them, and nullable snapshot-reference timestamps for included PIT segments. PIT helpers do not project satellite payload, rebuild PIT rows, perform parent maintenance, fall back to latest satellite reads, or add provider-specific query behavior.

Supported bridge helpers cover:

- many-to-many bridge traversal through `Read...FromAsync` and `Read...ToAsync`.
- hierarchy bridge traversal through `Read...AncestorAsync` and `Read...DescendantAsync`.
- required `maximumDepth` on hierarchy helpers.

Generated bridge read models project bridge-row endpoint hash-key columns and `TraversalDepth` for hierarchy bridges. Bridge helpers do not emit unbounded traversal overloads, graph/path APIs, path payload contracts, closure-state contracts, delete-aware maintenance behavior, or provider-specific traversal semantics.

## Helper Examples

```csharp
using ConsumerApp.DVault.GeneratedReadModels;

var snapshots = await readService.ReadPitCustomerProfileAsOfAsync(
    context,
    customerHashKeys,
    asOfTimestamp,
    cancellationToken);

var customerOrders = await readService.ReadBridgeCustomerOrderFromAsync(
    context,
    customerHashKeys,
    cancellationToken);

var descendants = await readService.ReadBridgeSalesRegionHierarchyDescendantAsync(
    context,
    regionHashKeys,
    maximumDepth: 3,
    cancellationToken);
```

Use generated helpers when the reviewed support bundle proves stable, shared, compile-time-friendly read shapes. Use dynamic `IDataVaultReadService` requests for runtime-built shapes, caller-selected projectors, or PIT/bridge shapes that stay outside the generated-helper contract. Use consumer-owned EF compiled queries for stable direct EF shared-type-table expressions with generated names, scalar parameters, `EF.Property<T>(...)`, and deterministic projections, as documented in [DVault EF Compiled Compatibility](../architecture/dvault-ef-compiled-compatibility.md).

## Typed Read-Model Diagnostics

The typed read-model generator diagnostic range remains `DMV1960` through `DMV1969`:

- `DMV1960` for missing, invalid, non-authoritative, or ambiguous `dvault.support-bundle.v1` metadata source input.
- `DMV1961` for `DVaultTypedReadModelMetadataSourceFingerprint` drift.
- `DMV1962` for unsupported satellite shapes, including non-string projected members and reserved projection-name collisions.
- `DMV1963` for PIT metadata or request-bound PIT read-shape evidence that is incomplete or outside the bounded generated-helper baseline.
- `DMV1964` for bridge metadata or request-bound bridge read-shape evidence that is incomplete or outside the bounded generated-helper baseline.
- `DMV1965` for deterministic generated type, method, property, or helper name collisions.
- `DMV1966` for payload nullability fallback when support-bundle facts cannot prove nullability.
- `DMV1967` for shapes that require dynamic runtime query construction, provider SQL, runtime projection selection, payload joins, tuple expansion, or unbounded traversal.
- `DMV1968` for raw or residual model-first source evidence that remains outside the projected support-bundle helper contract. Complete model-first support bundles with request-bound `ReadShape` evidence can still emit supported helpers.
- `DMV1969` for valid runtime metadata shapes intentionally skipped because they remain outside the v1 generated-helper boundary.

Diagnostics skip only the affected helper when possible. Supported satellite, PIT, or bridge helpers in the same support bundle can still generate when their own evidence is valid.

## Compatibility Notes

Existing explicit save and read service boundaries remain compatible. `IDataVaultReadService` remains the runtime read boundary for latest/as-of satellite reads, PIT reads, and bridge reads. Generated helpers delegate through that service rather than replacing it.

Dynamic `IDataVaultReadService` requests remain the documented default when read shapes are constructed at runtime, when callers need dynamic projector selection, or when support-bundle evidence is not the reviewed source for a generated helper. Consumer-owned EF compiled queries remain appropriate only for stable direct EF shared-type-table expressions and do not become a DVault-generated query surface.

The existing consumer-owned `guardrail --migration` lane now treats destructive drops of DVault-produced tables, generated columns, generated secondary indexes, and named generated primary-key constraints as blocking migration diagnostics. Explicit EF rename operations remain visible risky operations, and drop-plus-add replacements that look like generated-name or metadata drift are reported separately as suspicious risky diagnostics.

PIT and bridge maintenance remain explicit caller-owned service boundaries. `IDataVaultPitMaintenanceService` and `IDataVaultBridgeMaintenanceService` do not add automatic scheduling, read-time refresh, delete-aware incremental bridge shrinkage, or provider-specific maintenance strategies. SQLite remains the only repository-proven optimized PIT and bridge read provider path; unsupported providers and unsupported shapes fall back to provider-neutral read pipelines.

Raw `dvault.model.v1` artifacts remain reviewed workflow inputs, not direct typed-helper generator inputs. Support-bundle storage, attachment, retention, transport, and approval workflows remain consumer-owned.

Activity tracing, telemetry, stable hash governance, async source saves, EF safety guidance, provider package responsibilities, public API snapshot posture, and manual package publication separation carry forward from prior release notes.
