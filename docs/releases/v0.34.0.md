# DVault v0.34.0 Release Notes

Release: `v0.34.0 - DB2 Provider Support`
Intended release date: 2026-06-10

These notes define the v0.34.0 coordinated documentation baseline for the DVault package compatibility lines visible in the repository. They record the eight-package family, the DB2 provider package baseline, the supported consumer package-version lines, the finite .NET and EF Core provider matrix, the manual publication boundary, package-tested and local validation evidence, opt-in external-provider evidence, compatibility caveats, and explicit non-goals. They do not record a NuGet push, package hashes, final publication links, release approval, DB2 database provisioning, release automation, or a new default requirement for live external databases. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Package Scope

This is a coordinated release record for the eight-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.Db2`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

The `src/DCoding.Data` project remains a non-packable source-root build anchor for the namespace family and is not a NuGet publication artifact.

The planning release label `v0.34.0` is not a consumer-facing NuGet package version. Consumers choose exactly one aligned package-version line per project:

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.34.0` | `net8.0` | EF Core 8 |
| `10.34.0` | `net10.0` | EF Core 10 |

Do not publish or document a consumer-facing `0.34.0` package version. Do not combine `8.34.0` and `10.34.0` packages in one consumer project, one install example, one restored target, or one publish approval.

## DB2 Provider Baseline

The DB2 provider package id is `DCoding.Data.DVault.Db2`. The package targets `net8.0;net10.0` and depends on IBM's EF Core provider line for the selected target framework:

| Target framework | DVault package version | IBM EF Core provider |
| --- | --- | --- |
| `net8.0` | `8.34.0` | `IBM.EntityFrameworkCore` `8.0.0.400` |
| `net10.0` | `10.34.0` | `IBM.EntityFrameworkCore` `10.0.0.100` |

`AddDVaultDb2()` registers DVault defaults, DB2 provider behavior for `IBM.EntityFrameworkCore`, the `db2-v1` provider capability profile, an optimized clean-context save strategy for ordinary hub, link, and satellite rows, and diagnostics-gated PIT/bridge read dispatch. The DB2 profile uses the provider-neutral DVault metadata surface with DB2-specific projection facts, including a 128-character identifier limit, ISO 8601 UTC text timestamp storage by default, `CLOB` payload text, and appended-key handling for included-index columns that DB2 cannot represent as included columns.

DB2 execution support in this baseline remains scoped to the DVault service boundaries. Repository evidence covers representative hub, link, and satellite saves through `Db2DataVaultSaveStrategy`, latest/as-of satellite reads through the provider-neutral latest pipeline, and PIT/bridge reads through `Db2DataVaultReadStrategy` after `AddDVaultDb2()` registration. DB2 does not register a provider-native latest-satellite read strategy, staged bulk path, provider-native chunk execution, provider-specific PIT/bridge maintenance strategy, or built-in live-schema reader in this release.

## Consumer Guidance

Use the [README installation guidance](../../README.md#installation) for consumer setup. For `net8.0` projects on EF Core 8, install the `8.34.0` DVault runtime, provider, and analyzer package line. For `net10.0` projects on EF Core 10, install the `10.34.0` line. Keep `DCoding.Data.DVault.Analyzers` local to the project that owns DVault declarations or generated read helpers with `PrivateAssets="all"`.

Consumers still install and configure the normal Entity Framework Core database provider package used by the application. DB2 consumers install `IBM.EntityFrameworkCore` for the selected target framework and use normal EF Core DB2 configuration such as `UseDb2(...)` or `UseDB2(...)` as exposed by that provider. DVault provider packages register DVault-specific provider behavior; they do not replace the application-owned EF provider selection, connection strings, migrations, credentials, schema lifecycle, or deployment operations.

## External DB2 Test Boundary

DB2 tests are opt-in external-provider evidence. Default repository build and test execution does not require DB2, Docker, Podman, a DB2 connection string, or checked-in machine-specific configuration.

The live DB2 lane is selected with `Category=ProviderIntegration.ExternalOptIn&Provider=DB2` and the developer-supplied connection string environment variable:

```sh
DVAULT_TEST_DB2_CONNECTION_STRING='Server=localhost:50000;Database=dvault;UID=dvault;PWD=local-secret' dotnet test DVault.slnx --nologo --filter "Category=ProviderIntegration.ExternalOptIn&Provider=DB2" -p:DVAULT_TEST_DB2_CONNECTION_STRING=Configured
```

The non-secret MSBuild property marker keeps conditional package restore and project references available for the live DB2 run. The secret value remains in the environment variable. A developer-managed DB2 database may be hosted directly or in a local Podman/Docker container, but provisioning, license acceptance, user creation, database creation, credentials, lifecycle cleanup, and CI isolation remain outside DVault.

## External DB2 Benchmark Boundary

DB2 benchmark rows are also opt-in external-provider evidence. The benchmark project conditionally restores `IBM.EntityFrameworkCore` and references `DCoding.Data.DVault.Db2` when `DVAULT_TEST_DB2_CONNECTION_STRING` is supplied, then reuses the existing root artifact triplet and optional-provider matrix.

```sh
DVAULT_TEST_DB2_CONNECTION_STRING='Server=localhost:50000;Database=dvault;UID=dvault;PWD=local-secret' dotnet run --project benchmarks/DCoding.Data.DVault.Benchmarks/DCoding.Data.DVault.Benchmarks.csproj --configuration Release -- --provider db2 --iterations 1 --warmup 0 --output artifacts/benchmarks/db2
```

The DB2 lane records the bounded behavior already supported by the provider package: a provider-neutral fallback comparison row, a DB2 optimized clean-context save row, and DB2 read guidance rows for latest satellite, PIT as-of, and bridge traversal. Latest-satellite remains provider-neutral with `selectedStrategy=<none>`; PIT and bridge rows name `Db2DataVaultReadStrategy`. If DB2 is not configured or cannot be reached, the rows remain visible as skipped placeholders with `iterations=0`, blank/null metrics, normalized skip reasons, and `persistedOutcome=not executed`. The benchmark lane does not provision DB2, create checked-in credentials, add staged DB2 bulk dispatch, add provider-native chunk execution, or create a separate DB2 artifact schema.

## Manual Publication Boundary

Publication remains manual and separate from this documentation baseline. The [Manual NuGet Publication Checklist](../manual-nuget-publication.md) is the authoritative publish-flow document for the coordinated family, pre-publish evidence, stop conditions, final approval record, and publish order.

Each package-version line is validated, approved, and published as one synchronized eight-package family. A publish approval for `8.34.0` does not approve `10.34.0`, and a publish approval for `10.34.0` does not approve `8.34.0`. Do not approve or push a partial provider subset.

## Validation Evidence

The repository validation command baseline remains:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/verify-packages.sh
bash tools/check-format.sh
```

Package-tested evidence is the release pack script plus package verification lane. `bash tools/pack-release-packages.sh` creates eight `8.34.0` `.nupkg` files for `net8.0` / EF Core 8 and eight `10.34.0` `.nupkg` files for `net10.0` / EF Core 10, plus matching runtime/provider symbol packages. `bash tools/verify-packages.sh` checks the sixteen `.nupkg` files, the fourteen expected symbol packages, package metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, DB2 `IBM.EntityFrameworkCore` dependency alignment, and the line-specific `net8.0` or `net10.0` dependency group for each package version.

Default local evidence stays separate from opt-in external-provider evidence. The normal local validation path includes required SQLite-backed integration coverage and provider registration smoke coverage through the existing xUnit categories:

- `Category=ProviderIntegration.RequiredLocal`
- `Category=ProviderSmoke.Default`
- `Category=ProviderIntegration.ExternalOptIn`

`Category=ProviderIntegration.ExternalOptIn` covers live PostgreSQL, SQL Server, Oracle, MySQL, and DB2 database execution only when the caller supplies the documented connection-string gates:

- `DVAULT_TEST_POSTGRES_CONNECTION_STRING`
- `DVAULT_TEST_SQLSERVER_CONNECTION_STRING`
- `DVAULT_TEST_ORACLE_CONNECTION_STRING`
- `DVAULT_TEST_MYSQL_CONNECTION_STRING`
- `DVAULT_TEST_DB2_CONNECTION_STRING`

Default local test execution does not require those external databases. Missing connection strings are skip or opt-out evidence, not failed default-local validation.

## Limitations And Non-Goals

v0.34.0 does not add DB2 optimized latest-satellite read dispatch, staged DB2 bulk dispatch, provider-native chunk execution, DB2 live-schema reading, DB2 container provisioning, DB2 CI infrastructure, DB2 migrations automation, provider-specific PIT/bridge maintenance, or DB2 package publication evidence.

v0.34.0 does not provision Docker or Podman containers, databases, users, credentials, schemas, external-provider CI infrastructure, migration environments, or consumer application hosts. Live DB2 execution remains opt-in behind `DVAULT_TEST_DB2_CONNECTION_STRING`.

v0.34.0 does not add a standalone DVault CLI, first-party `dotnet ef` command shim, provider provisioning tool, platform management tool, DBA workflow automation, automatic artifact deployment, runtime artifact dispatch, automatic migration execution, automatic schema repair, or release automation. Existing consumer-owned design-time command guidance remains hosted by the consuming application.

v0.34.0 does not make external-provider integration mandatory in the default local validation path. The default local baseline remains build, test, pack, verify-packages, check-format, required SQLite-backed integration coverage, provider registration smoke coverage, and package/API verification available in the repository.

v0.34.0 does not record package publication. Package publication, final approval, package hashes, published package links, signing evidence, and stop-condition resolution remain separate release-operation records governed by the manual publication checklist.
