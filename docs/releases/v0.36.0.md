Release: `v0.36.0 - Binary Hash-Key Storage Adoption Guidance`

These notes define the v0.36.0 coordinated documentation baseline for the DVault package compatibility lines visible in the repository. ## Hash-Key Storage Guidance

DVault hash keys keep one logical representation: canonical lowercase hexadecimal text without a prefix. Request, save, read, diagnostics, support-bundle, and public metadata boundaries continue to use `string` hash-key values. The v0.36.0 guidance adds adopter-facing documentation for two physical storage profiles:

| Storage profile | Adoption posture | Public value boundary | Conversion behavior |
| --- | --- | --- | --- |
| `HexString` | Default compatible profile | Lowercase hexadecimal `string` | `none-string-model` |
| `Binary` | Explicit opt-in physical storage | Lowercase hexadecimal `string` | `lowercase-hex-string-to-bytes` |

`Binary` is not a public `byte[]` hash-key model. It persists digest bytes while preserving lowercase hexadecimal string values at the EF model boundary and at every DVault API boundary.

The active stable hash algorithm still determines digest width. `AddDVault()` keeps `sha256-v1` as the default stable hash service registration and keeps `HexString` as the compatible default storage profile. The built-in stable hash ids remain:

| AlgorithmId | Registration posture | Digest bytes | Hex characters | Guidance |
| --- | --- | ---: | ---: | --- |
| `sha256-v1` | Default registered by `AddDVault()` | 32 | 64 | Safe persisted-compatibility baseline |
| `sha1-v1` | Explicit opt-in only | 20 | 40 | Non-adversarial identity tradeoff only |
| `sha256-128-v1` | Explicit opt-in only | 16 | 32 | Non-adversarial shorter SHA-256-derived identity tradeoff |
| `sha256-160-v1` | Explicit opt-in only | 20 | 40 | Non-adversarial shorter SHA-256-derived identity tradeoff |

Algorithm id, digest byte length, digest encoding, hash-key storage profile, provider store type, provider value format, and conversion behavior are persisted compatibility facts. Changing any of them after hub keys, link keys, PIT rows, bridge rows, or satellite parent references have been persisted is caller-owned compatibility work.

DVault does not automatically rehash, backfill, migrate, repair, reconcile, or dual-write persisted keys when callers change stable hash algorithm or storage profile. Consumers that deliberately move from `HexString` to `Binary`, or between stable hash algorithms, should treat that as a reviewed application migration or data-reset plan outside the default runtime behavior.

## Provider Column Types

Built-in provider profiles size both `HashKey` and `ParticipantReference` storage from the active digest length.

| Provider profile | `HexString` storage | `Binary` storage | Width basis |
| --- | --- | --- | --- |
| SQLite `sqlite-v1` | `TEXT` | `BLOB` | Unbounded SQLite type names; payload bytes follow active digest width |
| Oracle `oracle-v1` | `VARCHAR2(n CHAR)` | `RAW(n)` | `n` is hex characters for `HexString`; digest bytes for `Binary` |
| PostgreSQL `postgres-v1` | `varchar(n)` | `bytea` | `n` is hex characters for `HexString`; `bytea` stores digest bytes for `Binary` |
| SQL Server `sqlserver-v1` | `nvarchar(n)` | `varbinary(n)` | `n` is hex characters for `HexString`; digest bytes for `Binary` |
| DB2 `db2-v1` | `VARCHAR(n)` | `VARBINARY(n)` | `n` is hex characters for `HexString`; digest bytes for `Binary` |
| MySQL `mysql-pomelo-v1` | `varchar(n)` | `varbinary(n)` | `n` is hex characters for `HexString`; digest bytes for `Binary` |

Examples:

- `sha256-v1` has 32 digest bytes and 64 hex characters, so SQL Server uses `nvarchar(64)` for `HexString` and `varbinary(32)` for `Binary`.
- `sha256-128-v1` has 16 digest bytes and 32 hex characters, so Oracle uses `VARCHAR2(32 CHAR)` for `HexString` and `RAW(16)` for `Binary`.

DB2 live-schema reading remains unsupported for `IBM.EntityFrameworkCore` until a DB2 catalog reader exists. DB2 provider packages still expose the capability profile and diagnostics-gated save/PIT/bridge read behavior documented in earlier baselines, but v0.36.0 does not add DB2 live-schema support.

## Limitations And Non-Goals

v0.36.0 does not change the runtime default stable hash algorithm, canonical normalizer, provider-side hashing behavior, persistence content-hash semantics, or public hash-key value type. It does not change request, save, read, explain, or support-bundle boundaries to expose raw bytes.

v0.36.0 does not add automatic rehashing, backfilling, dual-writing, persisted-key repair, migration tooling, collision simulation, provider-side SQL hashing, or HashDiff/content-hash storage changes.

v0.36.0 does not add DB2 live-schema catalog reading, provider-specific empirical evidence beyond the checked-in SQLite-local hash-key storage bundle, or cross-provider storage and lookup guarantees.

v0.36.0 does not make `sha1-v1` or truncated SHA-256 ids security features, compliance controls, password-hashing policies, message authentication codes, digital signatures, encryption schemes, or adversarial collision-defense policies.

v0.36.0 does not record package publication. Package publication, final approval, package hashes, published package links, signing evidence, and stop-condition resolution remain separate release-operation records governed by the manual publication checklist.
