# DVault v0.15.0 Release Notes

Release: `v0.15.0 - Explicit Read-Model Maintenance And Optimized Reads`
Intended release date: 2026-05-19

## Package Scope

This is a coordinated release for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`

## Highlights

- Added the public `IDataVaultPitMaintenanceService` as the explicit provider-neutral PIT population boundary, registered through the normal `AddDVault()` startup path beside `IDataVaultSaveService`, `IDataVaultReadService`, and `IDataVaultBridgeMaintenanceService`.
- Added `DataVaultPitRebuildRequest`, `DataVaultPitParentMaintenanceRequest`, and `DataVaultPitMaintenanceResult` for full PIT rebuilds and bounded parent maintenance over existing `DataVaultPitMetadata`.
- Implemented deterministic PIT row generation from persisted same-parent satellite history, including missing snapshot segments and late-arriving satellite corrections for maintained parents.
- Added the public `IDataVaultBridgeMaintenanceService` as the explicit provider-neutral bridge population boundary for callers with `DataVaultBridgeMetadata`.
- Added registry-backed bridge maintenance through `DataVaultRegistryBridgeMaintenanceRequest` and service extensions so callers using `UseDataVaultMetadata()` can maintain a bridge by logical name.
- Implemented many-to-many bridge rebuild and incremental maintenance over persisted source-link rows with one stored bridge row per distinct endpoint pair.
- Implemented hierarchy bridge rebuild and incremental maintenance over persisted recursive link rows with one stored row per distinct ancestor/descendant pair.
- Defined hierarchy `TraversalDepth` as the shortest positive recursive-link path length, with direct edges stored as depth `1` and no implicit self rows.
- Added current/as-of satellite read convenience overloads for explicit metadata and registry-backed `UseDataVaultMetadata()` callers while keeping `DataVaultLatestSatelliteReadRequest` as the compatibility baseline.
- Added SQLite provider-aware PIT and bridge read dispatch through `AddDVaultSqlite()` for supported shapes, with provider-neutral fallback when a provider or request shape is unsupported.

## PIT Maintenance Contract

PIT maintenance is caller-invoked. It reads persisted same-parent satellite history and writes only the generated PIT table for one requested `DataVaultPitMetadata` declaration. The current runtime baseline supports one hub or link parent plus ordered non-multi-active satellites attached to that same parent. It does not run during ordinary reads, ordinary saves, EF `SaveChanges`, provider startup, or background scheduling.

`RebuildAsync(...)` with `DataVaultPitRebuildRequest` clears the requested generated PIT table and rewrites the complete PIT history implied by the current persisted satellite rows. For each parent hash key, DVault materializes one PIT row for each distinct declared-satellite load timestamp and stores the latest visible snapshot timestamp for each declared satellite at that PIT row timestamp.

`MaintainParentsAsync(...)` with `DataVaultPitParentMaintenanceRequest` recomputes complete PIT history for explicit parent hash keys only. It deletes existing PIT rows for those parents before inserting the recomputed rows, so late-arriving satellite records can correct prior PIT snapshots for those parents. Empty parent-hash-key requests are accepted as no-ops.

PIT-backed reads consume these maintained PIT rows. They do not populate, refresh, or repair PIT rows implicitly.

## Bridge Maintenance Contract

Bridge maintenance is caller-invoked. It reads persisted source-link state and writes only the generated bridge table for one requested bridge. It does not run during ordinary reads, ordinary saves, EF `SaveChanges`, provider startup, or background scheduling.

`RebuildBridgeAsync(...)` clears the requested generated bridge table and writes the rows implied by the current persisted source-link state. For many-to-many bridges, the rebuilt table contains exactly one row for each distinct endpoint pair required by the bridge metadata. For hierarchy bridges, the rebuilt table contains exactly one row for each distinct ancestor/descendant pair reachable through positive recursive-link paths.

`MaintainBridgeAsync(...)` is addition-oriented for post-ingestion maintenance. It inserts missing bridge rows implied by the current persisted source-link state. For hierarchy bridges, it also updates an existing row when a newly materialized alternate path produces a lower `TraversalDepth`; equal-depth or longer alternate paths do not change the stored row.

## Read Service And Provider Dispatch

`ReadCurrentSatelliteRowsAsync(...)`, `ReadCurrentSatelliteAsync(...)`, `ReadAsOfSatelliteRowsAsync(...)`, and `ReadAsOfSatelliteAsync(...)` are convenience overloads over the existing latest-satellite read baseline. They construct `DataVaultLatestSatelliteReadRequest` instances for explicit metadata or registry-backed callers and do not add a separate satellite semantics contract.

PIT-backed reads and bridge reads remain read-service operations over maintained read-model tables. `AddDVaultSqlite()` registers `SqliteDataVaultReadStrategy` as the repository-proven optimized path for supported latest-satellite, PIT, and bridge read shapes. Unsupported providers, unsupported shapes, or declined strategy gates fall back to provider-neutral read pipelines without implicit PIT or bridge maintenance side effects.

## Hierarchy Depth Semantics

Hierarchy bridge rows store the minimum positive hop count across all currently materialized recursive-link paths for the ancestor/descendant pair. Direct parent-child edges are depth `1`. Longer indirect paths are depth `2` or greater. Cycles do not create implicit self rows, and the bridge table stores no path payload, effectivity window, or closure-maintenance state.

When destructive topology changes remove paths or make the shortest available path longer, callers should use `RebuildBridgeAsync(...)`. Incremental maintenance is intentionally not delete-aware and does not increase stored `TraversalDepth`.

## Compatibility Notes

- Existing `IDataVaultSaveService` and `IDataVaultReadService` APIs remain compatible.
- Existing latest/as-of satellite request objects and `ReadLatestSatelliteRowsAsync(...)` / `ReadLatestSatelliteAsync(...)` remain supported. The current/as-of convenience overloads delegate to that latest-satellite pipeline and do not add PIT-backed historical fallback behavior.
- Existing PIT-backed read requests continue to read maintained PIT tables through the same parent hash-key and `asOf` filters.
- Existing bridge read requests continue to read maintained bridge tables through the same endpoint hash-key filters and projection delegates.
- Existing manually populated PIT or bridge rows remain ordinary generated table rows; the new maintenance services give callers first-party ways to populate the same tables from persisted source state.
- Provider packages can continue to register provider-specific save or read optimizations without changing the provider-neutral PIT and bridge maintenance contracts.

## Known Limitations

- PIT and bridge maintenance remain provider-neutral and correctness-first; this release does not add provider-specific maintenance SQL, physical tuning, or benchmark claims for maintenance operations.
- PIT maintenance is one PIT per request and bridge maintenance is one bridge per request. This release does not add multi-read-model batch orchestration.
- PIT maintenance is limited to the existing `DataVaultPitMetadata` / registry-backed runtime baseline for hub- or link-parent non-multi-active PITs. Multi-active PITs, provider-specific PIT maintenance strategies, hosted orchestration, PIT/bridge coordination, and `dvault.model.v1` link-parent PIT declarations/import-export/diagnostics remain outside the current claim set.
- Incremental hierarchy bridge maintenance is not delete-aware and does not handle topology shrinkage that would require row removal or increased `TraversalDepth`; callers should run a full bridge rebuild for those cases.
- Effectivity windows, path payload columns, generated relationship graphs, closure-state columns, and broader graph traversal APIs remain outside the v0.15.0 bridge baseline.
- Non-SQLite provider-specific PIT or bridge read optimization is not claimed. Unsupported providers and unsupported request shapes fall back to provider-neutral read pipelines.
- PIT and bridge maintenance are not automatic, scheduler-driven, trigger-driven, read-time maintenance, or SaveChanges interception.
