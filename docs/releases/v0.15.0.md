# DVault v0.15.0 Release Notes

Release: `v0.15.0 - Explicit Bridge Maintenance`
Intended release date: 2026-05-19

## Package Scope

This is a coordinated release for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.15.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Added the public `IDataVaultBridgeMaintenanceService` as the explicit provider-neutral bridge population boundary, registered through the normal `AddDVault()` startup path beside `IDataVaultSaveService` and `IDataVaultReadService`.
- Added explicit bridge maintenance requests and results for callers that already have `DataVaultBridgeMetadata`.
- Added registry-backed bridge maintenance through `DataVaultRegistryBridgeMaintenanceRequest` and service extensions so callers using `UseDataVaultMetadata()` can maintain a bridge by logical name.
- Implemented many-to-many rebuild and incremental maintenance over persisted source-link rows with one stored bridge row per distinct endpoint pair.
- Implemented hierarchy rebuild and incremental maintenance over persisted recursive link rows with one stored row per distinct ancestor/descendant pair.
- Defined hierarchy `TraversalDepth` as the shortest positive recursive-link path length, with direct edges stored as depth `1` and no implicit self rows.
- Kept bridge reads compatible: `IDataVaultReadService` continues to consume maintained bridge tables and still requires bounded `maximumDepth` for hierarchy reads.

## Bridge Maintenance Contract

Bridge maintenance is caller-invoked. It reads persisted source-link state and writes only the generated bridge table for one requested bridge. It does not run during ordinary reads, ordinary saves, EF `SaveChanges`, provider startup, or background scheduling.

`RebuildBridgeAsync(...)` clears the requested generated bridge table and writes the rows implied by the current persisted source-link state. For many-to-many bridges, the rebuilt table contains exactly one row for each distinct endpoint pair required by the bridge metadata. For hierarchy bridges, the rebuilt table contains exactly one row for each distinct ancestor/descendant pair reachable through positive recursive-link paths.

`MaintainBridgeAsync(...)` is addition-oriented for post-ingestion maintenance. It inserts missing bridge rows implied by the current persisted source-link state. For hierarchy bridges, it also updates an existing row when a newly materialized alternate path produces a lower `TraversalDepth`; equal-depth or longer alternate paths do not change the stored row.

## Hierarchy Depth Semantics

Hierarchy bridge rows store the minimum positive hop count across all currently materialized recursive-link paths for the ancestor/descendant pair. Direct parent-child edges are depth `1`. Longer indirect paths are depth `2` or greater. Cycles do not create implicit self rows, and the bridge table stores no path payload, effectivity window, or closure-maintenance state.

When destructive topology changes remove paths or make the shortest available path longer, callers should use `RebuildBridgeAsync(...)`. Incremental maintenance is intentionally not delete-aware and does not increase stored `TraversalDepth`.

## Documentation Updates

- `README.md` now documents explicit bridge maintenance beside bridge reads, including rebuild, incremental maintenance, registry-backed resolution, and minimum-hop hierarchy depth behavior.
- `README.md` now treats v0.15.0 as the current release-note baseline while preserving explicit service boundaries from earlier releases.
- `docs/production-adoption-checklist.md` points adopters at `IDataVaultBridgeMaintenanceService` after source-link ingestion and keeps automatic maintenance, provider-specific optimization, and delete-aware hierarchy shrinking outside the current production-adoption baseline.
- Historical release notes remain historical. Earlier notes that describe bridge rows as read-only or caller-populated should not be read as the current v0.15.0 baseline.

## Compatibility Notes

- Existing `IDataVaultSaveService` and `IDataVaultReadService` APIs remain compatible.
- Existing bridge read requests continue to read maintained bridge tables through the same endpoint hash-key filters and projection delegates.
- Existing manually populated bridge rows remain ordinary generated bridge table rows; the new maintenance service gives callers a first-party way to populate the same tables from persisted source-link state.
- PIT-backed reads still do not maintain PIT rows. PIT maintenance remains outside this release.
- Provider packages can continue to register provider-specific save or read optimizations without changing the provider-neutral bridge maintenance contract.

## Known Limitations

- Bridge maintenance remains provider-neutral and correctness-first; this release does not add provider-specific bulk SQL, physical tuning, or benchmark claims for bridge maintenance.
- Bridge maintenance is one bridge per request. This release does not add multi-bridge batch orchestration.
- Incremental hierarchy maintenance is not delete-aware and does not handle topology shrinkage that would require row removal or increased `TraversalDepth`; callers should run a full rebuild for those cases.
- Effectivity windows, path payload columns, generated relationship graphs, closure-state columns, broader graph traversal APIs, PIT interactions, and multi-active interactions remain outside the v0.15.0 bridge baseline.
- Bridge maintenance is not automatic, scheduler-driven, trigger-driven, read-time maintenance, or SaveChanges interception.
