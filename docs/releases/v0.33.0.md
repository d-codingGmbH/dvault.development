# DVault v0.33.0 Release Notes

Release: `v0.33.0 - Net8 And Net10 Compatibility Documentation Baseline`
Intended release date: 2026-06-09

These notes define the v0.33.0 coordinated documentation baseline for the DVault package compatibility lines visible in the repository. They record the seven-package family, the supported consumer package-version lines, the finite .NET and EF Core provider matrix, the manual publication boundary, package-tested and local validation evidence, opt-in external-provider evidence, compatibility caveats, and explicit non-goals. They do not record a NuGet push, package hashes, final publication links, release approval, runtime behavior changes, provider provisioning, standalone platform tooling, release automation, or a new default requirement for live external databases. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Package Scope

This is a coordinated release record for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

The package ids stay unchanged across the v0.33 compatibility lines. The `src/DCoding.Data` project remains a non-packable source-root build anchor for the namespace family and is not a NuGet publication artifact.

The planning release label `v0.33.0` is not a consumer-facing NuGet package version. Consumers choose exactly one aligned package-version line per project:

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.33.0` | `net8.0` | EF Core 8 |
| `10.33.0` | `net10.0` | EF Core 10 |

Do not publish or document a consumer-facing `0.33.0` package version. Do not combine `8.33.0` and `10.33.0` packages in one consumer project, one install example, one restored target, or one publish approval.

Provider-neutral EF Core references, runtime DVault packages, provider DVault packages, analyzer package references, and package verification expectations must stay aligned with the selected consumer package-version line.

## Consumer Guidance

Use the [README installation guidance](../../README.md#installation) for consumer setup. For `net8.0` projects on EF Core 8, install the `8.33.0` DVault runtime, provider, and analyzer package line. For `net10.0` projects on EF Core 10, install the `10.33.0` line. Keep `DCoding.Data.DVault.Analyzers` local to the project that owns DVault declarations or generated read helpers with `PrivateAssets="all"`.

Consumers still install and configure the normal Entity Framework Core database provider package used by the application. DVault provider packages register DVault-specific provider behavior; they do not replace the application-owned EF provider selection, connection strings, migrations, credentials, schema lifecycle, or deployment operations.

## Manual Publication Boundary

Publication remains manual and separate from this documentation baseline. The [Manual NuGet Publication Checklist](../manual-nuget-publication.md) is the authoritative publish-flow document for the coordinated family, pre-publish evidence, stop conditions, final approval record, and publish order.

Each package-version line is validated, approved, and published as one synchronized seven-package family. A publish approval for `8.33.0` does not approve `10.33.0`, and a publish approval for `10.33.0` does not approve `8.33.0`. Do not approve or push a partial provider subset.

## Validation Evidence

The repository validation command baseline remains:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
dotnet pack DVault.slnx --configuration Release --nologo
bash tools/verify-packages.sh
bash tools/check-format.sh
```

Package-tested evidence is the solution pack plus package verification lane. `bash tools/verify-packages.sh` checks the seven `.nupkg` files, the expected symbol packages, package metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, and the `net8.0` and `net10.0` dependency groups.

Default local evidence stays separate from opt-in external-provider evidence. The normal local validation path includes required SQLite-backed integration coverage and provider registration smoke coverage through the existing xUnit categories:

- `Category=ProviderIntegration.RequiredLocal`
- `Category=ProviderSmoke.Default`
- `Category=ProviderIntegration.ExternalOptIn`

`Category=ProviderIntegration.ExternalOptIn` covers live PostgreSQL, SQL Server, Oracle, and MySQL database execution only when the caller supplies the documented connection-string gates:

- `DVAULT_TEST_POSTGRES_CONNECTION_STRING`
- `DVAULT_TEST_SQLSERVER_CONNECTION_STRING`
- `DVAULT_TEST_ORACLE_CONNECTION_STRING`
- `DVAULT_TEST_MYSQL_CONNECTION_STRING`

Default local test execution does not require those external databases. Missing connection strings are skip or opt-out evidence, not failed default-local validation.

## Limitations And Non-Goals

v0.33.0 does not add new runtime behavior, persistence semantics, provider strategy behavior, provider support, target frameworks beyond the documented matrix, EF Core dependency selection rules beyond the documented matrix, or package ids.

v0.33.0 does not provision Docker containers, databases, users, credentials, schemas, external-provider CI infrastructure, migration environments, or consumer application hosts. Live PostgreSQL, SQL Server, Oracle, and MySQL execution remains opt-in behind `DVAULT_TEST_*` connection-string gates.

v0.33.0 does not add a standalone DVault CLI, first-party `dotnet ef` command shim, provider provisioning tool, platform management tool, DBA workflow automation, automatic artifact deployment, runtime artifact dispatch, automatic migration execution, automatic schema repair, or release automation. Existing consumer-owned design-time command guidance remains hosted by the consuming application.

v0.33.0 does not make external-provider integration mandatory in the default local validation path. The default local baseline remains build, test, pack, verify-packages, check-format, required SQLite-backed integration coverage, provider registration smoke coverage, and package/API verification available in the repository.

v0.33.0 does not record package publication. Package publication, final approval, package hashes, published package links, signing evidence, and stop-condition resolution remain separate release-operation records governed by the manual publication checklist.
