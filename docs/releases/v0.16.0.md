# DVault v0.16.0 Release Notes

Release: `v0.16.0 - Telemetry And Support Bundle Diagnostics`
Intended release date: 2026-05-20

## Package Scope

This is a coordinated release for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.16.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Added an opt-in save/read telemetry surface in the core package through `IDataVaultTelemetryObserver`, `DataVaultSaveTelemetrySummary`, and `DataVaultReadTelemetrySummary`.
- Added `AddDVaultTelemetry()` for the built-in `System.Diagnostics.Metrics` observer while keeping the default `AddDVault()` registration free of telemetry observers and counters.
- Emitted one bounded save telemetry summary for each explicit single or bulk save attempt, including request counts, hub/link/satellite operation counts, rows written, saved-record count, duration, selected strategy status, selected strategy name, and finite fallback-cause kinds.
- Emitted one bounded read telemetry summary for latest/current/as-of satellite reads, PIT reads, and bridge reads, including requested-key counts, returned-row counts, duration, selected strategy status, selected strategy name, and finite fallback-cause kinds.
- Added the consumer-owned `support-bundle` design-time command path, exporting one deterministic redacted JSON payload under the `dvault.support-bundle.v1` contract.
- Reused the established diagnostics and request-bound save/read strategy explainability vocabulary for telemetry status, fallback classification, and support-bundle evidence.
- Updated public documentation so the current baseline points at v0.16.0 telemetry and support-bundle behavior without changing provider behavior or release publication mechanics.

## Telemetry Contract

Telemetry is observational and opt-in. Applications that keep the current `AddDVault()` startup path do not need to configure listeners and keep the same save/read behavior. Applications that want built-in counters can add:

```csharp
services.AddDVault();
services.AddDVaultTelemetry();
```

The built-in meter name is `DCoding.Data.DVault`. Save instruments cover attempts, rows written, saved records, request counts, operation counts, duration, and provider-neutral fallback causes. Read instruments cover attempts, returned rows, requested keys, duration, and provider-neutral fallback causes. Tags are limited to stable low-cardinality values: operation kind, read family, success/failure outcome, provider name, selected strategy type name, strategy status, and finite fallback-cause enum names.

Applications that need code-facing hooks can register custom `IDataVaultTelemetryObserver` services. Observers receive `DataVaultSaveTelemetrySummary` and `DataVaultReadTelemetrySummary` values after each completed or failed explicit attempt. Observer failures are ignored so telemetry cannot change persistence or read behavior.

## Save Coverage

Save telemetry is emitted from the explicit save implementation path used by `IDataVaultSaveService.SaveAsync(DbContext, DataVaultSaveRequest)` and `IDataVaultSaveService.SaveAsync(DbContext, DataVaultBulkSaveRequest)`. Registry-backed and typed mapper save helpers delegate into the same explicit service, so they share the same telemetry boundary.

Each save summary identifies single-request versus bulk invocation, reports request and operation counts, reports rows written and saved-record counts for successful attempts, records elapsed duration, and classifies provider strategy dispatch with `DataVaultSaveStrategyDiagnosticsStatus` and `DataVaultSaveStrategyFallbackCauseKind`.

## Read Coverage

Read telemetry is emitted from the default explicit read service paths for latest/current/as-of satellite reads, PIT reads, and bridge reads. The implementation also covers typed latest/as-of satellite projection and bridge projection helper paths that use the default DVault read service instead of relying on an external service decorator.

Each read summary identifies the read family, reports requested parent or endpoint key counts, reports returned-row counts for successful attempts, records elapsed duration, and classifies provider strategy dispatch with `DataVaultReadStrategyDiagnosticsStatus` and `DataVaultReadStrategyFallbackCauseKind`.

## Strategy Explainability Baseline

The release does not introduce a separate telemetry-only classification system. Telemetry and support-bundle output reuse the existing diagnostics vocabulary:

- `IDataVaultDiagnosticsService.Analyze(...)` still provides validation and explain output for metadata models, registries, Code-First declarations, and configured DbContexts.
- Request-bound save diagnostics still classify provider strategy selection with `DataVaultSaveStrategyDiagnosticsStatus`, selected strategy type name, provider name, and finite `DataVaultSaveStrategyFallbackCauseKind` values.
- Request-bound read diagnostics still classify latest/current/as-of satellite, PIT, and bridge read strategy selection with `DataVaultReadStrategyDiagnosticsStatus`, selected strategy type name, provider name, and finite `DataVaultReadStrategyFallbackCauseKind` values.
- Request-bound read diagnostics also expose an additive `DataVaultDiagnosticsResult.ReadShape` payload for latest/current/as-of satellite, PIT as-of, and bridge requests. This payload describes translated table identity, filter columns, row-selection and ordering rules, key/index baselines, and provider fallback caveats without including raw request values or SQL text.
- Telemetry summaries and support bundles preserve those bounded classifications instead of emitting raw SQL, exception text, hash keys, record sources, metadata names, table names, or full diagnostics text as metric tags.

## Support Bundle Export

DVault exposes the `support-bundle` verb through `DataVaultDesignTimeCommand` and `DataVaultDesignTimeCommandHost`. The command remains hosted by the consuming application project that owns the configured `DbContext`, design-time factory, migrations, metadata source, and command entrypoint:

```sh
dotnet run --project src/SalesVault/SalesVault.csproj -- support-bundle --output src/SalesVault/dvault-support-bundle.json
```

The default command path constructs the configured design-time `DbContext`, runs `IDataVaultDiagnosticsService.Analyze(DbContext)`, and serializes a `DataVaultSupportBundle` through `DataVaultSupportBundleExporter.ExportJson(...)`. The resulting JSON uses `schemaVersion: "dvault.support-bundle.v1"` and includes the diagnostics validation, explain, save-strategy, and read-strategy sections already present in the `DataVaultDiagnosticsResult`. When application code supplies request-bound read diagnostics, the bundle includes the additive `readShape` section in the same deterministic camelCase output.

The default path does not open a live database connection. `--artifact <path>` imports the reviewed `dvault.model.v1` artifact and adds a `DataVaultModelDriftReport` comparing that artifact with the current design-time model. `--live-schema` adds a `DataVaultLiveSchemaReadResult`; when it is combined with `--artifact`, the drift section is based on the live-schema result and selected provider capability profile.

Applications with representative save or read requests can set `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics` so the bundle records request-bound strategy diagnostics supplied by application code. The generic command runner does not invent representative requests.

Support bundle JSON is deterministic and redacted. Connection-string and URI credential fragments are redacted while provider names, profile names, diagnostic codes, metadata identifiers, and bounded strategy classifications remain available for troubleshooting.

## Out Of Scope

This release does not add telemetry for the SaveChanges metadata interceptor, diagnostics service calls themselves, design-time commands, migration guardrails, live-schema readers, PIT maintenance, bridge maintenance, or general EF Core activity outside explicit DVault save/read operations.

The support-bundle path does not add a standalone `dvault` CLI, a `dotnet ef` shim, EF CLI interception, automatic migration execution, automatic schema repair, automatic telemetry backend configuration, support-bundle upload, support-bundle archival, or release publication automation.

## Compatibility Notes

- Existing applications that call `AddDVault()` keep the same service registration behavior unless they explicitly call `AddDVaultTelemetry()` or register their own `IDataVaultTelemetryObserver`.
- Existing `IDataVaultSaveService`, `IDataVaultReadService`, PIT maintenance, bridge maintenance, diagnostics, model artifact, live-schema drift, and migration guardrail APIs remain compatible.
- `DataVaultDiagnosticsResult.ReadShape` is additive and nullable. Request-unbound `IDataVaultDiagnosticsService.Analyze(DbContext)` does not populate it; request-bound `IDataVaultReadDiagnosticsService.Analyze(...)` overloads populate it after any registry-backed latest-satellite or bridge request has resolved to the equivalent explicit request.
- Existing provider packages can continue to register provider-specific save and read strategies without changing the provider-neutral persistence, read, PIT, or bridge contracts.
- Existing design-time command hosts keep the same consumer-owned execution boundary. The reusable command runner adds `support-bundle` as another verb in that host; it still does not replace `dotnet ef` or own application migrations.
- Package publication remains manual and coordinated across all seven package ids.

## Known Limitations

- Telemetry is opt-in and library-local. DVault does not configure metric listeners, exporters, dashboards, alert rules, or backend-specific observability pipelines.
- Telemetry is bounded to explicit DVault save and read attempts. It does not cover ordinary EF Core activity, SaveChanges metadata interception, model validation, migration guardrails, live-schema reads, PIT maintenance, bridge maintenance, or support-bundle command execution.
- Metric tags intentionally stay low-cardinality. Raw exception messages, hash keys, record sources, metadata names, table names, generated SQL, and full diagnostics text are not emitted as counters or tags.
- Support bundles are generated by a consumer-owned design-time command host. DVault still does not ship a standalone CLI, intercept EF CLI commands, auto-run migrations, apply schema repairs, or own startup-project and target-project split layouts.
- Default support-bundle diagnostics analyze the configured design-time model. Request-bound save/read strategy evidence requires consumer code to supply representative diagnostics through `CreateSupportBundleDiagnostics`.
- Live-schema support-bundle sections remain opt-in and operationally managed by the consumer application. PostgreSQL, SQL Server, Oracle, and MySQL checks still require reachable databases, credentials, lifecycle cleanup, and CI isolation.
- Support-bundle distribution, attachment, archival, retention, and approval workflows remain outside this release.
