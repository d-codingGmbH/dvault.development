# DVault v0.100.0 Release Notes

Release: `v0.100.0 - Binary Hash-Key Default And Provider Parity`
Release date: 2026-07-02

These notes record the coordinated v0.100.0 breaking storage-default release, provider binary-default parity closure, dependent-child-key and effectivity modeling additions, documentation, validation, package-verifier, and package-line baseline for DVault. The public release label maps to the consumer package versions `8.100.0` and `10.100.0`. There is no consumer-facing `0.100.0` package version.

## Package Lines

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.100.0` | `net8.0` | EF Core 8 |
| `10.100.0` | `net10.0` | EF Core 10 |

Use exactly one line in a consumer project. Do not mix `8.100.0` and `10.100.0` packages in one project, install example, restored target, or publish approval.

## Breaking Storage Default

Generated hash-key and participant-reference columns now default to binary physical storage. Public DVault hash-key values remain lowercase hexadecimal strings at save, read, diagnostics, support-bundle, and model-governance boundaries.

Existing persisted `HexString` schemas are not migrated automatically. Recommended NuGet release-note wording for both package lines:

> Breaking release. DVault v0.100.0 publishes package versions 8.100.0 for net8.0/EF Core 8 and 10.100.0 for net10.0/EF Core 10. Generated hash-key and participant-reference columns now default to binary physical storage. Public hash-key values remain lowercase hex strings. Existing persisted HexString schemas are not migrated automatically; keep the previous package line or configure the HexString compatibility profile until a reviewed migration/reset/data-move plan is complete.

Use `UseHexStringStorageProfile()` for service registration or `UseDataVaultHexStringStorageProfile(...)` for EF model projection when an existing persisted schema must stay on hex-string physical storage. Use the hash-key storage migration guide before any intentional storage-profile change.

## Modeling Additions

v0.100.0 adds first-class support for the requested modeling gaps without turning DVault into a platform:

- Link metadata, Code-First declarations, explicit save operations, provider save strategies, design-time artifacts, diagnostics, and generated mapping support dependent child keys.
- Repeated same-hub link participants are supported when callers provide distinct explicit roles or produced participant names. DVault still fails closed when a same-hub mapping is ambiguous.
- Satellite metadata and Code-First declarations support effectivity roles through `EffectiveFrom`, optional `EffectiveTo`, and optional `CurrentFlag` payload fields.

These features remain inside the EF Core library surface. They do not add scheduling, ingestion orchestration, automatic PIT/bridge maintenance, or automatic semantic inference.

## Hashing And Allocation

The default stable hash algorithm id remains `sha256-v1`. The physical storage default changed to binary, and the built-in stable hash service now uses stack-allocated and pooled byte buffers for UTF-8 digest input handling where the implementation can do so safely.

`sha1-v1`, `sha256-128-v1`, and `sha256-160-v1` remain explicit opt-in non-adversarial identity-hashing tradeoffs. DVault does not automatically migrate, repair, reconcile, rehash, dual-write, or backfill persisted keys when an application changes algorithm id, digest width, or physical storage profile.

## Provider Binary-Default Parity

v0.100.0 closes the current binary-default provider parity pass by aligning SQLite, PostgreSQL, SQL Server, MySQL, Oracle, and DB2 provider save/read paths around binary hash-key storage. The current checked-in benchmark evidence is under `artifacts/benchmarks/v0.100.0-provider-binary-closure-20260702/`:

| Provider | Completed rows | Failed rows |
| --- | ---: | ---: |
| SQLite | 28 | 0 |
| PostgreSQL | 8 | 0 |
| SQL Server | 7 | 0 |
| MySQL | 7 | 0 |
| Oracle | 5 | 0 |
| DB2 | 5 | 0 |

The benchmark bundle ran one iteration and no warmup on Windows/.NET 10.0.9. PostgreSQL and DB2 were validated through the local Podman-backed test setup while preserving the benchmark harness external-provider contract. The timing rows are evidence for the checked-in run context, not absolute provider service-level objectives.

The provider-specific packages continue to keep their explicit fallback boundaries. DB2 remains a clean-context optimized save/read provider without staged bulk or provider-native chunk execution claims. PIT and bridge read timings assume the read-model rows were maintained before the measured read operation.

## Package Verification

`bash tools/pack-release-packages.sh` creates the coordinated package artifacts under `artifacts/packages/` for both visible package lines. `bash tools/verify-packages.sh` validates the expected package counts, package ids, versions, filenames, metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, DB2 dependency alignment, EF Core dependency lines, symbol packages, and stale package artifacts.

Package verification preserves stale-version guardrails for current-package guidance. Packaged README install guidance must not publish `0.100.0` from the release label, must not use stale package lines, must not mix the `8.100.0` and `10.100.0` lines, and must retain the dual `.NET 8 SDK` / `.NET 10 SDK` analyzer build-host guidance plus the one `netstandard2.0` analyzer asset contract.

Package creation and verification do not imply signed NuGet publication or final publish approval.

## Validation

The release validation lane is:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/run-analyzer-package-smoke.sh 8
bash tools/run-analyzer-package-smoke.sh 10
bash tools/verify-packages.sh
bash tools/check-format.sh
```

External provider validation remains opt-in through local `DVAULT_TEST_*` connection strings. The release evidence includes individual live provider integration runs for PostgreSQL, SQL Server, MySQL, Oracle, and DB2, plus provider benchmark artifacts for SQLite, PostgreSQL, SQL Server, MySQL, Oracle, and DB2 under the v0.100.0 benchmark bundle.

## Non-Goals

v0.100.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.100.0 does not define a consumer-facing `0.100.0` package version. Consumers should use the target-specific `8.100.0` or `10.100.0` package line.

v0.100.0 does not automatically migrate existing persisted hash-key storage, rehash values, backfill values, dual-write keys, provision providers, manage provider credentials, perform privacy compliance, execute provider-native encryption, emit encrypted DDL, manage key stores, delete rows, purge backups, perform crypto-shredding, create provider service-level objectives, add provider-specific bridge maintenance, or turn DVault into an ingestion platform or tool suite.
