## Boundary Shift From v0.27.0

v0.27.0 moved the coordinated public baseline forward around EF Core lifecycle analyzer guardrails. That analyzer-only boundary remains intact and historical.

v0.28.0 moves the current public baseline forward for provider read optimization guidance. The current documentation now distinguishes three surfaces that previously appeared together in older summaries:

- SQLite remains the only repository-proven optimized latest-satellite read provider path.
- SQLite, PostgreSQL, SQL Server, MySQL, and Oracle have diagnostics-gated PIT/bridge optimized read strategy candidates for supported maintained PIT and bridge shapes.
- Unsupported providers, non-SQLite latest-satellite reads, unsupported request shapes, incomplete read-shape evidence, and stale PIT/bridge maintenance evidence fall back to provider-neutral read pipelines.

This release is a documentation baseline over existing provider registrations, diagnostics, benchmark artifacts, and tests. It does not add new runtime read strategies, new benchmark executions, new external-provider timing claims, or new maintenance behavior.

## Provider Read Optimization Boundary

`AddDVault()` remains the provider-neutral read-service baseline. It provides latest/current/as-of satellite reads, PIT reads, and bridge reads with provider-neutral fallback behavior.

`AddDVaultSqlite()` registers `SqliteDataVaultReadStrategy` for supported latest-satellite, PIT, and bridge read shapes. The checked-in benchmark triplet contains completed SQLite timing rows for `latest-satellite-read`, `pit-as-of-read`, and `bridge-traversal-read`.

`AddDVaultPostgres()`, `AddDVaultSqlServer()`, `AddDVaultMySql()`, and `AddDVaultOracle()` register optimized PIT and bridge read strategy candidates only. They do not register optimized latest-satellite read strategies. The checked-in optional-provider read rows for PostgreSQL, SQL Server, MySQL, and Oracle are guidance rows that remain `executionStatus=skipped` when their connection-string environment variables are unset.

PIT and bridge rows remain caller-owned read models. `IDataVaultPitMaintenanceService` and `IDataVaultBridgeMaintenanceService` must be invoked by application code when those materialized rows should be refreshed. Provider startup, reads, saves, EF `SaveChanges`, and background scheduling do not maintain PIT or bridge rows implicitly.

## Fallback And Explainability

Adopters should verify read optimization through `IDataVaultReadDiagnosticsService` before making provider-specific claims. The useful facts are:

- `ReadStrategy.Status`
- `ReadStrategy.ProviderName`
- `ReadStrategy.SelectedStrategyName`
- `ReadStrategy.FallbackCauses`
- `ReadShape.Kind`
- `ReadShape.Provider.ReadStrategyStatus`
- `ReadShape.Provider.ReadStrategyFallbackCauses`

Fallback causes remain finite enum-backed values, including provider mismatch, unsupported PIT/bridge shapes, incomplete read-shape evidence, stale read-model maintenance, and missing provider-specific strategy registrations. The detailed redaction boundary remains [DVault V2 Redacted Read-Plan Explain Contract](../architecture/dvault-v2-redacted-read-plan-explain-contract.md).

Diagnostics do not expose raw hash keys, business keys, as-of values, payload values, record-source values, raw SQL, query plans, credentials, connection strings, provider exception text, stack traces, automatic index advice, or provider-specific physical-design promises.
