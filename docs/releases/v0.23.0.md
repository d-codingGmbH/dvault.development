## Boundary Shift From v0.22.0

v0.22.0 moved the public documentation baseline forward for support-bundle-driven typed satellite read helpers and stable `sha256-v1` hash governance. That boundary remains intact and historical.

v0.23.0 moves the current coordinated public baseline forward for listener-driven Activity tracing and benchmark-backed performance-profile guidance. It adds internal Activity tracing instrumentation behind the existing save, read, PIT maintenance, and bridge maintenance service boundaries. It does not add public APIs, new span vocabulary beyond the v1 tracing contract, new tracing event names, new telemetry semantics, benchmark artifact rewrites, benchmark reruns, release automation, or package publication claims.

## Activity Tracing Boundary

DVault Activity tracing is listener-driven through the `DCoding.Data.DVault` ActivitySource. Applications opt in by registering an `ActivityListener`, OpenTelemetry tracing provider, or equivalent listener. `AddDVault()` remains telemetry-free by default: without an interested Activity listener, DVault continues the save, read, or maintenance operation without creating observable Activity instances or building meaningful tag or event payloads.

Activity tracing complements the existing observability surfaces. `AddDVaultTelemetry()`, built-in `System.Diagnostics.Metrics`, and `IDataVaultTelemetryObserver` remain sibling opt-in surfaces. They are not prerequisites for Activity tracing and do not replace Activity tracing.

The exact ActivitySource name, closed span-name vocabulary, closed event-name vocabulary, tag keys, sampling rules, status mapping, omission rules, and redaction rules are defined by [DVault V1 Activity Tracing Contract](../architecture/dvault-v1-activity-tracing-contract.md). Public adopter docs should link to that contract instead of redefining the contract details.

The adopter-facing redaction boundary is explicit: DVault Activity names, tags, events, status descriptions, and exception metadata must not include raw business keys or hash-key values, payload values, record sources, SQL text, credentials, connection strings, provider messages, exception messages, stack traces, support-bundle content, or full diagnostic text.

DVault does not configure OpenTelemetry packages, exporters, collectors, dashboards, alert rules, hosting, sampling policy, baggage, custom trace identifiers, custom correlation storage, or DVault-specific parent selection. Those remain application-owned integration choices.

## Performance Profile Guidance

The detailed v0.23.0 adopter guidance is [Performance Profiles](../performance-profiles.md). It summarizes four starting profiles and routes timing-sensitive claims back to the checked-in benchmark artifacts:

- Small app-local vault.
- Medium chunked ingestion.
- Staged provider ingestion.
- Read-model heavy.

The guide does not create absolute performance guarantees, provider service-level objectives, dashboards, hosted observability, database provisioning, scheduler templates, credential-management guidance, or a requirement to use a provider package before local diagnostics justify it.

## Compatibility Notes

Existing explicit save and read service boundaries remain compatible. `IDataVaultSaveService` remains the public write boundary for single, bulk, and chunked explicit saves. `DataVaultBulkSaveRequest` remains the compatibility baseline when callers already have a fully materialized ordered batch. `DataVaultChunkedSaveRequest` remains the provider-neutral bounded streaming input shape and does not become a provider-native chunk execution promise.

Provider-specific optimized save strategies remain diagnostics-gated implementations behind the same public service contract. PostgreSQL staged COPY, MySQL staged bulk, SQL Server native bulk wording, and Oracle retained direct optimized batching carry forward from the v0.20.0 boundary without new measured external-provider claims in this release.

PIT and bridge maintenance remain explicit caller-owned service boundaries. `IDataVaultPitMaintenanceService` and `IDataVaultBridgeMaintenanceService` do not add automatic scheduling, read-time refresh, delete-aware incremental bridge shrinkage, or provider-specific maintenance strategies. SQLite remains the only repository-proven optimized PIT and bridge read provider path; unsupported providers and unsupported shapes fall back to provider-neutral read pipelines.

Typed satellite read-model generation remains support-bundle-driven and satellite-only. Raw `dvault.model.v1` artifacts remain reviewed workflow inputs, not direct generator inputs. Dynamic `IDataVaultReadService` requests and consumer-owned EF compiled queries remain the documented alternatives outside generated satellite helpers.

The package-family boundary remains the seven package ids listed above, and coordinated publication remains manual.
