# DVault v0.17.0 Release Notes

Release: `v0.17.0 - EF Safety And Aggregate Preflight`
Intended release date: 2026-05-22

## Package Scope

This is a coordinated release for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.17.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Added high-confidence EF Core misuse analyzer diagnostics `DMV1910` and `DMV1911` for generated DVault shared-type table exposure and direct generated-table writes.
- Added the opt-in runtime `UseDataVaultSaveChangesGuardInterceptor(...)` for warning or blocking unsafe generated-row `SaveChanges` patterns without changing the default `AddDVault()` registration.
- Added snapshot-model drift preflight through `DataVaultModelDriftPreflightReporter.Compare(...)`, keeping snapshot acquisition consumer-owned and avoiding an EF `ModelSnapshot` public contract.
- Strengthened migration guardrail reporting through `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)`, including per-operation `Safe`, `Risky`, and `Incompatible` outcomes.
- Expanded provider explainability around provider capability profiles, provider-behavior profiles, save strategy diagnostics, read strategy diagnostics, and request-bound read-shape diagnostics.
- Added the aggregate `DataVaultPreflight.Run(...)` facade for consumer-owned validation/provider explain, artifact drift, snapshot drift, migration guardrail, and representative request diagnostics lanes.
- Updated public documentation so v0.17.0 is the current baseline after v0.16.0 telemetry and support-bundle behavior.

## Analyzer Package

`DCoding.Data.DVault.Analyzers` remains developer tooling, not a runtime dependency. Consumer projects should reference it with `PrivateAssets="all"` so analyzer assets stay local to the project that owns DVault Code-First declarations or compile-time mapping declarations:

```xml
<PackageReference Include="DCoding.Data.DVault.Analyzers" Version="0.17.0" PrivateAssets="all" />
```

The v0.17.0 analyzer package keeps the existing selector, duplicate-member, code-fix, and generated-mapper diagnostics and adds the EF Core misuse slice:

- `DMV1910` reports `DbContext` properties or fields that expose source-visible DVault generated shared-type tables as `DbSet<Dictionary<string, object>>`.
- `DMV1911` reports direct mutating calls such as `Add(...)`, `AddRange(...)`, `Update(...)`, `Remove(...)`, or `Attach(...)` on source-visible generated shared-type DVault sets.

The analyzer intentionally does not report arbitrary non-DVault dictionary shared-type tables, documented read-only query shapes over `context.Set<Dictionary<string, object>>(producedName)`, `AsNoTracking()` and compiled-query projections, or a local source scope that visibly opts into `UseDataVaultSaveChangesMetadataInterceptor(...)`. It does not attempt whole-application DI inference, provider-specific SQL validation, runtime migration analysis, or a complete model validator role.

## Runtime SaveChanges Guard

`UseDataVaultSaveChangesGuardInterceptor(...)` is an explicit `DbContextOptionsBuilder` opt-in. `AddDVault()` does not enable the guard, and applications that continue to use `IDataVaultSaveService` as their DVault write boundary do not need to add it.

```csharp
services.AddDbContext<SalesVaultContext>(options => {
  options.UseSqlite(connectionString);
  options.UseDataVaultMetadata(salesVaultMetadata);
  options.UseDataVaultSaveChangesGuardInterceptor(guard => guard.UseBlockingMode());
});
```

Blocking mode throws `DataVaultSaveChangesGuardException` when unsafe generated-row changes are detected before `SaveChanges` persists them. Warning mode invokes the caller-supplied `Action<DataVaultSaveChangesGuardReport>` and allows `SaveChanges` to continue:

```csharp
options.UseDataVaultSaveChangesGuardInterceptor(guard =>
    guard.UseWarningMode(report => Console.Error.WriteLine(report.ToDisplayString())));
```

The guard can coexist with `UseDataVaultSaveChangesMetadataInterceptor(...)`. The metadata interceptor fills missing `LoadTimestamp` and `RecordSource` values on already tracked generated rows; the guard warns or blocks unsafe generated-row changes. Neither interceptor computes hash keys, computes hash diffs, creates generated rows, chooses save ordering, or replaces `IDataVaultSaveService` for ordinary hub, link, and satellite writes.

## Drift And Migration Preflight

The default validation lane remains `IDataVaultDiagnosticsService.Analyze(DbContext)`. It analyzes the configured model and provider explain surface without opening a live database connection.

Reviewed artifact drift remains artifact-versus-design-time-model work. A consumer project that owns a reviewed `dvault.model.v1` JSON artifact should import that artifact with `DataVaultModelArtifactImporter.ImportJson(...)`, project it through the configured context, and compare it with `DataVaultModelDriftReporter.Compare(...)` or through the `drift --artifact <path>` design-time command.

Snapshot-model drift is now documented as an explicit model input. The consumer materializes an `IReadOnlyModel` from its EF snapshot code and passes that model to DVault:

```csharp
using DCoding.Data.DVault;
using Microsoft.EntityFrameworkCore.Metadata;

using var context = new SalesVaultDesignTimeFactory().CreateDbContext(args);
IReadOnlyModel snapshotModel = SalesVaultSnapshotMaterializer.CreateSnapshotModel();

var report = DataVaultModelDriftPreflightReporter.Compare(
    SalesVaultMetadata.CreateModel(),
    context,
    snapshotModel);

Console.WriteLine(report.ToDisplayString());
return report.HasBlockingDifferences ? 1 : 0;
```

DVault accepts the materialized snapshot model. It does not expose EF `ModelSnapshot` as a public contract, discover migrations, scan the repository, or select snapshot files automatically.

Migration guardrails still run after a migration is scaffolded and before it is applied. The report keeps the existing DVM diagnostic catalog and adds operation-level outcome summaries:

```csharp
var baseline = diagnostics.Analyze(context);
var report = DataVaultMigrationOperationDiagnostics.AnalyzeReport(
    baseline,
    migration.UpOperations);

Console.WriteLine(report.ToDisplayString());
return report.HasFindings || !report.IsValid ? 1 : 0;
```

Operation outcomes are:

- `Safe`: no DVM migration guardrail findings were produced for the operation.
- `Risky`: warning-severity DVM findings were produced and should be reviewed before integration.
- `Incompatible`: one or more error-severity DVM findings were produced and should block apply until corrected.

A typical report can show safe created tables, risky renames or index shape changes, and incompatible drops or missing generated technical columns in one deterministic ordered summary. The output is intended for consumer-owned scripts and build logs; it does not run inside `dotnet ef migrations add` or `dotnet ef database update`.

## Aggregate Preflight

`DataVaultPreflight.Run(...)` is a facade over explicit lanes that consumers already own. It produces one `DataVaultPreflightReport` with section status for:

- validation and provider explain diagnostics;
- reviewed artifact drift;
- snapshot-model drift;
- migration guardrail diagnostics;
- representative request-bound save/read diagnostics.

```csharp
using DCoding.Data.DVault;
using Microsoft.EntityFrameworkCore.Migrations;
using Microsoft.Extensions.DependencyInjection;

using var services = new ServiceCollection()
    .AddDVaultSqlite()
    .BuildServiceProvider(validateScopes: true);

var diagnostics = services.GetRequiredService<IDataVaultDiagnosticsService>();
var readDiagnostics = services.GetRequiredService<IDataVaultReadDiagnosticsService>();
using var context = new SalesVaultDesignTimeFactory().CreateDbContext(args);

Migration migration = SalesVaultMigrationResolver.Resolve("AddCustomerProfile");

var report = DataVaultPreflight.Run(
    diagnostics,
    new DataVaultPreflightRequest(context, SalesVaultMetadata.CreateModel()) {
      ReviewedArtifactImport = SalesVaultArtifacts.ImportReviewedModel(),
      SnapshotModel = SalesVaultSnapshotMaterializer.CreateSnapshotModel(),
      MigrationOperations = migration.UpOperations,
      RepresentativeDiagnosticsRequests = [
        new DataVaultPreflightRepresentativeDiagnosticsRequest(
            "latest-profile",
            dbContext => readDiagnostics.Analyze(
                dbContext,
                SalesVaultRepresentativeRequests.CreateLatestProfileRead())),
      ],
    });

Console.WriteLine(report.ToDisplayString());
return report.IsBlocked ? 1 : 0;
```

Optional lanes are skipped when their inputs are omitted. The facade does not discover reviewed artifacts, discover snapshot files, discover migrations, invent representative requests, open live databases by default, execute migrations, apply schema repairs, publish dashboards, or route support-bundle output.

## Provider Explainability And Support Bundles

Provider explainability remains bounded and redacted. Diagnostics and support bundles can expose:

- provider name and selected provider capability profile;
- selected provider-behavior profile and whether provider behavior defaulted;
- save strategy status, selected strategy name, strategy priority, and finite fallback causes;
- read strategy status, selected strategy name, strategy priority, and finite fallback causes;
- request-bound read-shape facts for latest/current/as-of satellite, PIT, and bridge reads, including translated table identity, filter columns, deterministic row-selection rules, expected key/index access paths, and provider fallback caveats.

These surfaces do not include raw SQL, provider query plans, raw request keys, raw hash-key values, as-of values, connection strings, credentials, exception text, or secret-bearing output. `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics` remains the way for application code to include representative request-bound diagnostics in a `dvault.support-bundle.v1` payload without having the generic command runner invent requests.

## Out Of Scope

This release does not add a standalone DVault CLI, `dotnet ef` shim, EF CLI interception, automatic migration execution, automatic migration repair, automatic live-schema gate, automatic snapshot discovery, automatic reviewed-artifact discovery, automatic representative request generation, dashboards, alerting, or support-bundle transport.

This release does not change provider SQL behavior, provider-native save strategy thresholds, telemetry publication behavior, PIT or bridge maintenance orchestration, live-schema reader ownership, package publication mechanics, benchmark evidence, or performance claims.

## Compatibility Notes

- Existing applications that call `AddDVault()` keep the same default registration behavior. The SaveChanges guard, telemetry, support-bundle command execution, and representative preflight diagnostics all require explicit consumer action.
- Existing `IDataVaultSaveService`, `IDataVaultReadService`, PIT maintenance, bridge maintenance, diagnostics, model artifact, live-schema drift, telemetry, and support-bundle APIs remain compatible.
- `UseDataVaultSaveChangesGuardInterceptor(...)` is additive and may be registered beside `UseDataVaultSaveChangesMetadataInterceptor(...)`; their responsibilities remain separate.
- `DataVaultModelDriftPreflightReporter.Compare(...)` uses consumer-supplied `IReadOnlyModel` snapshot input and does not require DVault packages to reference `Microsoft.EntityFrameworkCore.Design`.
- `DataVaultPreflight.Run(...)` is additive. Existing design-time command hosts can keep running `validate`, `drift`, `guardrail`, and `support-bundle` separately.
- Package publication remains manual and coordinated across all seven package ids.

## Known Limitations

- The analyzer package is not a full model validator. It covers the documented Code-First selector diagnostics, duplicate-member diagnostics, bounded code fixes, compile-time mapping declaration diagnostics, and the high-confidence EF misuse slice.
- The runtime guard is opt-in and generated-row focused. It does not make EF entity tracking the default DVault persistence model, compute generated values, or replace explicit save service usage.
- Aggregate preflight is not an orchestration platform. Consumers supply every optional lane and decide how to fail builds or local commands.
- Migration guardrail reports are deterministic library diagnostics over supplied EF migration operations. DVault does not apply migrations, repair migrations, or intercept EF commands.
- Provider explainability and support bundles are redacted explain surfaces, not raw SQL validation or provider-specific tuning promises.
- Live-schema checks still require a consumer-managed database when the chosen provider needs external infrastructure. Non-SQLite checks should remain opt-in operational evidence.
- DVault does not provision Docker containers, databases, users, schemas, credentials, dashboards, metric exporters, support-bundle storage, or ticket attachments.
