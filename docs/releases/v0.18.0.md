## EF Compiled Compatibility

The compiled-model, compiled-query, and pooled-context evidence is intentionally bounded to the SQLite local compatibility and performance baseline documented in [DVault EF Compiled Compatibility](../architecture/dvault-ef-compiled-compatibility.md). DVault does not ship a compiled-model generator, EF design-time service, provider-specific compiled-model tooling, or provider matrix for compiled models, compiled queries, or pooled contexts.

The root benchmark summary records these SQLite rows:

- `compiled-model-startup` compares ordinary DVault model building with a precomputed EF runtime model supplied through `UseModel(runtimeModel)`. The measured rows cover consumer-owned runtime-model usage where runtime-model creation is outside the measured operation.
- `compiled-query-hub-read` compares an ordinary direct EF projection with `EF.CompileQuery(...)` over a generated `HubOrder` shared-type table. The supported shape is a stable direct EF expression using generated table names, `EF.Property<T>(...)`, scalar parameters, and deterministic projection.
- `dbcontext-pooling-dvault-operation` compares `AddDbContext<TContext>` with `AddDbContextPool<TContext>` for an options-only context, one fixed metadata source, one fixed model shape, SQLite provider options, and a generated order hub save/read operation.

Consumers should keep dynamic `IDataVaultReadService` request APIs as the default path for runtime-built reads. Compiled queries are appropriate only when table names, column names, filter shape, ordering, and projection are stable at compile time except for scalar parameters. Pooled contexts require one fixed metadata/model shape for the pooled context type; tenant, schema, naming, provider, or profile discriminators that affect the EF model remain caller-owned model-cache-key and pooling responsibilities.

## Read And Save Tuning Evidence

Provider-neutral read allocation work is represented by `latest-satellite-read`, `pit-as-of-read`, and `bridge-traversal-read` rows in the root benchmark triplet and the `06F492CAB2293R7BGJWMWMRKT4-provider-neutral-read-allocations` bundle. The release claim is bounded to the request-bound read-shape diagnostics and measured benchmark rows. It is not a raw-SQL advisor, automatic-index advisor, or physical-plan promise for every provider.

Explicit-save change-tracker tuning is represented by the `customer-profile-history`, `customer-profile-bulk-insert-only`, `customer-profile-bulk-history`, and `order-product-fulfillment-history` rows plus the `06F492CFSJHN0RGXXRG3KT63FM-explicit-save-change-tracker` bundle. The after-tuning evidence records allocation improvements for targeted provider-neutral fallback paths while keeping non-target SQLite rows and optional-provider skip rows visible.

Provider-optimization regression baselines are represented by `provider-native-bulk-ingestion` rows and the `06F492CTREZEDXVKJ839YGCPWW-provider-optimization-regression-baselines` bundle. PostgreSQL, SQL Server, MySQL, and Oracle rows remain part of the artifact set as completed rows when configured or skipped rows when not configured. Skipped optional providers are not silently removed from the evidence.

## Query-Shape Guidance

Query-shape tuning guidance comes from `IDataVaultReadDiagnosticsService` request-bound read diagnostics and the additive `ReadShape` payload. That surface describes translated table identity, filter columns, deterministic row-selection and ordering rules, expected key/index access paths, and provider fallback caveats for representative latest/current/as-of satellite, PIT as-of, and bridge read requests.

The diagnostics output is deterministic and redacted. It does not include raw SQL, provider query plans, raw request keys, hash-key values, as-of values, credentials, connection strings, or automatic index recommendations. SQL capture is required only when a performance claim depends on emitted SQL shape, index usage, batching behavior, or materialization behavior. The compiled-model, compiled-query, and pooled-context rows in this release are timing and allocation evidence only, so they do not require companion SQL captures.

## Compatibility Notes

- Existing applications that call `AddDVault()` keep the same default registration behavior. Compiled-model usage, compiled queries, context pooling, telemetry, support bundles, runtime guards, and representative preflight diagnostics all require explicit consumer action.
- Existing `IDataVaultSaveService`, `IDataVaultReadService`, PIT maintenance, bridge maintenance, diagnostics, model artifact, live-schema drift, telemetry, support-bundle, analyzer, and generated-mapper APIs remain compatible.
- `UseModel(runtimeModel)` is consumer-owned EF runtime-model usage after DVault metadata has already been projected into the design model.
- EF compiled queries are consumer-authored stable EF expressions over generated shared-type tables. DVault does not compile dynamic read request objects or arbitrary projector delegates.
- `AddDbContextPool<TContext>` remains limited to fixed metadata/model shapes that obey EF Core model-caching rules.
- Package publication remains manual and coordinated across all seven package ids.

## Known Limitations

- The SQLite benchmark rows are the required local evidence baseline. They do not assert provider-specific SQL shape, index usage, batching behavior, generated compiled-model code ownership, dynamic request-built read compilation, or pooling for caller-owned variable model shapes.
- PostgreSQL, SQL Server, MySQL, and Oracle provider-native benchmark lanes are optional external-provider lanes. When they are not configured, their rows must remain visible as skipped with normalized skip reasons.
- Query-shape diagnostics are explainability and tuning guidance. They do not emit raw SQL, create indexes, inspect provider physical plans, or promise provider-specific physical layout.
- SQL capture is not required for every performance row. It is required only when the claim depends on SQL shape, index usage, batching behavior, or materialization behavior.
- DVault still does not ship release automation, publish packages automatically, provide package credentials, or replace the final approval record required by `docs/manual-nuget-publication.md`.
