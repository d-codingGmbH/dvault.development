# DVault v0.50.0 Release Notes

Release: `v0.50.0 - Analyzer Compatibility and Adoption Hardening`
Release date: 2026-06-29

These notes record the coordinated v0.50.0 analyzer compatibility, privacy adoption diagnostics, hash-key storage migration manifest validation, documentation, validation, and package-line baseline for DVault. The public release label maps to the consumer package versions `8.50.0` and `10.50.0`. There is no consumer-facing `0.50.0` package version.

## Package Lines

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.50.0` | `net8.0` | EF Core 8 |
| `10.50.0` | `net10.0` | EF Core 10 |

Use exactly one line in a consumer project. Do not mix `8.50.0` and `10.50.0` packages in one project, install example, restored target, or publish approval.

## Analyzer Compatibility Baseline

`DCoding.Data.DVault.Analyzers` remains a local build-time package reference with `PrivateAssets="all"`. The current analyzer package ships one `net10.0` analyzer asset for both visible package lines, and supported analyzer consumption uses a `.NET 10 SDK` build host, including `net8.0` projects that select the `8.50.0` package line.

v0.50.0 keeps that boundary explicit instead of claiming a separate pure `.NET 8 SDK` analyzer host. The analyzer package compatibility audit, package verifier guardrails, packaged README guidance, smoke coverage, and local validation docs all preserve the same support statement: consumers can target `net8.0` with the `8.50.0` line, but analyzer execution is validated through a `.NET 10 SDK` build host.

## Privacy Adoption Diagnostics

v0.50.0 hardens the optional privacy adoption proof without turning privacy into automatic runtime behavior:

- `DataVaultPrivacyDiagnostics` now carries provider-native encryption boundary facts, privacy key-provider posture, encrypted-payload alias coverage facts, and personal-data coverage facts in the redacted diagnostics surface.
- `IDataVaultPrivacyAliasCoverageProvider` and `DataVaultPrivacyAliasCoverageReport` make registered encrypted-payload aliases reviewable against the EF model without querying a database.
- `DataVaultProviderNativeEncryptionBoundaryFact` records that SQL Server, PostgreSQL, Oracle, MySQL, SQLite, and DB2 native encryption capabilities are guidance-only and unmanaged by DVault until a future provider-specific capability owns one exact behavior.
- Personal-data preflight remains fail-closed when a marked payload has no usable privacy proof or observable converter coverage.

The diagnostics are model and configuration evidence only. They do not emit provider-native encrypted DDL, call provider SQL crypto functions, probe database encryption capabilities, manage keys, shred data, delete rows, rewrite historical satellite values, or provide a GDPR/DSGVO compliance attestation.

## Hash-Key Storage Migration Manifest Validation

Binary-first remains the recommended physical storage profile for new schemas. Existing persisted `HexString` storage stays compatible until an application owner plans a separate migration, reset, or data-move change.

v0.50.0 adds a review-only validation lane for generated `dvault.hash-key-storage-migration.v1` dry-run manifests:

- `DataVaultHashKeyStorageMigrationManifestValidator.ValidateJson(...)` validates manifest structure, schema version, provider and capability facts, source and target storage profiles, source-fingerprint facts, hash-key and participant-reference coverage, store type and CLR type facts, stable-hash algorithm facts, digest length, and lowercase hex digest encoding.
- `DataVaultHashKeyStorageMigrationValidationResult` and `DataVaultHashKeyStorageMigrationValidationFinding` expose error, warning, and informational findings without exposing raw manifest payload values.
- `DataVaultPreflightRequest.HashKeyStorageMigrationManifestJson` plugs the same manifest validation into `DataVaultPreflight.Run(...)`; error findings block the section, warning-only findings stay reviewable but non-blocking.

The lane validates a reviewed migration plan only. DVault does not run DDL or DML, apply migrations, backfill keys, dual-write, repair schemas, reconcile rows, rehash values, or automatically rewrite persisted hash keys.

## Package Verification

`bash tools/pack-release-packages.sh` creates the coordinated package artifacts under `artifacts/packages/` for both visible package lines. `bash tools/verify-packages.sh` validates the expected package counts, package ids, versions, filenames, metadata, README install guidance, XML documentation, analyzer assets, provider dependencies, DB2 dependency alignment, EF Core dependency lines, symbol packages, and stale package artifacts.

Package verification preserves the stale-version guardrails for current-package guidance. Packaged README install guidance must not publish `0.50.0` from the release label, must not use stale `8.49.0` or `10.49.0` package lines, must not mix the `8.50.0` and `10.50.0` lines, and must retain the `.NET 10 SDK` analyzer build-host guidance.

Package creation and verification do not imply signed NuGet publication or final publish approval.

## Validation

The release validation lane is:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/verify-packages.sh
bash tools/check-format.sh
```

The local validation baseline requires a .NET 10 SDK checkout. Helper projects may stay on `net10.0`; the packaging lane proves the consumer `net8.0` and `net10.0` package outputs.

## Non-Goals

v0.50.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.50.0 does not define a consumer-facing `0.50.0` package version. Consumers should use the target-specific `8.50.0` or `10.50.0` package line.

v0.50.0 does not add provider performance claims, provider performance benchmark evidence, provider provisioning, broader analyzer compatibility claims, pure `.NET 8 SDK` analyzer support, automatic privacy execution, provider-native encryption behavior, automatic hash-key migration execution, dependent child key modeling, model-first same-hub typed mapper generation, effectivity-specific fluent APIs, implicit persistence, or automatic PIT or bridge maintenance.
