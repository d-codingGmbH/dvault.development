Release: `v0.11.0 - Design-Time Commands and Provider Drift Readers`
Intended release date: 2026-05-16

## Highlights

- Added the reusable design-time command surface exposed by `DataVaultDesignTimeCommand` and `DataVaultDesignTimeCommandHost`.
- Documented the supported command verbs for consumer-owned command hosts: `validate`, `export`, `drift`, and `guardrail`.
- Kept the EF design-time boundary explicit: DVault does not ship a standalone CLI, does not intercept `dotnet ef`, does not apply migrations, and does not repair schema drift automatically.
- Clarified that `drift --artifact <path>` is the default blocking artifact-versus-design-time-model gate when a reviewed `dvault.model.v1` artifact exists.
- Clarified that `export` is for artifact maintenance and reviewed refresh workflows, not the default blocking CI gate.
- Added built-in live-schema reader dispatch for SQLite, PostgreSQL, SQL Server, Oracle, and MySQL.
- Mapped both `MySql.EntityFrameworkCore` and `Pomelo.EntityFrameworkCore.MySql` to the built-in MySQL live-schema reader.
- Refreshed README, quickstart, production-adoption, and model-first governance guidance for the v0.11.0 public baseline.

## Design-Time Command Surface

DVault provides reusable library-hosted command plumbing that applications can invoke from a small executable entrypoint in the project that owns the configured `DbContext`, migrations, design-time factory, and metadata source:

```sh
dotnet run --project <consumer-project> -- validate
dotnet run --project <consumer-project> -- export --output <path>
dotnet run --project <consumer-project> -- drift --artifact <path>
dotnet run --project <consumer-project> -- guardrail --migration <name>
```

`validate` runs DVault diagnostics against the configured design-time model. `export` writes canonical `dvault.model.v1` JSON from the command host's configured export source. `drift` imports a reviewed artifact and compares it against the configured design-time model by default. `guardrail` evaluates scaffolded EF migration operations before the migration is applied.

The command host is application code. DVault does not provide `IDesignTimeServices`, a custom `dotnet ef` shim, automatic EF command interception, automatic migration execution, or automatic schema repair.

## Drift Lanes

The default drift lane is metadata-only:

```sh
dotnet run --project <consumer-project> -- drift --artifact <path-to-reviewed-artifact>
```

This gate fails when the artifact cannot be imported or when the configured design-time model has blocking differences from the reviewed artifact. If a project has not adopted a reviewed artifact, keep this lane skipped until that artifact exists. Do not generate a fresh artifact with `export` and compare against that generated output as the default CI gate.

Live-schema drift remains opt-in and separate:

```sh
dotnet run --project <consumer-project> -- drift --artifact <path-to-reviewed-artifact> --live-schema
```

`DataVaultLiveSchemaReader.ReadAsync(context)` reads a bounded live snapshot of DVault-owned tables, ordered columns, named primary-key constraints, and secondary indexes. It does not compare foreign keys, arbitrary non-DVault database objects, destructive migration plans, or repair operations.

## Built-In Live-Schema Readers

The built-in reader dispatch covers these EF Core provider names:

- `Microsoft.EntityFrameworkCore.Sqlite`
- `Npgsql.EntityFrameworkCore.PostgreSQL`
- `Microsoft.EntityFrameworkCore.SqlServer`
- `Oracle.EntityFrameworkCore`
- `MySql.EntityFrameworkCore`
- `Pomelo.EntityFrameworkCore.MySql`

SQLite remains the default local live-schema proof because it does not require external infrastructure. PostgreSQL, SQL Server, Oracle, and MySQL live-schema checks require consumer-managed reachable databases, connection strings, credentials, lifecycle cleanup, and CI isolation. Keep those external provider live checks opt-in and operationally managed by the consuming application.

Providers without a built-in reader return `DataVaultLiveSchemaReadStatus.UnsupportedProvider`. A recognized provider whose database cannot be reached returns `DataVaultLiveSchemaReadStatus.Unavailable`. Both outcomes are stable drift evidence instead of silent passes.

## Compatibility Notes

- Existing Code-First, metadata-first, and model-first declaration paths remain additive alternatives for different ownership needs.
- Existing `IDataVaultSaveService`, typed read helpers, provider save strategies, model-first governance APIs, analyzer diagnostics, and opt-in `SaveChanges` metadata interceptor behavior remain compatible.
- Provider packages still depend on the aligned `DCoding.Data.DVault` package version.
- The analyzer package remains optional developer tooling and should usually be referenced with `PrivateAssets="all"`.
- The design-time command surface is reusable library code, not a standalone executable package.
- Built-in external provider live-schema readers do not provision databases, manage secrets, run containers, or make provider integration checks part of default local validation.

## Known Limitations

- Startup-project and target-project splits for design-time discovery remain outside the documented v1 workflow.
- DVault does not provide a first-party `dotnet ef` command shim, EF CLI interception, automatic migration execution, or automatic schema repair.
- `export` does not replace reviewed artifact governance and should not be the default blocking CI gate.
- Live-schema readers are bounded to DVault-owned table, column, primary-key, and index metadata.
- Runnable non-SQLite live-schema walkthroughs, provider-specific secret-management recipes, and container-provisioning guides are not included in this release note.
