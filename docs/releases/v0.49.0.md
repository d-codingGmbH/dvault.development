# DVault v0.49.0 Release Notes

Release: `v0.49.0 - Modeling and Generator Parity Refinement`
Release date: 2026-06-28

These notes record the coordinated v0.49.0 modeling, generator, diagnostics, documentation, validation, and package-line baseline for DVault. The public release label maps to the consumer package versions `8.50.0` and `10.50.0`. There is no consumer-facing `0.49.0` package version.

## Package Lines

| Package version line | Target framework | EF Core line |
| --- | --- | --- |
| `8.50.0` | `net8.0` | EF Core 8 |
| `10.50.0` | `net10.0` | EF Core 10 |

Use exactly one line in a consumer project. Do not mix `8.50.0` and `10.50.0` packages in one project, install example, restored target, or publish approval.

## Same-Hub Mapper Parity

v0.49.0 closes the bounded generated mapper gap for repeated same-hub links:

- Generated link mappers now bind exact produced participant names instead of assuming participant hub names are unique.
- Ordinary distinct-hub links continue to use hub names as produced participant names.
- Repeated same-hub links are supported only when every binding supplies a distinct explicit role-bearing produced participant name, such as `SourceCustomer` and `MatchedCustomer`.
- Ambiguous declarations that reuse the same produced participant name still fail deterministically through `DMV1955`.
- Generated same-hub link mappers remain thin `IDataVaultLinkMapper<TSource>` implementations and still flow through the existing explicit `IDataVaultSaveService` path with caller-supplied load timestamp and record source.

The previous `ParticipantHubNames` generated helper member is retained as an alias for compatibility; new generated code also exposes `ProducedParticipantNames` to describe the actual contract.

## Support-Bundle Facts

Diagnostics and support-bundle explain output now include ordered `linkParticipants` facts for link entities:

- `hub` records the participant hub metadata name.
- `name` records the exact produced participant name.
- `role` is omitted for ordinary distinct-hub participants and populated for role-bearing same-hub participants.
- `producedName`, `columnName`, and `ordinal` keep the generated EF mapping traceable without exposing raw request values.

These facts make repeated same-hub roles reviewable by support-bundle-driven tooling. They do not create raw model-first mapper generation, provider-specific SQL, implicit persistence, or runtime inference beyond the existing projected metadata.

## Hash-Key Storage Migration Validation

Binary-first remains the recommended physical storage profile for new schemas only. Existing persisted `HexString` storage remains compatible until the application owner plans a separate migration, reset, or data-move change.

For existing persisted `HexString` storage, route through the reviewed dry-run path before changing EF migrations or data:

- Capture a redacted `dvault.support-bundle.v1` or equivalent translated EF metadata baseline from the current configured application.
- Run the consumer-owned `hash-key-storage-migration` design-time command to export a `dvault.hash-key-storage-migration.v1` manifest.
- Validate and review the manifest with `DataVaultHashKeyStorageMigrationManifestValidator.ValidateJson(...)` directly or by supplying it to the optional `DataVaultPreflight.Run(...)` hash-key storage migration manifest lane.
- Treat structural or compatibility errors as blocking. Warning-only manifests are non-structural and still require review.

The manifest checks the reviewed source facts against the current design-time model: provider and capability profile, metadata source fingerprint, complete `HashKey` and `ParticipantReference` coverage for hubs, links, satellites, PITs, and bridges, source `HexString` to target `Binary` storage-profile facts, provider store type and value format, EF CLR model type, conversion behavior, stable-hash `algorithmId`, digest byte length, and `lowercase-hex-no-prefix` digest encoding.

The validation lane is review-only. DVault does not apply migrations, run DDL or DML, backfill keys, dual-write, repair schemas, reconcile rows, rehash values, or automatically rewrite persisted hash keys.

## Adjacent Modeling Decisions

The dependent child key feasibility tickets intentionally defer first-class dependent child key modeling for the current DVault surface. v0.49.0 does not add a new metadata concept, parent-reference kind, fluent builder, `dvault.model.v1` section, save/read API, migration behavior, or support-bundle shape for dependent child keys.

Effectivity remains the existing caller-owned link-parent satellite pattern. No effectivity-specific fluent API or table family is added in this release.

## Validation

The release validation lane is:

```sh
dotnet build DVault.slnx --nologo
dotnet test DVault.slnx --nologo
bash tools/pack-release-packages.sh
bash tools/verify-packages.sh
bash tools/check-format.sh
```

Package validation checks the expected `8.50.0` and `10.50.0` artifact set, package metadata, dependency groups, analyzer asset placement, XML documentation, symbol packages, README installation guidance, and stale-version guardrails. Package creation and verification do not imply signed NuGet publication.

## Non-Goals

v0.49.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.49.0 does not define a consumer-facing `0.49.0` package version. Consumers should use the target-specific `8.50.0` or `10.50.0` package line.

v0.49.0 does not add dependent child key modeling, model-first same-hub typed mapper generation, effectivity-specific fluent APIs, implicit persistence, automatic PIT or bridge maintenance, provider-specific SQL for same-hub mappers, automatic hash-key migration execution, automatic privacy execution, provider provisioning, or broader analyzer compatibility claims.
