# DVault v0.42.0 Release Notes

Release: `v0.42.0 - Provider Performance Evidence and Tuning`
Release date: 2026-06-20

These notes define the coordinated v0.42.0 package, evidence, and documentation baseline for DVault. The public release label maps to the consumer package versions `8.42.0` and `10.42.0`. The release fixes the provider evidence promotion rules for completed timing, skipped guidance rows, diagnostics-only posture, smoke-only posture, and provider-neutral fallback while keeping DVault inside the existing EF Core library, explicit save/read service, provider-strategy, diagnostics, and benchmark-evidence boundary.

This release note does not record a NuGet push, package hashes, package-signing approval, release automation, stored-procedure deployment, runtime SQL artifact dispatch, automatic PIT or bridge maintenance, or widened provider capability guarantees. It records the scoped MySQL latest-satellite provider-configured benchmark triplet as evidence for the current optimized path, without claiming a provider-neutral fallback improvement comparator, and records the SQL Server bulk-threshold and DB2 hotspot provider-configured benchmark bundles only for their accepted scenario boundaries.

## Evidence Promotion Rules

Provider evidence claims must cite the canonical matrix row identity: `scenario`, `provider`, `baseline`, and `posture`. A row counts as measured timing only when a provider-configured benchmark artifact triplet completed that row and preserves the run context. Skipped placeholders, diagnostics-only rows, smoke-only rows, storage-footprint rows, and gap-matrix recommendations do not become completed timing evidence.

The root `benchmark-summary.md`, `benchmark-summary.csv`, and `benchmark-summary.json` triplet remains the quick SQLite and skipped optional-provider baseline. PostgreSQL, SQL Server, MySQL, Oracle, and DB2 guidance rows stay visible when their matching `DVAULT_TEST_*` connection string is unset, but those rows remain `executionStatus=skipped`, `iterations=0`, and `persistedOutcome=not executed`.

PostgreSQL, SQL Server, MySQL, and Oracle PIT/bridge completed timing remains accepted only through the checked-in v0.32.0 smoke-read bundle. SQLite remains the optimized latest-satellite provider row with completed timing in the root benchmark triplet. MySQL latest-satellite completed timing is accepted only through the checked-in ticket `06FE4QQ9VF7B74E60CXEHSS5XW` bundle, where `MySqlDataVaultReadStrategy` was selected for the supported current window-function path; that bundle does not by itself claim a provider-neutral fallback improvement comparator. SQL Server provider-native bulk timing is accepted only through the configured 2026-06-20 SQL Server bulk-threshold bundle, and its incidental latest-satellite row remains out of scope. DB2 clean-context optimized save plus supported latest-satellite/PIT/bridge completed timing is accepted only through `artifacts/benchmarks/06FE4QR3DD7EFZ4F35SBTFGWSR-db2-hotspot-evidence-20260620/benchmark-summary.*`. The additional host-to-Podman DB2 validation bundle at `artifacts/benchmarks/06FE4PMQ8GNKY6X54F8D16AVGC-db2-host-podman-validation-20260621/benchmark-summary.*` repeats the same scoped DB2 lanes as release validation evidence and does not widen the accepted DB2 boundary. PostgreSQL, SQL Server, and Oracle latest-satellite rows are strategy-registration, diagnostics, smoke, or skipped-placeholder guidance until provider-configured timing lanes exist.

DB2 remains narrower than the other provider follow-ups. DB2 completed timing is limited to the DB2 hotspot bundle's clean-context optimized save and supported latest-satellite/PIT/bridge rows. Staged DB2 bulk, provider-native chunk execution, dirty-context saves, unsupported latest-satellite shapes, stale PIT/bridge maintenance, incomplete read-shape evidence, and DB2 live-schema timing evidence remain out of scope.

## Provider Tuning Gates

The v0.42.0 starting boundaries are gates, not universal performance promises:

| Provider | Starting gate | Stop or fallback boundary |
| --- | --- | --- |
| PostgreSQL | Retain direct or UNNEST below 60 operations; use staged COPY at 60-plus operations. | Stop when the connection string is unset, the context is dirty, provider diagnostics do not select the strategy, or a provider-configured artifact triplet is missing for the timing claim. |
| SQL Server | Native bulk starts at 100-plus total operations; mixed hub/link batches start at 900-plus total operations; no more than 500 satellite operations. | Stop when the connection string is unset, the context is dirty, operation count is below 100, mixed hub/link batches are below 900 total operations, satellite count exceeds 500, or diagnostics do not select `SqlServerDataVaultSaveStrategy`. |
| MySQL | Retain multi-row behavior below 100 operations; staged bulk is bounded to satellite-only 100-plus batches or mixed 100-to-303-operation batches; mixed hub/link batches above 303 operations deliberately return to provider-neutral fallback; tiny satellite-history fallback remains provider-neutral. | Stop when the connection string is unset, the context is dirty, candidate gates decline, the mixed batch exceeds the staged window, diagnostics do not show the expected fallback or selected strategy, or the row is only a skipped placeholder. |
| Oracle | Direct optimized batching starts at 50-plus total operations and no more than 10000 satellite operations. | Stop when the connection string is unset, the context is dirty, operation count is below 50, satellite count exceeds 10000, diagnostics do not select the strategy, or a staged Oracle claim lacks new evidence. |
| DB2 | Clean-context set-based save only. | Stop when the DB2 connection string is unset for a new run, the context is dirty, diagnostics do not select `Db2DataVaultSaveStrategy`, the timing claim does not cite the DB2 hotspot bundle, or the proposed work needs staged DB2 bulk, provider-native chunk execution, unsupported read shapes, stale read-model maintenance, incomplete read-shape evidence, or DB2 live-schema timing/provisioning guarantees. |

Latest-satellite tuning remains limited to PostgreSQL, SQL Server, MySQL, Oracle, and DB2 provider packages and the already documented supported hub-parent, non-multi-active shapes. Unsupported providers, unsupported latest-satellite or PIT/bridge shapes, incomplete read-shape evidence, stale PIT or bridge maintenance, provider mismatches, and diagnostics that do not select the provider strategy fall back to provider-neutral read behavior.

## Limitations And Non-Goals

v0.42.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.42.0 does not define a consumer-facing `0.42.0` package version. Consumers should use the target-specific `8.42.0` or `10.42.0` package line.

v0.42.0 does not change the stable hash algorithm default, binary hash-key storage contract, analyzer target-framework boundary, package dependency matrix, or public save/read API.

v0.42.0 does not create external-provider benchmark artifact triplets beyond the scoped MySQL latest-satellite bundle, the configured SQL Server bulk-threshold bundle, and the checked-in DB2 hotspot bundle; it also does not create completed non-SQLite latest-satellite timing beyond the MySQL scoped row and DB2 supported hotspot row, staged DB2 bulk, provider-native chunk execution, automatic PIT or bridge maintenance, provider-specific physical-design promises, deployable provider-specific SQL runtime dispatch, or universal provider performance guarantees. The MySQL latest-satellite row is a completed optimized timing baseline, not a provider-neutral fallback improvement claim. Future provider read or bulk optimizations must add their own diagnostics-selected behavior and preserved benchmark evidence before documentation can promote them from recommendation to completed timing claim.
