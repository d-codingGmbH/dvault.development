## Highlights

- Promoted the existing public `DataVaultBulkSaveRequest` path as the documented release baseline for ordered explicit bulk saves through `IDataVaultSaveService.SaveAsync(DbContext, DataVaultBulkSaveRequest)`.
- Reconfirmed registry-backed bulk-save adaptation through `DataVaultRegistryBulkSaveRequest`, so shared metadata registries can construct the same ordered explicit batch shape.
- Kept provider-neutral fallback as the guaranteed persistence baseline when no provider strategy is registered or an optimized strategy declines the current context and request batch.
- Extended provider-native bulk-ingestion proof for PostgreSQL, SQL Server, MySQL, and Oracle as opt-in external-provider evidence behind the existing `DVAULT_TEST_*_CONNECTION_STRING` lanes.
- Added diagnostics-visible native-save gates for provider-specific bulk dispatch so applications can explain why a provider strategy was selected or why fallback was used.
- Expanded benchmark evidence around provider-native bulk ingestion while keeping machine, provider, execution status, and skipped-row context attached to reported timings.
- Refreshed README, quickstart, analyzer-package, architecture, model-first, and benchmark guidance for the `0.14.0` public baseline.

## Explicit Bulk Ingestion

`IDataVaultSaveService` remains the public write boundary. Single-request saves still use `DataVaultSaveRequest`, and loaders that already have ordered source batches use a `DataVaultBulkSaveRequest` with the same service:

```csharp
var result = await saveService.SaveAsync(
    context,
    new DataVaultBulkSaveRequest(
        [
            hubRequest,
            linkRequest,
            firstSatelliteRequest,
            changedSatelliteRequest,
        ]),
    cancellationToken);
```

The ordered batch keeps caller-supplied load timestamps, record sources, hub operations, link operations, and satellite operations explicit on each contained request. The default writer processes the batch deterministically and keeps latest satellite HashDiff state in memory across the ordered requests, so unchanged replay operations in the same bulk request can be skipped without requiring callers to collapse their source batches first.

Registry-backed callers can use `DataVaultRegistryBulkSaveRequest` when a `DataVaultMetadataModel` or `DataVaultMetadataRegistry` is the authoritative metadata source. The registry adapter resolves logical names once and delegates to the same explicit bulk pipeline; it does not hide timestamps, record sources, provider selection, or save ordering.

## Provider-Native Bulk Boundaries

Provider-specific save strategies remain optimizations around the same explicit save contract. The core package dispatches registered strategies in deterministic priority order and uses the provider-neutral writer when every strategy declines.

The shipped provider-native eligibility boundary is intentionally visible through `IDataVaultDiagnosticsService`:

- The DbContext must have a clean change tracker.
- The batch must not contain multi-active satellite operations.
- Provider-name matching must identify the selected EF Core provider.
- SQL Server native dispatch requires at least `50` total hub, link, and satellite operations and accepts at most `500` satellite operations.
- MySQL native dispatch requires at least `50` total operations and matches both `Pomelo.EntityFrameworkCore.MySql` and `MySql.EntityFrameworkCore`.
- Oracle native dispatch requires at least `50` total operations.

PostgreSQL and SQLite keep their existing provider-specific save strategies. SQL Server, MySQL, and Oracle add threshold-gated native bulk dispatch for clean ordinary hub, link, and satellite batches. Dirty contexts, multi-active satellite batches, provider-name mismatches, below-threshold batches, and SQL Server batches with too many satellite operations decline to the provider-neutral writer instead of changing the public save result contract.

## Benchmark Evidence Boundary

The benchmark harness in `benchmarks/DCoding.Data.DVault.Benchmarks` remains the documentation-ready evidence source. When an output directory is supplied, one run emits:

- `benchmark-summary.md`
- `benchmark-summary.csv`
- `benchmark-summary.json`

The artifacts preserve scenario, provider, baseline, strategy family, dataset size, change ratio, execution status, skip reason, iteration count, mean/min/max milliseconds, persisted outcome, benchmark options, operating-system details, architecture, processor count, .NET runtime details, and optional provider discovery status.

SQLite rows remain the required local benchmark evidence because they use local temporary files. PostgreSQL, SQL Server, MySQL, and Oracle provider-native bulk-ingestion rows are optional external-provider rows. If an optional provider is not configured or unavailable, the artifacts still include skipped rows with `executionStatus` and `skipReason` instead of silently dropping the provider boundary.

Do not copy benchmark timing numbers without the provider identity, execution status, skip status, benchmark options, and machine/runtime context that came from the same artifact set.

## Compatibility Notes

- Existing single-request `DataVaultSaveRequest` calls remain supported.
- Existing metadata-first and model-first registry-backed paths remain supported; the bulk registry adapter remains additive.
- Provider packages continue to register optimizations without replacing the core explicit save API.
- Provider-specific native execution is not guaranteed for every request shape. The provider-neutral writer remains the compatible fallback for unsupported shapes.
- Ordinary EF `SaveChanges` tracking remains separate from DVault persistence. The optional metadata interceptor still fills metadata only for caller-owned generated rows and does not create DVault rows, compute hashes, or replace `IDataVaultSaveService`.
- External-provider tests and benchmarks still require consumer-managed databases, credentials, cleanup, and CI isolation.

## Known Limitations

- DVault does not provision Docker containers, databases, schemas, users, or credentials for provider integration tests or benchmarks.
- Checked-in benchmark result snapshots are not part of this release. Consumers should archive benchmark artifacts generated in their own environment when they need performance evidence.
- Provider-native bulk dispatch declines multi-active satellite batches in this release; those batches remain supported by the provider-neutral writer.
- SQL Server, MySQL, and Oracle native bulk strategies are threshold-gated and may fall back for small batches.
- Non-SQLite provider-specific read optimization is not expanded by this release.
- Runnable quickstarts remain SQLite and PostgreSQL metadata-first examples; a separate bulk-ingestion quickstart is not included.
- Historical release notes remain historical and should not be read as the current package baseline when they describe earlier version scopes.
