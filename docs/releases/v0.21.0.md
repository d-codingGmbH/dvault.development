## Boundary Shift From v0.20.0

v0.20.0 introduced the staged provider bulk-ingestion documentation boundary for eligible materialized ordered saves. That provider-optimized write-path guidance remains the historical source for staged PostgreSQL and MySQL wording, SQL Server native-bulk wording, Oracle direct optimized batching, stored-procedure caveats, and benchmark evidence expectations.

v0.21.0 moves the current public documentation boundary forward for PIT and bridge read models already proven in the repository. It does not add runtime behavior, new public APIs, new maintenance automation, new diagnostic payload shape, or new benchmark artifact schema. The release centralizes the shipped PIT/bridge maintenance, read, diagnostics, and benchmark evidence in [DVault V1 PIT And Bridge Boundary](../architecture/dvault-v1-pit-bridge-boundary.md).

## PIT Read-Model Boundary

PIT-backed reads are read-service helpers over materialized PIT tables. The caller explicitly maintains those tables through `IDataVaultPitMaintenanceService`; reads, saves, EF `SaveChanges`, provider startup, and background work do not refresh PIT rows implicitly.

The supported public PIT boundary is:

- `DataVaultPitMetadata` requests for one generated PIT table at a time.
- `IDataVaultPitMaintenanceService.RebuildAsync(...)` for full recomputation from persisted hub- or link-parent satellite history.
- `IDataVaultPitMaintenanceService.MaintainParentsAsync(...)` for recomputing complete PIT history for explicit parent hash keys, including late-arriving history correction for those parents.
- `DataVaultPitAsOfReadRequest`, `ReadPitRowsAsync(...)`, and `ReadPitAsync(...)` for as-of reads over explicitly maintained PIT rows.
- hub-parent ordinary PITs.
- hub-parent multi-active PITs only when all referenced multi-active satellites share one canonical driving-key name/order family.
- bounded link-parent PITs only when every referenced satellite is unique, non-multi-active, and attached to the same declared link parent.
- registry-backed PIT maintenance resolution through `DataVaultRegistryPitRebuildRequest` and `DataVaultRegistryPitParentMaintenanceRequest`.

The public `dvault.model.v1` PIT artifact shape remains hub-parent-only. Link-parent PIT maintenance and reads are available through the runtime `DataVaultPitMetadata` / registry-backed maintenance path, not through model-first link-parent PIT artifacts. Registry-backed PIT coverage is maintenance-only; v0.21.0 does not document or imply a `DataVaultRegistryPitAsOfReadRequest`.

## Bridge Read-Model Boundary

Bridge-backed reads are read-service helpers over materialized bridge tables. The caller explicitly maintains those tables through `IDataVaultBridgeMaintenanceService`; bridge reads do not infer maintenance, schedule refreshes, or provide a general graph traversal API.

The supported public bridge boundary is:

- `DataVaultBridgeMetadata` requests for one generated bridge table at a time.
- `IDataVaultBridgeMaintenanceService.RebuildBridgeAsync(...)` for full bridge recomputation from persisted source-link rows.
- `IDataVaultBridgeMaintenanceService.MaintainBridgeAsync(...)` for inserting missing rows from current source-link state.
- many-to-many bridges with `From` and `To` endpoint filters.
- hierarchy bridges with `Ancestor` and `Descendant` endpoint filters, bounded `maximumDepth`, and positive `TraversalDepth` values.
- registry-backed bridge maintenance resolution through `DataVaultRegistryBridgeMaintenanceRequest`.

`MaintainBridgeAsync(...)` is not delete-aware. It inserts missing rows and can lower an existing hierarchy `TraversalDepth` when a newly materialized shorter path is available, but it does not remove obsolete rows or increase persisted depths after topology shrinkage. Use `RebuildBridgeAsync(...)` when hierarchy deletions, row removal, or increased `TraversalDepth` must be reflected.

## Read Dispatch And Diagnostics

`AddDVaultSqlite()` is the only repository-proven optimized PIT/bridge read provider path in this release. Supported SQLite PIT and bridge read shapes can select `SqliteDataVaultReadStrategy`. Unsupported providers, unsupported PIT shapes, unsupported bridge shapes, or unregistered provider strategies fall back to provider-neutral read pipelines without changing the public request contract or triggering maintenance side effects.

`IDataVaultReadDiagnosticsService` is the diagnostics surface for read strategy and read-shape evidence. Request-bound diagnostics keep provider strategy selection in `ReadStrategy` and PIT/bridge query-shape facts in `ReadShape` without raw hash-key values, as-of values, request keys, SQL text, or provider query plans.

## Compatibility Notes

Existing callers of `IDataVaultPitMaintenanceService`, `IDataVaultBridgeMaintenanceService`, `IDataVaultReadService`, and `IDataVaultReadDiagnosticsService` remain on the same public service boundaries documented in the README. v0.21.0 documentation does not require callers to change method calls or request types.

Applications that already use PIT or bridge metadata can keep explicit maintenance after ingestion and explicit reads after maintenance. Applications that need shrink-safe bridge recomputation should keep using `RebuildBridgeAsync(...)` for destructive hierarchy changes.

## Limitations

v0.21.0 documentation does not implement automatic PIT maintenance, automatic bridge maintenance, read-time refresh, background scheduling, provider-specific PIT maintenance, provider-specific bridge maintenance, non-SQLite optimized PIT/bridge reads, registry-backed PIT as-of reads, model-first link-parent PIT artifacts, tuple-filter request parameters, cross-product multi-active tuple semantics, delete-aware bridge maintenance, graph traversal APIs beyond the bounded bridge read helpers, effectivity-specific APIs, path payload columns, closure-state columns, or provider-specific physical tuning.

Future work that adds any of those capabilities should land under additive capability tickets and later release notes rather than widening the v0.21.0 boundary retroactively.
