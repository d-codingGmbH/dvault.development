## Async Save API Additions

The v0.24.0 public write surface adds one async chunk-source overload on the existing explicit save boundary:

```csharp
Task<DataVaultSaveResult> SaveAsync(
    DbContext dbContext,
    IAsyncEnumerable<DataVaultSaveChunk> chunks,
    CancellationToken cancellationToken = default);
```

That overload consumes caller-ordered bounded chunks of ordinary `DataVaultSaveRequest` values. It uses the same explicit load timestamp, record source, metadata resolution, hash-key, hash-diff, hub, link, satellite, cancellation, telemetry, and caller-owned transaction rules as the existing `DataVaultSaveRequest`, `DataVaultBulkSaveRequest`, and `DataVaultChunkedSaveRequest` overloads.

The v0.24.0 helper surface also includes async source convenience methods over that same boundary:

- `SaveAsync<TSource>(...)` maps `IAsyncEnumerable<TSource>` values through a caller-owned `Func<TSource, DataVaultSaveRequest>` and buffers at most the caller-supplied `chunkSize`.
- `SaveHubsAsync(...)` maps `IAsyncEnumerable<TSource>` values through `IDataVaultHubMapper<TSource>`.
- `SaveLinksAsync(...)` maps `IAsyncEnumerable<TSource>` values through `IDataVaultLinkMapper<TSource>`.
- `SaveOrdinaryHubSatellitesAsync(...)` maps `IAsyncEnumerable<TSource>` values through `IDataVaultSatelliteMapper<TSource>` for ordinary hub-parent satellites.

All async helpers require an explicit positive `chunkSize`, preserve caller source order, use the same cancellation token for enumeration, mapping, and save execution, and stop at the observed mapping, validation, provider, cancellation, or enumeration failure. Mapper and request-factory failures include the source CLR type and zero-based batch index in the helper exception context while preserving the underlying validation reason.

## Save-Path Selection

Use `DataVaultBulkSaveRequest` when the loader already has the complete ordered request set materialized and memory use is acceptable. This remains the compatibility baseline for ordered explicit bulk saves and the provider-specific optimized batch gates.

Use `DataVaultChunkedSaveRequest` when the loader has already formed bounded materialized `DataVaultSaveChunk` values and needs to preserve explicit load timestamps, record sources, request order, chunk order, cancellation behavior, and caller-owned transaction behavior without pre-buffering the complete logical load as one bulk request.

Use `IDataVaultSaveService.SaveAsync(DbContext, IAsyncEnumerable<DataVaultSaveChunk>, ...)` when the bounded chunk producer is already asynchronous and should be enumerated once in yielded order. Use `SaveAsync<TSource>(...)`, `SaveHubsAsync(...)`, `SaveLinksAsync(...)`, or `SaveOrdinaryHubSatellitesAsync(...)` when source rows are already asynchronous and should be mapped into bounded chunks through the existing explicit save boundary.

Chunked and async source saves remain provider-neutral public behavior. They do not imply provider-native async writes, provider-native chunk execution, hidden background continuation, file ingestion, CDC ingestion, scheduler behavior, hosted worker behavior, or implicit `SaveChanges` streaming. If callers need all-or-nothing behavior across chunks, they should open the transaction before invoking the save service and roll it back when the returned task fails or is canceled.

The detailed contract is [DVault V1 Streaming Explicit Save Contract](../architecture/dvault-v1-streaming-explicit-save-contract.md).

## EF Safety Guidance

EF safety remains guidance-only in v0.24.0 for model-cache, compiled-model, and `DbContext` pooling concerns. The analyzer package does not add model-cache or pooling diagnostic IDs in this release.

Registry-backed `UseDataVaultMetadata(...)` remains the safe built-in baseline for DVault-owned metadata selection. DVault isolates EF model-cache entries for contexts configured with registry-backed metadata by carrying the DVault metadata source kind and deterministic metadata fingerprint in the model-cache key. That covers the app-default registry selected by `UseDataVaultMetadata()`, explicit `DataVaultMetadataModel` and `DataVaultMetadataRegistry` values, and successful model-import results that resolve to a registry before projection.

That built-in isolation does not discover arbitrary caller state. Tenant, schema, naming, provider, profile, constructor, ambient, or branch inputs that change the realized EF model shape remain application-owned `IModelCacheKeyFactory` responsibilities. Use the README section [Isolate EF model cache entries](../../README.md#isolate-ef-model-cache-entries) as the authoritative model-cache guidance.

`UseModel(...)` and `AddDbContextPool<TContext>(...)` are documented as safe only when one fixed realized model shape is in play. Applications that use EF runtime models own the runtime-model creation path and any generated compiled-model artifact. Pooled contexts require one fixed metadata/model shape for the context type and options-only construction. Use [DVault EF Compiled Compatibility](../architecture/dvault-ef-compiled-compatibility.md) for the fixed-model lane.

## Analyzer Surface

The implemented EF misuse analyzer surface remains:

- `DMV1910` for exposing DVault generated shared-type tables as `DbSet<Dictionary<string, object>>` members on a `DbContext`.
- `DMV1911` for direct EF write calls against DVault generated shared-type `DbSet<Dictionary<string, object>>` sets.

Those IDs are shared-type-table misuse guidance. They are not model-cache, compiled-model, or pooling diagnostics. Analyzer documentation should route readers to the README model-cache section and the EF compiled compatibility note for those guidance-only boundaries instead of inventing new diagnostic IDs. The package-local surface remains documented in [DCoding.Data.DVault.Analyzers README](../../src/DCoding.Data.DVault.Analyzers/README.md).

## Compatibility Notes

Existing explicit save and read service boundaries remain compatible. `IDataVaultSaveService` remains the public write boundary for single, ordered bulk, materialized chunked, and async source explicit saves. `DataVaultBulkSaveRequest` remains the compatibility baseline when callers already have a fully materialized ordered batch. `DataVaultChunkedSaveRequest` remains the materialized bounded chunk input shape. `IAsyncEnumerable<DataVaultSaveChunk>` is the async source input shape over the same bounded chunks.

Provider-specific optimized save strategies remain diagnostics-gated implementations behind the same public service contract. PostgreSQL staged COPY, MySQL staged bulk, SQL Server native bulk wording, and Oracle retained direct optimized batching carry forward from the v0.20.0 boundary without new measured external-provider claims in this release.

PIT and bridge maintenance remain explicit caller-owned service boundaries. `IDataVaultPitMaintenanceService` and `IDataVaultBridgeMaintenanceService` do not add automatic scheduling, read-time refresh, delete-aware incremental bridge shrinkage, or provider-specific maintenance strategies. SQLite remains the only repository-proven optimized PIT and bridge read provider path; unsupported providers and unsupported shapes fall back to provider-neutral read pipelines.

Typed satellite read-model generation remains support-bundle-driven and satellite-only. Raw `dvault.model.v1` artifacts remain reviewed workflow inputs, not direct generator inputs. Dynamic `IDataVaultReadService` requests and consumer-owned EF compiled queries remain the documented alternatives outside generated satellite helpers.

Activity tracing remains listener-driven through the `DCoding.Data.DVault` ActivitySource. `AddDVault()` remains telemetry-free by default, and `AddDVaultTelemetry()`, built-in `System.Diagnostics.Metrics`, and `IDataVaultTelemetryObserver` remain sibling opt-in observability surfaces.

The package-family boundary remains the seven package ids listed above, and coordinated publication remains manual.

## Limitations And Non-Goals

v0.24.0 does not implement new analyzer diagnostics, benchmark harness changes, benchmark artifact schema changes, benchmark reruns, package publication, release automation, external-provider measurement claims, provider-native async writes, provider-native chunk execution, ingestion platforms, file ingestion, CDC ingestion, background workers, schedulers, automatic retries, checkpoints, hosted observability, database provisioning, deployment guidance, or credential-management guidance.

It does not make `UseModel(...)` or `AddDbContextPool<TContext>(...)` safe for multiple realized model shapes under one EF cache entry.

This release does not reopen carried-forward compatibility boundaries for explicit save and read services, PIT and bridge maintenance, provider registration, provider package responsibilities, stable hash governance, support-bundle ownership, typed satellite helper generation, Activity tracing, package-family membership, or manual publication separation.
