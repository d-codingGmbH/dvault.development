# DVault v0.45.0 Release Notes

Release: `v0.45.0 - Server-Side PIT and Bridge Maintenance Exploration`
Release date: 2026-06-23

These notes record the coordinated v0.45.0 architecture, documentation, validation, and package-line baseline for DVault. The public release label maps to the consumer package versions `8.45.0` and `10.45.0`. There is no consumer-facing `0.45.0` package version.

This release keeps PIT and bridge read models caller-maintained. Saves, reads, EF `SaveChanges`, provider startup, and background scheduling do not refresh PIT or bridge rows implicitly.

## Exploration Outcome

The accepted PIT maintenance baseline has two provider-specific prototypes with different seams and different eligibility:

- PostgreSQL adds a provider PIT maintenance strategy through `AddDVaultPostgres()`.
- SQL Server replaces the public PIT maintenance service through `AddDVaultSqlServer()`.
- Bridge maintenance push-down remains deferred. `IDataVaultBridgeMaintenanceService` stays provider-neutral, and there is no `IDataVaultProviderBridgeMaintenanceStrategy` seam in this baseline.

Maintained-bridge read timing evidence remains read-side evidence over already-maintained bridge rows. It is not write-side bridge-maintenance push-down proof.

## PIT Maintenance Baseline

| Provider | Registration seam | Provider-maintained full rebuilds | Fallback boundary |
| --- | --- | --- | --- |
| PostgreSQL | `AddDVaultPostgres()` registers `PostgresDataVaultPitMaintenanceStrategy` as an `IDataVaultProviderPitMaintenanceStrategy`. | Clean Npgsql-backed full rebuilds for ordinary hub-parent PITs, shared-driving-key multi-active hub-parent PITs, and link-parent non-multi-active PITs when no caller transaction is already active. | Provider mismatch, dirty tracked contexts, caller transactions, unsupported PIT shapes, and guard failures fall back through provider-neutral PIT maintenance. |
| SQL Server | `AddDVaultSqlServer()` replaces `IDataVaultPitMaintenanceService` with `SqlServerDataVaultPitMaintenanceService`. | Clean SQL Server full rebuilds for ordinary hub-parent PITs only. | `MaintainParentsAsync(...)`, multi-active PITs, link-parent PITs, provider mismatch, dirty tracked contexts, caller transactions without savepoint support, and other guard failures fall back through provider-neutral PIT maintenance. |

PostgreSQL caller transactions fall back with `CurrentTransactionSavepointUnavailable` because the provider strategy does not currently create a strategy-owned savepoint around delete-plus-insert full rebuild work. SQL Server full-rebuild faults and cancellations preserve the pre-rebuild rows instead of leaving partially refreshed PIT data behind. PostgreSQL and SQL Server provider-maintenance paths are explicit caller-invoked maintenance paths; neither provider path adds automatic refresh, scheduling, SaveChanges interception, deployment artifacts, or background orchestration.

## Bridge Maintenance Deferment

Bridge maintenance remains on the provider-neutral `IDataVaultBridgeMaintenanceService` surface:

- `RebuildBridgeAsync(...)` recomputes bridge rows from persisted source-link rows.
- `MaintainBridgeAsync(...)` inserts missing rows from the current source-link state.
- Many-to-many bridge semantics remain one row per distinct endpoint pair.
- Hierarchy bridge semantics remain minimum positive hop count, no implicit self rows, and non-delete-aware incremental maintenance.
- Destructive hierarchy changes that require row removal or increased `TraversalDepth` still require a full bridge rebuild.

Provider-specific bridge maintenance needs a separate core/provider seam, bridge-specific gate and fallback diagnostics, parity coverage for many-to-many and hierarchy semantics, and a preserved provider-configured benchmark artifact triplet before it can be promoted.

## Performance Evidence Boundary

The v0.45.0 PIT maintenance work is not a performance-profile promotion. The source and tests prove provider-maintenance availability and fallback behavior for specific maintenance shapes. They do not provide a completed benchmark timing row for PIT maintenance.

Use [Provider Optimization Evidence Matrix](../plans/provider-optimization-evidence-matrix.md) for provider read and save row identity, posture, artifact source, and stop/fallback conditions. Completed `pit-as-of-read` and `bridge-traversal-read` rows remain read evidence over already-maintained read-model rows, not evidence that provider SQL maintained those rows.

Use [Performance Profiles](../performance-profiles.md) for adopter-facing performance guidance. The v0.45.0 overlay keeps benchmark-backed read evidence separate from PIT maintenance prototype availability and keeps bridge write-side maintenance push-down deferred.

## Limitations And Non-Goals

v0.45.0 does not publish packages, record final publish approval, record package hashes, add package-signing evidence, or add release automation.

v0.45.0 does not define a consumer-facing `0.45.0` package version. Consumers should use the target-specific `8.45.0` or `10.45.0` package line.

v0.45.0 does not add automatic PIT or bridge maintenance, read-time refresh, background scheduling, EF `SaveChanges` interception, deployment artifacts, provider-specific bridge maintenance, bridge-maintenance benchmark lanes, support-bundle orchestration, or provider expansion beyond the current PostgreSQL and SQL Server PIT maintenance prototypes.

v0.45.0 does not promote PIT maintenance push-down into a benchmark-backed performance claim. Future provider-maintenance timing claims need preserved benchmark artifacts with run context, fallback rows, and exact workload shape.
