# DVault v0.8.0 Release Notes

Release: `v0.8.0 - EF Core Lifecycle Guardrails`
Intended release date: 2026-05-13

## Package Scope

This is a coordinated release for the six-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.8.0`. Package publication remains a separate manual release activity; these notes do not record a NuGet push, package hashes, or final publication links.

## Highlights

- Stabilized the EF Core lifecycle guardrail story around existing `DMV####` model and artifact diagnostics plus the DVM2001-DVM2006 migration-operation guardrail catalog.
- Documented deterministic migration preflight through `DataVaultMigrationOperationDiagnostics.Analyze(...)` and `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)`, including stable issue ordering, remediation text, and `DataVaultMigrationGuardrailReport.ToDisplayString()` output.
- Ratified the v1 `dotnet ef` composition boundary as consumer-owned, single-project, and preflight-driven: the application owns the configured `DbContext`, its `IDesignTimeDbContextFactory<TContext>`, and the local DVault preflight entrypoint.
- Kept the DVault package boundary explicit: DVault does not provide `IDesignTimeServices`, does not ship a custom `dotnet ef` shim, does not intercept EF CLI commands, and does not reference `Microsoft.EntityFrameworkCore.Design`.
- Preserved normal EF Core command ownership. Consumers run `dotnet ef migrations add`, run their DVault preflight command against the generated migration operations, and then decide whether to continue with `dotnet ef database update`.
- Documented non-live drift evidence through `DataVaultModelDriftReporter.Compare(...)` against generated or current EF metadata, including design-time metadata shaped by an imported `dvault.model.v1` artifact.
- Documented optional live-schema drift evidence as a separate SQLite-first lane through `DataVaultLiveSchemaReader.ReadAsync(...)` and `DataVaultLiveSchemaDriftReporter.Compare(...)`, with explicit unsupported or unavailable outcomes when live evidence cannot be produced.

## Lifecycle Guardrail Workflow

DVault v0.8.0 keeps lifecycle validation explicit and reviewable before a generated schema change is applied.

Model and artifact validation continues to use stable `DMV####` diagnostics. Model-first artifacts are imported with `DataVaultModelArtifactImporter.ImportJson`, projected into EF metadata through `UseDataVaultMetadata(DataVaultModelImportResult)`, and compared against generated or current EF metadata with `DataVaultModelDriftReporter.Compare(...)`.

Design-time model validation is a consumer preflight step. The consumer-owned entrypoint constructs the same configured context that EF design-time commands use, runs `IDataVaultDiagnosticsService.Analyze(DbContext)`, prints `DataVaultDiagnosticsResult.ToDisplayString()`, and stops the local workflow when validation is invalid. This preflight does not require opening a live database connection.

Migration guardrail validation runs after the migration has been scaffolded and before it is applied. The consumer-owned entrypoint resolves the generated `Migration`, passes its `UpOperations` into `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)`, prints `DataVaultMigrationGuardrailReport.ToDisplayString()`, and stops the local workflow when guardrail findings exist.

## Design-Time Boundary Notes

The supported v1 design-time layout is one project that owns the concrete `DbContext`, DVault metadata registration through `ApplyDataVaultMetadata(...)` or `UseDataVaultMetadata(...)`, the consumer-owned `IDesignTimeDbContextFactory<TContext>`, the consumer-owned preflight entrypoint, and the `dotnet ef` invocation point.

Startup-project and target-project splits, host discovery from a separate executable, and other multi-project design-time layouts remain unsupported in v1. A later ticket may broaden that layout, but v0.8.0 keeps the design-time boundary local to the project that owns the configured context.

The consumer project that runs EF commands may reference `Microsoft.EntityFrameworkCore.Design` as an application dependency. DVault packages remain design-package-free and do not add an EF CLI integration surface.

## Migration Guardrail Notes

The DVM2001-DVM2006 catalog is the stable migration guardrail surface for this release:

- `DVM2001` reports descriptive payload columns added directly to Data Vault hub or link tables.
- `DVM2002` reports required technical column changes such as `LoadTimestamp`, `RecordSource`, satellite `HashDiff`, or PIT load-timestamp mutations.
- `DVM2003` reports Data Vault key or structural shape changes involving hash keys, participant references, parent hash keys, satellite driving keys, PIT snapshot references, or bridge traversal-depth columns.
- `DVM2004` warns when default primary-key or index coverage changes through drops, renames, recreated definitions, uniqueness changes, column-order changes, or target-column changes.
- `DVM2005` warns when Data Vault-owned columns are renamed away from their produced names.
- `DVM2006` reports dropped Data Vault-owned hub, link, satellite, PIT, or bridge tables.

The guardrail report is advisory preflight evidence for the proposed migration operation set. DVault does not apply migrations, rewrite migrations, repair schema drift, or inject guardrail output into EF Core commands.

## Drift Evidence Notes

The non-live drift lane is metadata-based. `DataVaultModelDriftReporter.Compare(...)` compares expected metadata or an imported `dvault.model.v1` artifact with generated or current EF metadata and does not open a database connection. This is the supported lane for design-time review evidence, including ModelSnapshot-style evidence where the current EF model is constructed for comparison.

The live-schema lane is optional and separate. `DataVaultLiveSchemaReader.ReadAsync(...)` captures DVault-owned tables, ordered columns, primary-key constraints, and secondary indexes from a reachable database, and `DataVaultLiveSchemaDriftReporter.Compare(...)` compares that snapshot with expected metadata or an imported model.

SQLite is the supported v1 live-schema reader. Providers without a live reader return `UnsupportedProvider`, and reachable-provider failures return `Unavailable`; requested live checks do not silently pass when evidence cannot be produced.

## Compatibility Notes

- v0.7.0 model-first governance remains compatible. Reviewed `dvault.model.v1` JSON artifacts, `DataVaultModelArtifactImporter.ImportJson`, `UseDataVaultMetadata(DataVaultModelImportResult)`, `DataVaultModelArtifactExporter.ExportJson`, and `DataVaultModelDriftReporter.Compare(...)` remain the documented artifact review surface.
- Code-First declarations remain compatible through `ApplyDataVaultMetadata(vault => ...)` for app-local EF models that fit the implemented fluent hub, hub-parent satellite, multi-active driving-key, and ordered hub-link surface.
- Metadata-first declarations remain compatible through `DataVaultMetadataModel`, `DataVaultMetadataRegistry`, `AddDVault(...)`, and `UseDataVaultMetadata()` when one shared metadata source should drive schema projection, diagnostics, reads, examples, or provider setup.
- The design-time preflight workflow is additive. Existing applications keep normal EF Core ownership of their project layout, EF design package reference, migrations folder, and `dotnet ef` command invocation.
- Migration guardrails inspect proposed EF `MigrationOperation` values. They do not replace code review of generated migration files or normal EF migration history management.
- Live-schema drift evidence remains SQLite-first in this release. Do not cite broader live-schema provider support until repository evidence adds those readers and tests.

## Known Limitations

- No DVault-owned `IDesignTimeServices` integration is delivered in v0.8.0.
- No first-party `dotnet ef` command shim or EF CLI interception is delivered in v0.8.0.
- No automatic migration execution, provider-specific online migration runner, or schema repair workflow is delivered in v0.8.0.
- No automatic guardrail output during `dotnet ef migrations add` or `dotnet ef database update` is delivered in v0.8.0.
- No startup-project or target-project split design-time workflow is delivered in v0.8.0.
- No broad multi-provider live-schema drift reader beyond the SQLite-first lane is delivered in v0.8.0.
- No single operator guide that chains artifact review, metadata or ModelSnapshot comparison, live-schema comparison, migration scaffolding, preflight, and database update is delivered in v0.8.0.
