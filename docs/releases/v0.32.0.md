# DVault v0.32.0 Release Notes

Release: `v0.32.0 - High-Performance Artifact Evidence Lane`
Intended release date: 2026-06-09

These notes define the v0.32.0 coordinated documentation baseline for the high-performance artifact evidence lane visible in the repository. They record the benchmark-driven provider save-threshold evidence, the bounded provider-specific SQL artifact review lane, the consumer-owned design-time command surface, the `dvault.sql-artifact.v1` review manifest contract, the current SQL Server dry-run prototype boundary, and explicit non-goals. They do not record a NuGet push, package hashes, final publication links, release approval, deployable SQL payload generation, runtime artifact dispatch, automatic deployment, automatic migration synchronization, DBA workflow automation, or package-publication automation by themselves. The final approval record described by [Manual NuGet Publication Checklist](../manual-nuget-publication.md#final-approval-record) remains the publication authority before any package is pushed.

## Package Scope

This is a coordinated release record for the seven-package DVault NuGet family:

- `DCoding.Data.DVault`
- `DCoding.Data.DVault.Analyzers`
- `DCoding.Data.DVault.MySql`
- `DCoding.Data.DVault.Oracle`
- `DCoding.Data.DVault.Postgres`
- `DCoding.Data.DVault.Sqlite`
- `DCoding.Data.DVault.SqlServer`

All packages are version-aligned at `0.32.0`. Package publication remains a separate manual release activity.

## Boundary Shift From v0.31.0

v0.31.0 moved the coordinated documentation baseline forward for performance decision-tree guidance, application-owned observability examples, and realistic quickstart evidence. That performance and observability baseline remains intact and historical.

v0.32.0 moves the artifact-lane documentation from future-only non-goal wording to the current bounded dry-run surface and records local Podman-backed provider threshold evidence for PostgreSQL, SQL Server, MySQL, and Oracle. The artifact lane remains inside the existing consumer-owned design-time workflow: the application project that owns the configured `DbContext`, `IDesignTimeDbContextFactory<TContext>`, migrations, metadata source, and DVault command host explicitly opts into artifact generation.

This release does not change the default runtime write or read boundary. `IDataVaultSaveService` and `IDataVaultReadService` remain the runtime surfaces. The artifact lane does not auto-discover, auto-deploy, auto-invoke, auto-register, or replace those services.

## Design-Time Command Surface

The current command surface is:

```sh
dvault sql-artifact --output <path> [--workload provider-native-bulk-ingestion]
```

Consumers normally host that verb through their application project entrypoint:

```sh
dotnet run --project <consumer-project> -- sql-artifact --output <path>
dotnet run --project <consumer-project> -- sql-artifact --output <path> --workload provider-native-bulk-ingestion
```

The emitted manifest schema version is `dvault.sql-artifact.v1`. The default and currently supported workload label is `provider-native-bulk-ingestion`. The output is review-only dry-run evidence, not a deployable runtime lane.

## Current Prototype Boundary

The current visible exporter covers one provider and one workload: SQL Server `provider-native-bulk-ingestion`. It requires request-bound save diagnostics for `Microsoft.EntityFrameworkCore.SqlServer` that select `SqlServerDataVaultSaveStrategy`.

The dry-run manifest records:

- `status=review-only`
- `deployment=not-generated`
- `runtimeDispatch=not-generated`
- `payloadPolicy=manifest-only-no-sidecar-sql`
- benchmark references to `benchmark-summary.md`, `benchmark-summary.csv`, and `benchmark-summary.json`
- semantic-parity notes for ordering, load timestamp, record source, hash key, hash diff, latest-state behavior, cancellation, cleanup, and caller-owned transaction behavior

The repository-wide supported-provider baseline remains SQLite, PostgreSQL, SQL Server, MySQL, and Oracle. The current SQL Server dry-run exporter must not be read as implemented artifact-export coverage for every supported provider.

## Evidence Gate

Artifact-lane and provider-threshold claims stay tied to the exact provider, representative workload, and preserved benchmark run context. Before a manifest or threshold change is treated as release evidence, the adopting workflow must preserve:

- request-bound diagnostics for the same provider and workload;
- benchmark evidence under the shared artifact triplet contract;
- semantic-parity review against explicit DVault save/read behavior;
- skipped optional-provider rows when external provider connection strings are unavailable;
- a consumer-owned migration-compatibility plan.

The root benchmark artifact triplet remains a historical quick evidence surface:

- [benchmark-summary.md](../../benchmark-summary.md)
- [benchmark-summary.csv](../../benchmark-summary.csv)
- [benchmark-summary.json](../../benchmark-summary.json)

Skipped optional-provider rows are visible evidence rows, not completed external-provider measurements. The v0.32 checked-in artifact bundles above record local Podman benchmark measurements where their summaries show `executionStatus=completed`; consumers should rerun locally before copying timing values into their own production records.

## Consumer-Owned Responsibilities

The consuming application owns all operational decisions after generation:

- artifact review, storage, and retention;
- deployment packaging and environment routing;
- invocation and transaction policy;
- versioning, rollback, and cleanup;
- credentials and secret management;
- migration compatibility and model-change review;
- runtime observability, alerting, and failure handling.

DVault supplies the bounded design-time manifest contract and evidence references. It does not take over application operations or DBA workflow ownership.

## Limitations And Non-Goals

v0.32.0 does not add provider support beyond SQLite, Oracle, PostgreSQL, SQL Server, and MySQL. It also does not claim implemented artifact exporters for that full provider baseline; the current dry-run exporter is SQL Server-only for `provider-native-bulk-ingestion`.

v0.32.0 does not add deployable SQL payload files, stored-procedure deployment, automatic artifact discovery, automatic artifact invocation, runtime artifact dispatch, default provider routing, EF `SaveChanges` interception, schedulers, background workers, DBA workflow automation, credential handling, environment routing, automatic cleanup, or automatic rollback.

v0.32.0 does not automatically synchronize artifacts with EF migrations, live schema reads, metadata changes, model-first import/export, support-bundle refreshes, or benchmark artifacts. Consumers own migration compatibility and operational review before using any artifact outside the dry-run review lane.
