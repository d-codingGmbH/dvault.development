# Production Adoption Checklist

Use this checklist when preparing a DVault-consuming application for production. It is a routing document for adopter readiness; follow the linked source documents for setup examples, governance details, migration guardrails, release evidence, and current limitations.

## Package And Provider Baseline

- [ ] Install the provider-neutral `DCoding.Data.DVault` package from NuGet and use the published installation guidance in the [README](../README.md#installation).
- [ ] Select the DVault provider package that matches the application database and keep every DVault package on one aligned published release version.
- [ ] Install `DCoding.Data.DVault.Privacy` only when the application explicitly opts into the optional privacy extension seam. Treat it as a provider-neutral registration and alias-driven encrypted payload conversion proof, not a compliance guarantee, automatic encryption/redaction feature, or provider-native encryption feature.
- [ ] Treat [v0.45.0 release notes](releases/v0.45.0.md) and [Package Compatibility](package-compatibility.md) as the current public documentation baseline for the coordinated package family, the `8.45.0` / `net8.0` / EF Core 8 line, the `10.45.0` / `net10.0` / EF Core 10 line, optional privacy extension boundary, stable hash algorithm-selection guidance, binary hash-key storage opt-in guidance, finite target-specific provider/version matrix, manual publication separation, validation evidence, compatibility caveats, and explicit non-goals.
- [ ] Treat [v0.32.0 release notes](releases/v0.32.0.md) as the historical source for benchmark-driven provider threshold evidence, the review-only provider-specific SQL artifact manifest lane, validation evidence, and explicit non-goals. Treat [v0.31.0 release notes](releases/v0.31.0.md) as the historical source for performance decision-tree guidance, application-owned observability examples, realistic customer-profile quickstart evidence, root benchmark artifact anchors, validation evidence, and explicit non-goals. Treat [v0.30.0 release notes](releases/v0.30.0.md) as the historical source for support-bundle freshness, stale typed read-model generator inputs, and request-bound `ReadShape` troubleshooting. Treat [v0.29.0 release notes](releases/v0.29.0.md) as the historical source for provider schema guardrail guidance, finite supported-provider DDL safety claims, provider-neutral logical naming and provider-safe physical-name review, compatibility posture, validation evidence, and explicit non-goals. Treat [v0.28.0 release notes](releases/v0.28.0.md) as the historical source for provider read optimization boundaries and evidence posture. Treat [v0.27.0 release notes](releases/v0.27.0.md) as the historical source for EF lifecycle analyzer guardrails. Treat [v0.26.0 release notes](releases/v0.26.0.md) as the historical source for provider-tuning diagnostics, benchmark verifier evidence, migration and idempotency guardrails, stored-procedure artifact boundaries, request-bound ReadShape/read-plan diagnostics, and support-bundle-driven satellite/PIT/bridge typed read helpers. Treat [v0.25.0 release notes](releases/v0.25.0.md) as the historical source for request-bound ReadShape/read-plan diagnostics and support-bundle-driven satellite/PIT/bridge typed read helpers. Treat [v0.24.0 release notes](releases/v0.24.0.md) as the historical source for async chunk-source saves, async save helper convenience, guidance-only EF safety, listener-driven Activity tracing, benchmark-backed performance profiles, benchmark evidence references, and explicit non-goals. Treat [v0.23.0 release notes](releases/v0.23.0.md) as the historical source for listener-driven Activity tracing and benchmark-backed performance profile guidance. Treat [v0.22.0 release notes](releases/v0.22.0.md) as the historical source for the original support-bundle-driven typed satellite helper and stable `sha256-v1` hash governance baseline, public API snapshot evidence, and compiled-query alternatives. Treat [v0.21.0 release notes](releases/v0.21.0.md) as the historical source for PIT/bridge maintenance and read boundaries, original SQLite-only optimized PIT/bridge read dispatch, diagnostics/read-shape evidence, and PIT/bridge performance evidence. Treat [v0.20.0 release notes](releases/v0.20.0.md) as the historical source for staged PostgreSQL/MySQL ordered-bulk guidance, SQL Server native-bulk wording, Oracle retained direct optimization, and stored-procedure caveats.
- [ ] Treat the coordinated DVault package family as exactly these package ids: `DCoding.Data.DVault`, `DCoding.Data.DVault.Analyzers`, `DCoding.Data.DVault.Db2`, `DCoding.Data.DVault.MySql`, `DCoding.Data.DVault.Oracle`, `DCoding.Data.DVault.Postgres`, `DCoding.Data.DVault.Privacy`, `DCoding.Data.DVault.Sqlite`, and `DCoding.Data.DVault.SqlServer`.
- [ ] Choose one consumer package-version line per project: `8.45.0` for `net8.0` and EF Core 8, or `10.45.0` for `net10.0` and EF Core 10. Do not use a consumer-facing `0.45.0` package version from the v0.45.0 release label, do not mix both lines in one project or install example, and do not restore both 8.x and 10.x dependency lines for one target. Patch movement belongs only inside the selected target major line and must be backed by the project files, matrix tests, package verifier, release notes, and adopter guidance.
- [ ] For `8.45.0` / `net8.0`, use the current accepted dependency baseline: `Microsoft.EntityFrameworkCore` `8.0.28`, `Microsoft.EntityFrameworkCore.Relational` `8.0.28`, `Microsoft.Extensions.DependencyInjection.Abstractions` `8.0.2`, `IBM.EntityFrameworkCore` `8.0.0.400`, `Microsoft.EntityFrameworkCore.Sqlite` `8.0.28`, `MySql.EntityFrameworkCore` `8.0.26`, `Npgsql.EntityFrameworkCore.PostgreSQL` `8.0.11`, `Oracle.EntityFrameworkCore` `8.23.26200`, and `Microsoft.EntityFrameworkCore.SqlServer` `8.0.28`.
- [ ] For `10.45.0` / `net10.0`, use the current accepted dependency baseline: `Microsoft.EntityFrameworkCore` `10.0.9`, `Microsoft.EntityFrameworkCore.Relational` `10.0.9`, `Microsoft.Extensions.DependencyInjection.Abstractions` `10.0.9`, `IBM.EntityFrameworkCore` `10.0.0.100`, `Microsoft.EntityFrameworkCore.Sqlite` `10.0.9`, `MySql.EntityFrameworkCore` `10.0.7`, `Npgsql.EntityFrameworkCore.PostgreSQL` `10.0.2`, `Oracle.EntityFrameworkCore` `10.23.26200`, and `Microsoft.EntityFrameworkCore.SqlServer` `10.0.9`.
- [ ] Install `DCoding.Data.DVault.Analyzers` only in projects that own DVault Code-First declarations, compile-time generated row mapping declarations, or support-bundle-driven typed satellite, PIT, and bridge read helpers, and keep it local with `PrivateAssets="all"`. Treat `DMV1910` and `DMV1911` as project-local EF Core misuse diagnostics for generated shared-type tables, treat `DMV1912` through `DMV1914` as high-confidence source-visible EF lifecycle diagnostics for caller-owned model-cache discriminators, direct `UseModel(...)` compiled-model selection, and direct `AddDbContextPool<TContext>(...)` usage, and treat `DMV1960` through `DMV1969` as typed read-model generator metadata-source, fingerprint, unsupported-shape, collision, nullability-fallback, and skipped-helper outcomes. Do not treat lifecycle diagnostics as runtime guards, runtime behavior changes, provider-specific lifecycle guarantees, or whole-application inference.
- [ ] Also install and configure the normal Entity Framework Core database provider package used by the application, such as `IBM.EntityFrameworkCore` for DB2, SQLite, PostgreSQL, SQL Server, Oracle, or MySQL.
- [ ] Do not treat `src/DCoding.Data` as a consumer package. It is the non-packable source-root build anchor for the namespace family.
- [ ] Register `AddDVault()` and, when using a provider package, the matching provider startup extension shown in [Getting Started](getting-started.md#register-services). Register `AddDVaultPrivacy(...)` only for explicit privacy extension experiments or future privacy flows.
- [ ] Use the runnable SQLite or PostgreSQL quickstarts as setup evidence when a small local proof is useful; see [examples/README.md](../examples/README.md).

## Model Declaration Readiness

- [ ] Choose one authoritative model declaration path for each model boundary: Code-First metadata, metadata-first registry-backed metadata, or governed model-first `dvault.model.v1` artifacts.
- [ ] Use Code-First declarations when the model is local to one EF model and fits the fluent hub, hub-parent satellite, link-parent satellite, multi-active driving-key, explicit or derived link, and repeated same-hub role-bearing link surface described in [Getting Started](getting-started.md#declare-metadata).
- [ ] Use metadata-first registry-backed metadata when one shared `DataVaultMetadataModel` or `DataVaultMetadataRegistry` should drive schema projection, explicit saves, typed reads, diagnostics, examples, or provider setup.
- [ ] Use model-first governance when source-controlled `dvault.model.v1` JSON artifacts need review, strict import diagnostics, canonical export, projection into EF metadata, drift-report evidence, and optional consumer-owned support-bundle export after projection. Follow [Model-First Governance Workflow](model-first-governance.md).
- [ ] For repeated same-hub Code-First links, require an explicit relationship name plus distinct non-blank `Participant<TEntity>(string role)` roles so generated participant names and hash-key columns are unambiguous.
- [ ] Model effectivity as caller-owned link-parent satellite state declared with `Link(...).Satellite<TSatellite>(...)`, `Payload(...)`, and optional `DrivingKey(...)`; do not assume an effectivity-specific builder or metadata kind exists.
- [ ] Mark multi-active satellites, PIT declarations, and bridge declarations as explicit opt-in model features in the adopter's design notes. They are not prerequisites for ordinary hub, link, and satellite setup.

## Migration And Drift Guardrails

- [ ] Keep the configured `DbContext`, DVault metadata registration, EF design-time factory, and preflight entrypoint in the consumer project that owns migrations.
- [ ] Run DVault diagnostics against the configured design-time model before applying migrations. Use [DVault Dotnet EF Design-Time Workflow](architecture/dvault-dotnet-ef-design-time-workflow.md) for the supported v1 order and GitHub Actions baseline.
- [ ] Add a consumer-owned CI step that invokes `dotnet run --project <consumer-project> -- validate` through the application's design-time command host.
- [ ] Use `dotnet run --project <consumer-project> -- export --output <path>` only for artifact maintenance or reviewed refresh workflows, not as the default blocking CI gate.
- [ ] When a reviewed `dvault.model.v1` artifact exists, make `dotnet run --project <consumer-project> -- drift --artifact <path>` a blocking artifact-versus-design-time-model check. Do not generate a fresh artifact with `export` as the default CI gate.
- [ ] When the project owns a materialized EF snapshot model, compare it explicitly with `DataVaultModelDriftPreflightReporter.Compare(...)`; do not pass EF `ModelSnapshot` itself as a DVault public contract or expect DVault to discover snapshot files.
- [ ] Use `DataVaultPreflight.Run(...)` when one consumer-owned entrypoint should aggregate validation/provider explain, reviewed-artifact drift, snapshot-model drift, idempotency live-schema preflight, migration guardrail, and representative request diagnostics. Supply every optional lane explicitly.
- [ ] Add `dotnet run --project <consumer-project> -- support-bundle --output <path>` as a consumer-invoked troubleshooting artifact when configuration, provider-behavior evidence, or typed read-helper generator input must be shared. Keep the command host in the consumer project that owns the configured context.
- [ ] For existing persisted hash-key storage, use the [Hash-Key Storage Migration Guide](hash-key-storage-migration.md) before changing from `HexString` physical storage to `Binary` physical storage. Treat the support bundle or equivalent translated metadata facts as the preflight baseline, review the generated `dvault.hash-key-storage-migration.v1` dry-run manifest before writing database changes, keep stable-hash algorithm changes out of the same cutover, and fail closed when persisted compatibility facts drift.
- [ ] Run `dotnet run --project <consumer-project> -- guardrail --migration <name>` after scaffolding a migration and before apply or integration.
- [ ] Review migration guardrail output as operation-level `Safe`, `Risky`, or `Incompatible` evidence from `DataVaultMigrationOperationDiagnostics.AnalyzeReport(...)`; treat incompatible outcomes as blocking until the migration is corrected.
- [ ] Review provider schema guardrail facts before applying provider-specific DDL. Keep logical DVault names provider-neutral and traceable through `DataVaultAnnotationNames.ProducedName`, and review any provider-safe physical name, included-index shape, duplicate-index caveat, or load-timestamp storage mapping against the selected provider capability profile.
- [ ] Treat MySQL's `mysql-pomelo-v1` 64-character identifier cap as a migration-review constraint. A long generated logical name can remain the produced name, but the physical identifier must be deterministically projected to a provider-safe name or blocked before unsafe DDL is emitted.
- [ ] Treat Oracle primary-key-covered secondary indexes as unsafe or redundant generated metadata. Do not hand-edit a migration to recreate an Oracle index that the reviewed DVault profile omitted for this caveat.
- [ ] Treat unrecognized EF providers as unsupported for provider-specific DDL safety claims. Do not copy SQLite, Oracle, PostgreSQL, SQL Server, DB2, or MySQL guardrail guarantees to an unrecognized provider without a future explicit profile contract.
- [ ] Run idempotency preflight only from consumer-owned live-schema evidence, such as a `DataVaultLiveSchemaReadResult` supplied to `DataVaultPreflightRequest.IdempotencyLiveSchemaReadResult`. Treat missing, unsupported, unavailable, or mismatched idempotency-critical primary-key and secondary-index structures as explicit preflight outcomes, not hidden schema repair instructions.
- [ ] Use live-schema drift checks only within the documented boundary. Built-in successful catalog-reader coverage includes SQLite, PostgreSQL, SQL Server, Oracle, DB2, and MySQL. `IBM.EntityFrameworkCore` maps to the DB2 reader, and both `MySql.EntityFrameworkCore` and Pomelo map to the MySQL reader.
- [ ] Keep PostgreSQL, SQL Server, Oracle, DB2, and MySQL live-schema checks opt-in and operationally managed by the consumer application, including connection strings, credentials, reachable databases, lifecycle cleanup, and CI isolation.
- [ ] Do not expect DVault to ship a `dotnet ef` command shim, intercept EF CLI commands, auto-run migrations, or apply schema repairs. Those behaviors are outside the current v1 workflow.

## Save And Read Boundaries

- [ ] Use `IDataVaultSaveService` as the default write boundary. Each save request should carry an explicit UTC load timestamp and record source.
- [ ] Keep `DataVaultBulkSaveRequest` for already-materialized ordered batches. Use `DataVaultChunkedSaveRequest` with bounded `DataVaultSaveChunk` values when the loader needs materialized bounded chunking without changing explicit timestamps, record sources, request ordering, or caller-owned transaction behavior. Use `IDataVaultSaveService.SaveAsync(DbContext, IAsyncEnumerable<DataVaultSaveChunk>, ...)` only when the bounded chunk producer is already asynchronous and should be enumerated once in caller order.
- [ ] Treat provider-specific optimized saves as diagnostics-gated implementations behind the same explicit service. Review `SaveStrategy` status, provider name, selected strategy name, candidate facts, gate requirements, operation counts, and finite fallback causes before claiming provider-native behavior. Do not promote `DataVaultChunkedSaveRequest` as a provider-optimized default, and do not bypass the explicit service boundary for stored-procedure automation.
- [ ] For chunked and async source saves, preserve caller-supplied chunk order and request order, keep empty chunks as no-ops, and open the transaction before invoking `SaveAsync(...)` when all-or-nothing behavior across chunks is required. Follow [DVault V1 Streaming Explicit Save Contract](architecture/dvault-v1-streaming-explicit-save-contract.md) for ordering, cancellation, retained-state fallback, telemetry, limitations, and non-goals.
- [ ] Treat generated mapper helpers as compile-time ergonomics around the same explicit save boundary: they construct registry-backed operations but do not choose timestamps, record sources, contexts, providers, or save orchestration. Async helper overloads such as `SaveAsync<TSource>(...)`, `SaveHubsAsync(...)`, `SaveLinksAsync(...)`, and `SaveOrdinaryHubSatellitesAsync(...)` add bounded async source mapping convenience, not a second persistence subsystem.
- [ ] Keep ordinary EF `SaveChanges` separate from DVault persistence unless the application deliberately owns generated DVault rows and opts into metadata fill.
- [ ] Treat `UseDataVaultSaveChangesMetadataInterceptor(...)` as optional and metadata-only. It fills missing `LoadTimestamp` and `RecordSource` values on already tracked generated DVault rows; it does not create rows, compute hash keys, compute hash diffs, or replace `IDataVaultSaveService`.
- [ ] Treat `UseDataVaultSaveChangesGuardInterceptor(...)` as a separate optional runtime guard. Choose blocking mode for hard failures or warning mode for caller-observed reports; do not expect `AddDVault()` to enable it automatically.
- [ ] Prefer registry-backed requests or typed save helpers when they reduce repeated metadata declarations in loaders.
- [ ] Use `IDataVaultReadService` for provider-neutral latest and as-of satellite reads with caller-owned typed projectors, following the service boundary summarized in [Getting Started](getting-started.md#read-and-maintain).
- [ ] Use generated typed read helpers only when the project opts in with `DVaultGenerateTypedReadModels=true` and supplies one reviewed `dvault.support-bundle.v1` additional file. Pin `DVaultTypedReadModelMetadataSourceFingerprint` when build-time drift enforcement is required.
- [ ] Limit generated typed read helpers to the implemented v1 helper shapes: satellite latest/current/as-of; PIT as-of for hub-parent ordinary PITs, hub-parent multi-active PITs with one canonical driving-key family, and bounded link-parent PITs with unique non-multi-active satellites; bridge helpers for many-to-many `From`/`To` and hierarchy `Ancestor`/`Descendant` traversal with required `maximumDepth`.
- [ ] Keep dynamic `IDataVaultReadService` requests as the default for runtime-built shapes and caller-selected projectors, including PIT or bridge requests whose shape remains outside the generated-helper contract. Use consumer-owned EF compiled queries only for stable direct EF shared-type-table expressions documented in [DVault EF Compiled Compatibility](architecture/dvault-ef-compiled-compatibility.md).
- [ ] Use `IDataVaultPitMaintenanceService` after satellite ingestion when PIT declarations should be materialized explicitly; PIT-backed reads then consume those maintained rows. Use full PIT rebuilds for one generated PIT table and bounded parent maintenance for explicit parent hash keys, including late-arriving history correction for those parents. Hub-parent PITs may include ordinary satellites and multi-active satellites only when all referenced multi-active satellites share one canonical driving-key name/order family. Follow [DVault V1 PIT And Bridge Boundary](architecture/dvault-v1-pit-bridge-boundary.md) for the centralized PIT/bridge maintenance, read, diagnostics, and evidence boundary.
- [ ] Use `IDataVaultBridgeMaintenanceService` after source-link ingestion when bridge declarations should be materialized explicitly; bridge reads then consume those maintained rows. Use full bridge rebuilds when destructive hierarchy changes require row removal or increased `TraversalDepth`; `MaintainBridgeAsync(...)` is not delete-aware.
- [ ] Treat `AddDVaultSqlite()`, `AddDVaultPostgres()`, `AddDVaultSqlServer()`, `AddDVaultMySql()`, `AddDVaultOracle()`, and `AddDVaultDb2()` as repository-proven diagnostics-gated latest-satellite/PIT/bridge read provider candidate paths for their supported shapes. Treat DB2 save execution as a diagnostics-gated optimized clean-context strategy for ordinary hub, link, and satellite rows, not as a staged bulk or provider-native chunk lane. Unsupported providers, unsupported latest-satellite or PIT/bridge request shapes, incomplete generated read-model projection evidence, or stale maintenance evidence fall back to the provider-neutral read pipelines without implicit maintenance side effects.
- [ ] Do not expect current/as-of satellite helpers, PIT-backed reads, or bridge reads to refresh read-model rows, schedule automatic PIT or bridge maintenance, infer graph traversal APIs, or change the explicit service boundaries.

## Telemetry, Explainability, And Support Evidence

- [ ] Keep `AddDVault()` as the default telemetry-free startup path unless the application intentionally opts into observability.
- [ ] Register `AddDVaultTelemetry()` only when the application wants the built-in `System.Diagnostics.Metrics` observer for explicit DVault save/read attempts.
- [ ] Register custom `IDataVaultTelemetryObserver` implementations when code-facing bounded summaries are needed. Observer failures are ignored by DVault and must not be used as persistence or read control flow.
- [ ] Treat Activity tracing as a sibling observability surface. `AddDVault()` remains telemetry-free by default; applications opt into tracing by registering an `ActivityListener`, OpenTelemetry tracing provider, or equivalent listener for the `DCoding.Data.DVault` ActivitySource. `AddDVaultTelemetry()`, built-in `System.Diagnostics.Metrics`, and `IDataVaultTelemetryObserver` are not prerequisites for tracing and do not replace tracing.
- [ ] Keep exporters, collectors, dashboards, alerting, hosting, sampling policy, baggage, custom trace identifiers, and custom correlation storage application-owned. Follow [DVault V1 Activity Tracing Contract](architecture/dvault-v1-activity-tracing-contract.md) for the exact ActivitySource, span-name, event-name, tag-key, sampling, status, and omission rules.
- [ ] Preserve the Activity tracing redaction boundary: no raw business keys or hash-key values, payload values, record sources, SQL text, credentials, connection strings, provider messages, exception messages, stack traces, support-bundle content, or full diagnostic text in Activity names, tags, events, status descriptions, or exception metadata.
- [ ] Treat chunked-save telemetry as bounded operational evidence: chunk count, processed chunk count, retained-state high-water counts, finite retained-state fallback causes, unsupported-shape classifications, and transaction guidance. Do not expect raw hash keys, payload values, per-parent retained state entries, or provider-specific SQL text from this surface.
- [ ] Treat telemetry as bounded operational evidence only. Do not expect DVault to configure metric listeners, exporters, dashboards, alert rules, backend-specific pipelines, or high-cardinality raw tags.
- [ ] Treat provider capability profile, provider-behavior profile, save strategy, read strategy, and read-shape diagnostics as deterministic explain output. Follow [DVault V2 Redacted Read-Plan Explain Contract](architecture/dvault-v2-redacted-read-plan-explain-contract.md) for the request-bound read-shape payload and redaction rules. Do not treat these surfaces as raw SQL validation, provider query plans, credential-bearing dumps, or provider-specific orchestration.
- [ ] Use request-bound read-shape diagnostics and bounded benchmark evidence for query-shape tuning guidance. Do not expect DVault to emit raw SQL, create indexes automatically, inspect provider physical plans, or turn diagnostics into provider-specific physical-design promises.
- [ ] Capture SQL only when a claim depends on emitted SQL shape, index usage, batching behavior, or materialization behavior. Do not require companion SQL captures for compiled-model/query/pooling timing and allocation claims that are already bounded by [DVault EF Compiled Compatibility](architecture/dvault-ef-compiled-compatibility.md).
- [ ] Use the `support-bundle` design-time verb for redacted diagnostic snapshots under the `dvault.support-bundle.v1` contract. The default path analyzes the configured design-time model and does not open a live database connection.
- [ ] Use `--artifact <path>` to include reviewed `dvault.model.v1` drift evidence when a committed artifact exists.
- [ ] When using typed read-helper generation, review the exported support bundle as the generator input and pass exactly one authoritative bundle as an analyzer additional file. Do not pass raw `dvault.model.v1` files directly to the generator or rely on repository-root baseline artifacts that are not owned by the consuming project.
- [ ] Use `--live-schema` only in an environment where the consumer application owns the reachable database, credentials, lifecycle cleanup, and CI isolation. Keep non-SQLite live-schema checks external opt-in evidence.
- [ ] Supply representative request-bound save/read strategy diagnostics through `DataVaultDesignTimeCommandHost.CreateSupportBundleDiagnostics` when that evidence is needed. PIT and bridge typed helper generation depends on representative `ReadShape` evidence reaching the support bundle this way. Do not expect the generic command runner to invent representative requests.
- [ ] Keep support-bundle storage, attachment, retention, transport, and approval workflows consumer-owned. DVault exports JSON; it does not publish or route the artifact.

## Provider And Advanced Feature Posture

- [ ] Confirm the selected provider package matches the configured EF provider and the application's supported database. Use the [README installation guidance](../README.md#installation) and [Getting Started](getting-started.md#register-services) as the package responsibility reference.
- [ ] Confirm provider-specific schema safety claims stay inside the finite documented provider baseline: SQLite (`sqlite-v1`), Oracle (`oracle-v1`), PostgreSQL (`postgres-v1`), SQL Server (`sqlserver-v1`), DB2 (`db2-v1`), and MySQL (`mysql-pomelo-v1`). Do not infer provider-specific identifier, included-index, duplicate-index, load-timestamp, or migration DDL safety for providers outside that set.
- [ ] Treat [DVault EF Compiled Compatibility](architecture/dvault-ef-compiled-compatibility.md) as the bounded compiled-model, compiled-query, `DbContext` pooling, and EF lifecycle analyzer guidance. Registry-backed `UseDataVaultMetadata(...)`, fixed-shape `UseModel(runtimeModel)`, stable direct EF compiled queries over generated shared-type tables, and options-only pooling for one fixed metadata/model shape remain supported and non-diagnostic. Use that document for caller-owned `IModelCacheKeyFactory` duties when tenant, schema, naming, provider, or profile state changes the realized model. Do not treat `DMV1912` through `DMV1914` as runtime guards, provider-specific lifecycle guarantees, or whole-application inference.
- [ ] Use [Performance Profiles](performance-profiles.md) for detailed benchmark-backed starting guidance before selecting small app-local, medium chunked-ingestion, staged provider-ingestion, or read-model-heavy tuning paths.
- [ ] Apply the v0.43 provider evidence and tuning gates from [DVault v0.43.0 Release Notes](releases/v0.43.0.md), [Provider Optimization Evidence Matrix](plans/provider-optimization-evidence-matrix.md), and [Provider Optimization Gap Matrix](plans/provider-optimization-gap-matrix.md). Treat benchmark verifier evidence as triplet consistency, provider-guidance row visibility, optional-provider skipped-row visibility, regression-budget checks, and preserved completed/skipped provider outcomes proved by repository tests; do not paste raw benchmark tables into adopter records. ## Current Limitations To Keep Visible

- DVault's default path is explicit and service-based. It does not make Data Vault persistence implicit through EF entity tracking.
- `DMV1912` through `DMV1914` are analyzer-only lifecycle diagnostics for direct source-visible evidence. They do not add runtime guards, runtime behavior changes, compiled-model generation, provider-specific lifecycle guarantees, cross-assembly inference, whole-application inference, arbitrary helper expansion, generated compiled-model artifact inspection, or pooled factory diagnostics.
- Chunked and async source explicit saves do not introduce provider-native async writes, provider-native chunk execution, background ingestion, file ingestion, CDC ingestion, schedulers, or implicit `SaveChanges` streaming. Staged provider bulk guidance is separate provider-specific optimized ordered-bulk guidance, not a chunked-save default.
- The carried-forward v0.20.0 staged bulk guidance is provider-specific, not universal. PostgreSQL and MySQL have documented staged lanes; SQL Server remains native bulk, and Oracle remains direct optimized batching until measured evidence selects staged Oracle bulk.
- Stored procedures are not a default runtime path. They require explicit application-owned design, migration synchronization, provider proof, and operational rollback guidance.
- `AddDVault()` remains telemetry-free by default. Telemetry requires explicit `AddDVaultTelemetry()` or custom `IDataVaultTelemetryObserver` registration and is limited to explicit DVault save/read attempts.
- `AddDVaultPrivacy(...)` remains an explicit opt-in privacy proof registration path. It does not enable automatic encryption, pseudonymization, redaction, export filtering, deletion, compliance workflow ownership, key lifecycle ownership, or provider-native encryption behavior.
- Activity tracing remains listener-driven through the `DCoding.Data.DVault` ActivitySource. DVault does not add OpenTelemetry packages, exporters, collectors, dashboards, alerting, hosting, sampling policy, baggage, custom trace identifiers, or custom correlation storage, and tracing output must not carry raw keys, payload values, record sources, SQL text, credentials, connection strings, provider messages, exception messages, stack traces, support bundles, or diagnostic text.
- `UseDataVaultSaveChangesGuardInterceptor(...)` remains an explicit runtime opt-in. It supports warning and blocking modes for generated-row guard findings, but it does not replace `IDataVaultSaveService` or turn ordinary EF tracking into the default DVault persistence path.
- `DataVaultPreflight.Run(...)` aggregates supplied validation, drift, migration, and representative diagnostics lanes. It does not discover snapshots, scan repositories, invent representative requests, run migrations, repair schemas, or open live databases by default.
- The `support-bundle` verb is hosted by the consumer application and exports redacted JSON only when invoked. DVault does not ship a standalone CLI, upload support bundles, attach them to tickets, or open live database connections by default.
- Typed read-model generation is opt-in and support-bundle-driven for bounded satellite, PIT, and bridge helper shapes. The generator does not parse raw `dvault.model.v1` additional files directly, infer helpers from source-visible declarations, generate provider-specific SQL, compile dynamic read requests, emit unbounded traversal helpers, maintain PIT or bridge rows, or create dedicated approval snapshots.
- Dependent child key modeling is outside the current public documentation baseline.
- Repeated same-hub runtime and metadata support does not imply typed mapper or source-generator parity for repeated same-hub mappings.
- Design-time guardrails are explicit library APIs owned by the consumer project. DVault does not intercept EF migration commands.
- Provider schema guardrails are review and diagnostics boundaries for DVault-owned generated metadata. They do not add automatic migration repair or execution, do not rewrite consumer-authored migrations or raw SQL, do not silently drop generated keys or unique requirements, and do not provide provider-specific guarantees outside SQLite, Oracle, PostgreSQL, SQL Server, DB2, and MySQL.
- PIT-backed reads operate over PIT tables maintained through explicit `IDataVaultPitMaintenanceService` rebuild or parent-maintenance calls; those calls may use explicit PIT metadata or registry-backed exact logical-name/CLR-mapping PIT resolution for hub-parent ordinary PITs, the bounded hub-parent shared-driving-key multi-active tuple baseline, and link-parent non-multi-active runtime PITs. Reads do not refresh PIT rows implicitly. The `dvault.model.v1` PIT artifact shape remains hub-parent-only; link-parent multi-active PITs, incompatible driving-key families, cross-product tuple semantics, tuple-filter requests, registry-backed PIT as-of reads, automatic orchestration, and provider-specific PIT maintenance remain outside the current baseline. Bridge maintenance is available as an explicit caller-invoked service that rebuilds or incrementally maintains one bridge from persisted source-link rows; it is not automatic or delete-aware. Keep the detailed boundary in [DVault V1 PIT And Bridge Boundary](architecture/dvault-v1-pit-bridge-boundary.md).
- SQLite, PostgreSQL, SQL Server, MySQL, Oracle, and DB2 are the repository-proven diagnostics-gated latest-satellite/PIT/bridge read provider candidate paths for supported shapes. Unsupported providers, unsupported latest-satellite or PIT/bridge request shapes, incomplete generated read-model projection evidence, and stale PIT/bridge maintenance evidence fall back to provider-neutral read pipelines.
- SQLite is the default local live-schema proof because it does not need external infrastructure. PostgreSQL, SQL Server, Oracle, DB2, and MySQL live-schema readers are built in, but non-SQLite live-schema checks remain external opt-in operational checks.
- Advanced configuration hooks beyond the documented record-source resolver path remain optional planning boundaries, not required setup.
